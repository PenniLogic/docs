## ADR-015 — Money wire format, time and idempotency conventions
**Status:** ACCEPTED · 2026-09-30

**Decision.** Three conventions bind every service, every contract and every generated client:

1. **Money** is an integer count of ISO 4217 minor units plus a currency code inside every process
   (ADR-001) and crosses every JSON boundary as one object of two strings,
   `{"amount":"-1234.56","currency":"INR"}`, whose `amount` is a canonical decimal string carrying
   exactly the currency's minor-unit exponent of fraction digits. Raw JSON numbers — floating point
   or 64-bit integer — are rejected. Each language has one generated wrapper type and one named
   serialisation seam; no raw primitive carries money into application code.
2. **Instants** are stored and transported in UTC in the fixed 24-character RFC 3339 form
   `2026-09-30T04:52:08.439Z`. Calendar reasoning — day, month, pay period — is done server-side in
   the user's IANA time zone stored on the profile, never from an offset and never by a client.
3. **Every state-changing operation** carries a client-generated UUIDv4 `Idempotency-Key`, scoped to
   (principal, operation, key), honoured for 30 days from first receipt, persisted together with its
   payload before the first send and reused unchanged on every retry. Same key and same payload
   replays the stored response; same key and a different payload returns one stable `422` conflict
   with no effect. Reinstall and queue loss are absorbed by the structured duplicate-detection path
   whose key ADR-018 defines, never by a silent second post.

**Why.** The contract skeleton (`PenniLogic/contracts#1`) types amounts as `int64` JSON numbers.
Every mainstream JavaScript runtime parses a JSON number into an IEEE 754 binary64 `number`, so
integer precision ends at `Number.MAX_SAFE_INTEGER = 9007199254740991` (2^53 − 1):
`JSON.parse("9007199254740993")` yields `9007199254740992` with no error. A decimal fraction in a
JSON number (`1234.56`) is corrupted the same way in every language whose default parser is a
binary float, and RFC 8259 §6 permits implementations to lose precision beyond binary64. Strings
survive every parser byte for byte. Making the string *canonical* (one spelling per value) means
string equality is value equality, so fingerprints, deduplication and generated fixtures are stable
across Kotlin, TypeScript and Python. Idempotency and time conventions decide, together with the
money form, whether a retried or rescheduled financial write is correct; deciding them separately
would let three clients invent three incompatible answers.

### 1. Money on the wire

**1.1 The only money shape.** Every monetary field in the OpenAPI document references one component:

```yaml
Money:
  type: object
  additionalProperties: false
  required: [amount, currency]
  properties:
    amount:
      type: string
      pattern: '^(0(\.[0-9]+)?|-?[1-9][0-9]*(\.[0-9]+)?|-0\.[0-9]*[1-9][0-9]*)$'
      maxLength: 21
      description: Canonical decimal string in major units; exactly the currency exponent of fraction digits.
    currency:
      type: string
      pattern: '^[A-Z]{3}$'
      description: ISO 4217 alphabetic code present in the published currency registry.
  example: { amount: "-1234.56", currency: "INR" }
```

No schema may declare a standalone amount string, a money-typed number, a defaulted currency or an
additional member on this object. The generated wrapper type in each language *is* this component;
the raw `{amount, currency}` shape is internal to the generated client package and is not exported.

**1.2 Canonical `amount` grammar.** ASCII only. An optional leading `-` (never `+`), an integer part
with no leading zero other than a lone `0`, and — when the currency exponent `e` is greater than
zero — a `.` followed by **exactly `e` digits** (INR `e = 2`: `"1234.56"`; JPY `e = 0`: `"1234"`,
no point; KWD `e = 3`: `"1.500"`). No exponent notation, thousands separators, whitespace, Unicode
digits, `NaN`, `Infinity` or negative zero (`"-0.00"` is rejected; zero is unsigned). The exponent
comes from the currency registry (§1.4), never from counting digits, so `"12.5"` for INR fails as a
scale mismatch rather than being read as ₹12.50. The exact-scale rule is what makes the form unique:
`"1.5"` and `"1.50"` never coexist as spellings of one value.

**1.3 Range.** The value in minor units lies in the symmetric interval
`[−9223372036854775807, 9223372036854775807]` (±(2^63 − 1)). `−2^63` (`Long.MIN_VALUE`) is
excluded so negation can never overflow. The wire maximum per exponent is therefore INR
`"92233720368547758.07"`, JPY `"9223372036854775807"`, KWD `"9223372036854775.807"`; total digits
never exceed 19, hence `maxLength: 21`. Server arithmetic on minor units is overflow-checked
(`Math.addExact` and friends; Postgres `BIGINT` raises) and fails the request rather than wrapping.

**1.4 Currency registry.** `PenniLogic/contracts` publishes `currency-registry.v1.json` with one entry
per accepted code — `code`, `exponent`, `minor_unit_name` — consumed by the API, the codecs and the
conformance fixtures, so no repository hardcodes `/100` (ADR-001). The MVP registry carries `INR`
(2, paise) plus the exponent-0 and exponent-3 codes the fixtures need (`JPY`, `KWD`). Accepting a
code at the codec is not offering it in the product: which currencies a ledger accepts is ADR-017's
decision and multi-currency surfaces are E30's; the application layer refuses a registry currency
the ledger does not admit with a validation rejection. Adding a currency is an additive registry
change. Every code is validated against the registry; `"inr"`, `"XYZ"` and an absent `currency`
member are rejected.

**1.5 Rejections and their reasons.** The codec rejects, with a machine-readable reason that
carries the field name and never the offending value: a JSON number of any kind
(`number_not_string` — a fraction is corrupted by binary64 parsing, an integer above 2^53 − 1 is
not reliably representable and is silently rounded by JavaScript, and a bare integer is ambiguous
about scale and currency); a string
violating §1.2 (`grammar`); wrong fraction digit count (`scale_mismatch`); `-0` forms
(`negative_zero`); a value outside §1.3 (`out_of_range`); a code absent from the registry
(`currency_unknown`); a missing member or extra member (`shape`). At the API this is a
`validation_rejected` condition binding to the client state `error` in its validation variant, which
names the field and echoes no monetary value (`T-CON-12`; `product/client-state-taxonomy.md` §3.3,
§9).

**1.6 Related rules.** The sign is semantic: ledger entries are signed (ADR-002); a field that must
be non-negative says so in its description and the server validates it. Money in a query string
(filters such as a minimum amount) uses the same canonical string with a separate `currency`
parameter (`T-CON-17`). Non-money exact decimals — interest and FX rates, percentages — also travel
as decimal strings with a fixed per-field scale stated by their contract (ADR-017 for FX quotes);
they are never `Money` and never JSON numbers. Any JSON a service stores or emits on another path —
audit rows, metadata, exports, the administrative API — carries money in this same object form, so
an admin console cannot receive a raw number the customer API would have refused. The canonical
string is not a display string: locale rendering (₹1,23,456.78, `PenniLogic/android#34`) and
locale-aware parsing of user input happen at the presentation layer and produce or consume the
wrapper, never a string that bypasses it.

### 2. Language wrappers and serialisation seams

One wrapper per language, generated or published from `PenniLogic/contracts` (`T-SCA-CON-01`,
`PenniLogic/contracts#2`) and pinned by every consumer, so `api`, `android`, `web`, `admin` and
`ai-service` run identical codec code for their language. The seam is the single place where the
wrapper is constructed from the wire object and destructed back to it. Nothing else parses or formats
money; a raw primitive that escapes the seam is a defect the tests in §7 catch.

| | Kotlin (`api`, `android`) | TypeScript (`web`, `admin`) | Python (`ai-service`) |
|---|---|---|---|
| Internal representation | `Long` minor units + `CurrencyCode` | `bigint` minor units + `CurrencyCode` | `decimal.Decimal` at the currency's scale + `str` currency |
| Construction seam | `Money.parse(amount, currency)` inside `MoneySerializer` (`kotlinx.serialization`; the Ktor module the generated client registers) | `Money.fromWire(wire)` inside the generated client's decoder | `Money.from_wire(mapping)` inside the generated Pydantic model's `before` validator |
| Destruction seam | `Money.toWire()` in the same serializer | `Money.toWire()`; `toJSON()` returns it so `JSON.stringify` never meets the `bigint` | `Money.to_wire()` in the model serializer |
| Forbidden types for money | `Double`, `Float`, `BigDecimal` in domain or DTO fields, bare `Long` outside the class | `number`, bare `bigint` outside the class, `parseFloat`, `Number()` on an amount | `float`, bare `int`, bare `Decimal` outside the class |
| Parsing path | grammar check, digits concatenated and parsed with `toLong()` — the digit string of `−2^63` (`9223372036854775808`) exceeds `Long.MAX_VALUE`, fails to parse and is rejected | grammar check, `BigInt(digits)`, compare with `9223372036854775807n` | grammar check, `Decimal(text)` under `MONEY_CONTEXT`, `int(amount.scaleb(exponent))` range check |
| Formatting path | integer division and modulo by `10^e`, zero-padded fraction | same on `bigint` | `format(amount, "f")` — never `str()`, which may emit exponent notation, and never `float()` |
| Arithmetic | `plus`, `minus`, `unaryMinus`, comparison: same currency only, `*Exact` overflow checks; `allocate(shares)` distributes remainders deterministically and sums exactly (`architecture/01-domain-model.md` §4.3) | `plus`, `minus`, `negate`, `compare`: same currency only, range-checked | none: equality and same-currency ordering only |
| Maximum representable | full §1.3 range | full §1.3 range | full §1.3 range |
| Local storage | Room: `amount_minor INTEGER` + `currency TEXT`, never `REAL`; Postgres: `BIGINT` + `CHAR(3)` (ADR-001) | not persisted as a number; the wire object when cached | not persisted |

**Currency mismatch** in any operation is an immediate failure, never a coercion: equality across
currencies is simply `false`; ordering and arithmetic across currencies fail. **Every destruction
seam self-checks**: the formatted string must satisfy §1.2 and re-parse to the same minor units,
so a negative zero, a wrong scale or an out-of-range result can never leave a process. **Rounding** is
never performed by a wrapper. A domain computation that must round — interest, FX, an allocation —
is a named server-side function that states its rounding mode in its contract; the default is
`HALF_EVEN`, and any other mode (for example `HALF_UP` to mirror a lender statement) is declared per
operation by the record or contract that owns the computation (ADR-017, `T-CON-01`). Rounding is
never performed on a client (constitution: deterministic, server-authoritative calculation).

**2.1 TypeScript: `bigint` is internal only.** A `bigint` cannot cross a JSON boundary
(`JSON.stringify(1n)` throws `TypeError: Do not know how to serialize a BigInt`) and cannot cross a
React Server Component or Server Action boundary as part of the wrapper: the React Flight
serialisation accepts only plain data, so a `Money` class instance cannot be passed at all, and
older React and Next.js versions reject a `bigint` outright. Therefore `bigint` is an
internal representation of the wrapper and nothing more. The only portable form of money in a web
process is the canonical `{amount, currency}` object: across `fetch`, RSC props, Server Action
arguments and results, `postMessage`, URL parameters, `localStorage`/IndexedDB and logs, money is
the wire object, and the receiving side reconstructs the wrapper at the seam. `number` is never used
for money at all (§Why).

**2.2 Python: decimal context.** The wrapper runs its seam under a dedicated context:

```python
MONEY_CONTEXT = decimal.Context(
    prec=28,
    rounding=decimal.ROUND_HALF_EVEN,
    traps=[decimal.InvalidOperation, decimal.DivisionByZero, decimal.Overflow,
           decimal.Inexact, decimal.Rounded, decimal.FloatOperation],
)
```

Applied with `decimal.localcontext(MONEY_CONTEXT)` inside the seam, never by `setcontext`. The
declared rounding mode is `HALF_EVEN`; because `Inexact` and `Rounded` are trapped, any operation
that would actually round raises instead, so the `ai-service` cannot round money at all — it carries
figures the core API computed (PRODUCT.md: AI never computes money). `FloatOperation` makes
`Decimal(1.1)` and any ordering comparison with a `float` raise; Python still allows equality with
a `float` under the trap, so the wrapper's `__eq__` accepts only another `Money` of the same
currency. `from_wire` accepts only `str` members: `float`, `int`, `bool` and `Decimal` inputs are
rejected (`number_not_string`/`shape`), the generated Pydantic model is `strict`, and the model is
the only place the wire mapping is parsed or rendered, so no `float`, bare `int` or bare `Decimal`
reaches a route handler, a tool result or a prompt builder. `minor_units` is exposed read-only for
fixtures and tests.

### 3. Time

**3.1 Instants.** Transport form is exactly `YYYY-MM-DDTHH:MM:SS.sssZ` (24 characters, uppercase
`T` and `Z`, three fraction digits always present, years `0001`–`9999`, valid proleptic Gregorian
date, no leap second). Anything else — an offset such as `+05:30`, a missing or longer fraction,
lowercase letters, `2026-02-30` — is rejected as `validation_rejected`. Instants are truncated to
milliseconds at creation by the application everywhere (`Instant.truncatedTo(MILLIS)` on the server,
`Date` on the web, `microsecond % 1000 == 0` in Python) so storage, transport and fingerprints agree;
Postgres columns are `TIMESTAMPTZ(3)` as a guard, SQLite stores epoch milliseconds or the canonical
string, and `T-SYN-04` proves the round trip. Server-assigned instants (`recorded_at`, `booked_at`)
never trust a client clock. A date-only fact (statement `value_date`, a due date) is a
`YYYY-MM-DD` `LocalDate`; the server never invents a time of day for it.

```yaml
Instant:
  type: string
  format: date-time
  pattern: '^[0-9]{4}-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])T([01][0-9]|2[0-3]):[0-5][0-9]:[0-5][0-9]\.[0-9]{3}Z$'
  minLength: 24
  maxLength: 24
TimeZone:
  type: string
  pattern: '^[A-Za-z][A-Za-z0-9_+-]*(/[A-Za-z0-9_+-]+)*$'
  maxLength: 64
  example: Asia/Kolkata
```

Internal types: `java.time.Instant` (Kotlin), a wrapper over epoch milliseconds (TypeScript — safe in
`number`, unlike money), timezone-aware UTC `datetime` (Python). Each seam validates the grammar,
parses, re-formats and requires the result to equal the input, which rejects calendar roll-over such
as 30 February.

**3.2 The user's time zone.** An IANA identifier (`Asia/Kolkata`) is stored on the profile,
required at profile creation, supplied by the client from the device zone
(`TimeZone.getDefault().id`, `Intl.DateTimeFormat().resolvedOptions().timeZone`) and changeable by the
user. It is validated against the server's tz database, canonicalised from link names, and is never
inferred from a UTC offset: offsets are not zones. It is personal data and is protected and excluded
from logs and signals like any other profile field.

**3.3 Month and pay-period boundary rule.** An instant belongs to the local calendar day, month and
pay period that contain it in the profile zone. A period is the half-open interval `[start, end)` of
UTC instants where `start` is the first instant of the local day on which the period begins
(local `00:00:00.000` resolved by the zone's own rules, so a skipped or repeated local midnight is
resolved the way the platform's zone rules resolve it) and `end` is the `start` of the next period.
Calendar month `M` is `[day 1 of M, day 1 of M+1)`. A pay period anchored on day-of-month `D`
begins on local day `D`, clamped to the month's last day when `D` does not exist (31 → 30 April,
28/29 February), and ends at the next anchor; a weekly or fortnightly anchor begins on its anchor
date and repeats every 7 or 14 local days. The pay-cycle configuration shape is `T-CON-08`'s; the
quota reset boundary and its zone are ADR-023's. Boundaries are computed **only on the server**, at
read time, from immutable stored instants and the current profile zone; responses carry each
period's `start`, `end` and the `time_zone` used, and clients render them without recomputing
(ADR-010: derive, never sync a cached figure). Changing the profile zone therefore re-derives every
report consistently and rewrites nothing.

### 4. Idempotency

**4.1 Which operations require a key.** Every `POST`, `PUT`, `PATCH` and `DELETE` operation of every
service under the contract — the core API, the `ai-service` and the administrative API — declares
the `IdempotencyKey` header parameter as required. An operation may be exempt only by an explicit
`x-idempotency` extension with a reason: `not-applicable` for a side-effect-free `POST` such as a
search query, `per-item` for a batch whose every item carries its own key (the sync `apply` batch,
whose per-change identifier `T-SYN-01` defines under these same rules), `provider-event` for a
webhook deduplicated by the provider's event identifier (`PenniLogic/api#32`), and `auth` for the
session and authentication operations owned by ADR-019. An operation whose request or response
contains `Money` can never be exempt. The contract lint enforces this table; `T-QA-01` fails a
build in which an endpoint accepts a financial write without a key. The header is ignored on safe
methods, and the lint forbids declaring it there.

**4.2 Key form and generation.** A UUID version 4 in lowercase canonical form, generated by the
client from a cryptographically secure random source (`UUID.randomUUID()`, `crypto.randomUUID()`,
`uuid.uuid4()`), one per intended effect. The server validates the version nibble, so a name-based
(v3/v5) key derived from payload content or a v1 key carrying a node address is rejected as
malformed. A key is never derived from payload content — two genuine identical purchases must not
collide, and no raw-derived digest crosses the API (ADR-004) — and is never issued by the server,
because an offline client must be able to queue the write before it has ever spoken to the server.

```yaml
parameters:
  IdempotencyKey:
    name: Idempotency-Key
    in: header
    required: true
    schema:
      type: string
      pattern: '^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$'
headers:
  IdempotentReplayed:
    schema: { type: boolean }
    description: Present and true when the response was served from the idempotency store.
```

**4.3 Scope.** A key is unique within (authenticated principal, operation, key), where the operation
is the HTTP method plus path template. The same key on another operation is another key; the same
key presented by another principal is independent, so no principal can probe, replay or collide with
another's keys. Administrative operations use the operator principal under the same rule.

**4.4 Server behaviour.**

1. Missing or malformed key on a required operation: `400`, condition `request_failed`, no effect.
2. Unknown key: the server executes the operation and, **in the same database transaction as the
   effect**, inserts the record (principal, operation, key, fingerprint, response status, response
   body, `first_received_at`, `expires_at = first_received_at + P30D`). Effect and record commit or
   roll back together; a crash can never leave one without the other.
3. Known key, same fingerprint: the stored status and body are returned unchanged with
   `Idempotent-Replayed: true`, no effect — a replay is a receipt of the original effect, not the
   resource's current state.
4. Known key, different fingerprint: `422`, condition `idempotency_payload_mismatch`, body
   `application/problem+json` carrying the key and a correlation identifier, never the stored
   response, the original payload or any amount. The response is the same every time and regardless
   of what differs. No effect.
5. Same key while the first request is still uncommitted: the server either waits for the outcome
   and replays it or returns `409` with `Retry-After`; it never executes twice. The store's primary
   key (principal, operation, key) enforces this under concurrency — an implementation may reserve
   the key before executing or let the second insert fail and roll back its effect; exactly one
   effect commits either way.
6. A refusal or failure — validation, entitlement, `5xx`, a serialization retry that gives up —
   commits no record, because no effect happened; the same key retried later is evaluated afresh.

The fingerprint is SHA-256 over the method, the concrete request target (path with parameters and
query) and the RFC 8785 canonical JSON of the request body (raw bytes for a non-JSON body such as a
statement upload). It is a digest, so the store holds no request payload; the stored response body
is per-user data encrypted under the principal's DEK (ADR-006) and purged at `expires_at`. The
illustrative `idempotency_key TEXT UNIQUE` column and any fixed 24-hour lifetime in
`architecture/03-stack-and-monetization.md` §12 are replaced by this scoped store.

**4.5 Lifetime.** A key is honoured for **30 days from the server's first receipt** (`P30D`,
published as contract metadata like the revocation bounds of `T-CON-04`). The clock starts at first
receipt because the server has no state before it; a first send after any delay is simply a first
send. After expiry the record is purged and the key presented again would execute as new, so
clients must never retry automatically across that horizon (§4.6). Thirty days covers a month of
offline use and every plausible lost-response replay window at bounded storage cost.

**4.6 Client lifecycle: persist before first send, reuse unchanged.** Before the first network
attempt the client generates the key, serialises the payload once, and durably persists
`(key, operation, payload bytes, source_event_id, created_at, state)` in its encrypted queue
(Room + SQLCipher on Android, ADR-010; IndexedDB or the same durable store the web app uses for
pending writes). Every retry — background or user-initiated `retry` — resends the same key and the
same bytes; automatic retries never modify a payload. An edited request is a new intended effect
and gets a new key; a `validation_rejected` response therefore leads to an edited resubmission under
a new key (`product/client-state-taxonomy.md` §3.3), never to the rejected bytes again.
`first_attempted_at` is persisted at the first send. Automatic retries of an entry stop **14 days
after its first attempt** (`P14D`, contract metadata): the entry is surfaced as a failed record that
needs the user's decision (`T-SYN-03`), not dropped and not resent, because a later retry could
outlive the server record. The user's choices are to discard it or to submit it again, and a
resubmission is a new intended effect under a new key that the structured duplicate-detection path
(§4.7) then screens; the client never resends the expired key. An entry never attempted may be
sent at any age. A `422` mismatch marks
the entry failed and is never answered by minting a new key for the same bytes. A successful or
replayed `2xx` marks it acknowledged. A client that cannot persist the key before sending — a web
page without durable storage — does not retry across a reload, treats the outcome as unknown, and
refreshes server state rather than resubmitting (taxonomy §3.3: no claim that a write took effect
unless the service confirmed it).

**4.7 Reinstall, device change and queue loss.** After a reinstall, a cleared app, a corrupted or
lost queue or a move to a new device, the client holds no keys. Three cases:

- Writes the server already committed are visible to the rebuilt client through the sync change
  feed (`T-SYN-01`); the server is the source of truth for the account (ADR-010) and the client never
  re-creates what it receives.
- A queue restored from an encrypted backup keeps its original keys, payload bytes and
  `source_event_id`s (`T-CON-15`), so replaying restored entries within the lifetime is recognised by
  key.
- Entries that were captured but never acknowledged and cannot be restored are re-derived by the
  capture layer: the SMS inbox and notification history survive a reinstall, so re-parsing produces
  the same structured transaction with a **new** key and a **new** `source_event_id`; a user who
  re-types a transaction produces the same. The key layer cannot recognise these. What prevents the
  silent double post is the **structured duplicate-detection path**: the server-computed
  `transactions.dedupe_key` over canonical structured fields — ADR-004's `amount`, `direction`,
  `occurred_at`, `account_ref` and merchant, with the exact field set and construction fixed by
  ADR-018 — plus the fuzzy candidate match on those fields within a time window,
  which yields a *deduplication outcome* naming the surviving record and the reason, a reversible
  link, and a `needs_review` clarification item when confidence is low
  (`architecture/01-domain-model.md` §2.3, `T-CON-02`, `PenniLogic/android#12`). It never deletes
  either candidate. ADR-018 (`T-ADR-CRYPTO-04`) defines the construction and key class of that
  server dedupe key and the reversible fuzzy-match semantics; ADR-015 requires that the path exists,
  that it applies to every ingestion source including manual entry, and that its outcome is shown
  rather than silently applied. It is a second, independent layer: the key layer stops replays of
  requests the client still remembers; the dedupe layer stops re-creations of facts the client has
  forgotten.

**4.8 Mapping to the client state taxonomy** (`product/client-state-taxonomy.md`). A queued or
in-flight write is the happy-path *pending marker*, not a state (§9). No connectivity with the write
queued is still the pending marker; a write that could not be queued is `offline` at action scope.
A failure while connected — `5xx`, timeout, `409` in progress — is `error` at action scope for a
foreground write, whose `retry` repeats the same key (taxonomy §3.3), and remains the pending
marker for a background queue entry that will retry itself. `400` and `422` idempotency conditions
bind to `request_failed` with the retry classification *not retryable under the same key*, and a
replayed `2xx` is success. `T-CON-12` binds the codes; this record adds no state and no taxonomy
condition.

### 5. Security and privacy consequences

- **Chosen: strings, wrappers, scoped random keys.** No precision loss anywhere, but a string can
  be concatenated or displayed raw by mistake; the wrappers, the seams and the CI guards in §7 exist
  to make that a build failure. Keys are unguessable and scoped per principal, so a leaked key alone
  neither replays nor reveals anything, and a foreign principal's key lookup is simply unknown. The
  store keeps digests, not requests; stored responses contain amounts and are therefore encrypted
  under the user's DEK (ADR-006), purged after 30 days and rendered unreadable by erasure.
  Codec and idempotency diagnostics carry field names, reason codes and correlation identifiers,
  never an amount, a balance or the offending string (`PenniLogic/api#1`). The profile time zone is
  coarse location data and stays out of logs and signals.
- **Rejected: JSON floating point** — silent corruption of financial fact, the failure ADR-001
  exists to prevent. **Rejected: raw `int64` numbers** — silent rounding of values above 2^53 − 1
  in every JavaScript client, and scale and currency invisible on the wire. **Rejected:
  content-derived keys** — collide on legitimate duplicates and reintroduce a raw-derived digest at
  the API boundary (ADR-004, ADR-018). **Rejected: server-issued keys** — an offline write would
  need a round trip before it could be queued. **Rejected: global key uniqueness or an unbounded
  lifetime** — cross-user collision and probing, or unbounded storage of response bodies.
  **Rejected: a 24-hour lifetime** — shorter than an ordinary offline period, so a delayed retry
  would double post.
- The API still has no field able to carry raw message text (ADR-004); `source_event_id` and the
  idempotency key are random identifiers, not digests, and the device-local raw-message HMAC never
  enters a request (`T-SYN-03`).

### 6. Observability

Signals that prove the decision is honoured, none carrying an amount, balance, key value or
account identifier:

- `money.wire.rejected{reason, field}` and `time.instant.rejected{reason}` — counts per §1.5 and
  §3.1 reason, expected near zero from generated clients; a rise names a non-conforming client.
- `idempotency.outcome{result=new|replayed|mismatch|in_progress|missing|malformed}` and
  `idempotency.replay_age_seconds` (histogram from first receipt to replay) — replays absorbed, and
  evidence that the 30-day lifetime and 14-day horizon are adequate; `idempotency.records_purged`.
- `dedupe.outcome{reason}` from the ingestion pipeline, distinguishing structured-key matches with
  distinct `source_event_id`s — the second layer catching what the key layer cannot.
- `time.profile_zone_missing` (must be zero) and a scheduled invariant check that no stored instant
  has sub-millisecond precision.
- Client: `client.queue.oldest_pending_age`, `client.queue.horizon_exceeded`,
  `client.queue.replayed_responses` (responses with `Idempotent-Replayed: true`), alongside the
  taxonomy's `client_state.error` and `client_state.offline` signals.
- Build-time: the floating-point guard's scanned-file count (`PenniLogic/api#1`) and the count of
  `x-idempotency` exemptions in the published specification, both trended so a silent narrowing
  shows up.

### 8. Migration note

The specification of `PenniLogic/contracts#1` changes before its first publication: every
`type: integer, format: int64` amount becomes `$ref: '#/components/schemas/Money'`; free-form
`format: date-time` fields become `Instant`; the profile gains a required `time_zone` (`TimeZone`);
`CurrencyCode`, `LocalDate`, the `IdempotencyKey` parameter and the `IdempotentReplayed` header are
added as components; every mutating operation references the parameter; `currency-registry.v1.json`
and both fixture files ship with the artifact; the idempotency and horizon durations are contract
metadata. No client has been generated from the public specification yet, so there is no
compatibility window for `int64` amounts: the first published version conforms. **All three
generated clients must be regenerated** from that version — Kotlin (server stubs in `api`, client in
`android`), TypeScript (`web`, `admin`) and Python (`ai-service`) — and any prototype code that
consumed integer amounts is replaced by the wrappers. `PenniLogic/contracts#2` implements the
codecs and fixtures, `PenniLogic/api#1` the Kotlin primitive and CI guard, `PenniLogic/api#7` the
idempotency store; `T-CON-12` binds the conditions in §4.4 and §4.8 to codes; `T-CON-15`,
`T-SYN-01`, `T-SYN-03` and `T-SYN-04` inherit the persistence, scope, lifetime and fingerprint rules
unchanged. The research SQL in `architecture/03-stack-and-monetization.md` §12 is illustrative and
its global key column and 24-hour prose are superseded here; ADR-010's "idempotency keys" are now
defined.

### 9. Rollout and rollback

Adopted on merge; contracts and implementation tickets consume it directly and must not restate
or contradict it. Additive evolution is allowed without a new record: a new registry currency, a new
reasoned `x-idempotency` exemption, a relaxation of the key pattern to admit another random UUID
version. Changing the wire form, the canonical grammar, the range, the instant form, the scope, the
lifetime or the conflict semantics requires a superseding record that states the migration cost:
every published contract version, three generated clients and their consumers, the stored
idempotency records and both fixture files.

### 10. Non-goals

Implementation, which belongs to the tickets above; ADR-017's ledger currency and FX policy;
ADR-018's dedupe key construction and encryption scope; ADR-019's authentication operations;
ADR-023's quota reset boundary; `T-CON-12`'s code vocabulary; `T-SYN-01`'s per-entity conflict
rules; which currencies the product offers (E30); the pay-cycle configuration shape (`T-CON-08`).

**Revisit if:** a runtime boundary emerges that cannot carry strings; the int64 range proves too
small for an aggregate the product genuinely computes; or measured `idempotency.replay_age_seconds`
approaches the 14-day horizon.
