## ADR-023 — Entitlement and quota model: plan versions, feature keys, request and token dimensions, usage ledger and reset boundary
**Status:** ACCEPTED · 2026-09-30

**Decision.** One entitlement model binds the quota contract, the AI gateway and billing:

1. **A plan is an immutable published version.** Its identity is the pair (`plan_code`, `plan_version`)
   with an opaque `plan_version_id`; a subscription pins exactly one `plan_version_id` and every
   entitlement check resolves against that pin and nothing else. A **feature** is a stable
   `feature_key` in a closed, published vocabulary, independent of every plan that grants it; a plan
   version grants a set of feature keys, and for each metered feature it grants quota per dimension
   and window. When no subscription resolves to an entitling pinned version the check returns
   **deny**; there is no default plan, and the Free tier is an explicitly assigned plan version.
2. **Quota has two independent dimensions.** `requests` counts admitted requests for a metered
   feature (integer, no fraction exists, measured at gateway admission, settled at first delivered
   byte). `tokens` counts provider-reported input plus output tokens of the inference the request
   made (integer, estimates rounded up, reserved at admission, measured at completion). Neither is
   derived from the other; every metered feature grant declares both, and every entitlement or
   usage payload reports both.
3. **A per-plan-version model allowlist** bounds Modes A and B. A request naming a model outside it
   is refused with the distinguishable code `model_not_in_plan` and is never executed on another
   model.
4. **Bring-your-own-key and custom-endpoint requests consume `requests` and not `tokens`.** Their
   tokens are recorded uncharged. Entitlement, the allowlist, rate limits, safety filtering, audit,
   egress controls and the kill switch apply to them unchanged, and a Mode B or Mode C request is
   never re-executed as Mode A.
5. **Usage is event-sourced.** An append-only `usage_events` ledger with one terminal event per
   reservation is the only source of truth; the `usage_counters` projection that admission reads is
   written in the same transaction, verified against the ledger hourly and at period close, and
   rebuilt from the ledger whenever it diverges.
6. **The reset boundary is the calendar unit in the user's IANA profile zone**, computed by the
   ADR-015 §3.3 period rule from the zone in effect when the period opens; a zone change takes
   effect at the next period. A reservation open when the boundary passes settles against the
   period in which it was admitted.
7. This record **supersedes both** entitlement sketches — `architecture/01-domain-model.md` §5 and
   `architecture/03-stack-and-monetization.md` §8 — as design authority (§1), and both sections
   carry an in-place redirect to this record.

**Why.** The two sketches disagree about what a plan identifies (a mutable `plans` row with a `code`
versus a mutable row with prices), what a quota counts (`max_requests` and `max_tokens` on the plan
versus one `quota_value` per feature) and where usage lives (`ai_usage_events` versus a
`user_entitlements.quota_used` counter reset by a cron job). Billing (`T-BIL-01`, `T-BIL-02`), the
gateway (`T-AI-01`) and the quota contract (`T-CON-03`) all read them, so the disagreement would ship
as three incompatible implementations. The product's margin depends on server-side quota enforcement
(ADR-007; `product/01-product-spec.md` §4.2), and enforcement needs one schema. Each choice below is
the one whose failure mode is visible: an immutable version cannot re-entitle a subscriber silently
(`T-BIL-10`); a ledger cannot drift without the projection check saying so; a refused model cannot
be quietly swapped for a cheaper one; a missing grant denies instead of granting everything; and a
period pinned at admission cannot be double-counted when the month turns.

**Ticket.** `T-ADR-ENT-09`, PenniLogic/docs#47, parent epic E26 (PenniLogic/docs#29). It builds on
ADR-007 (entitlements owned in-house, enforced server-side), ADR-001 and ADR-015 (money form for plan
prices and the instant, time-zone and idempotency conventions used here), ADR-009 and ADR-014 (the
`api` core owns entitlements; the `ai-service` gateway consumes them), ADR-020 §5 item 7 (plan and
quota administration is an audited `admin_api` effect) and the runtime-independent decisions of
ADR-022 §2 (gateway-only egress, Modes A, B and C, the kill switch). Nothing here depends on the
runtime choice ADR-022 leaves to the owner. Pricing levels and packaging are confirmed product
decisions (`product/01-product-spec.md` §4.1, §4.3) and are referenced, not decided. Consumers are
listed in §16.

### 2. Plan and feature identity

#### 2.1 Plan version

A plan is a **published, immutable version record**:

| Field | Meaning |
|---|---|
| `plan_code` | Stable lowercase identifier of the commercial plan family (grammar `^[a-z][a-z0-9_]*$`, ≤ 32 characters), for example the codes product assigns to the Free, Pro, Pro+ and BYOK Pro tiers. Never carries a price or a version |
| `plan_version` | Integer ≥ 1, strictly increasing within a `plan_code` |
| `plan_version_id` | UUIDv4 surrogate; the value a subscription pins and every ledger event records |
| `state` | `draft` (editable by operators through `T-ADM-07`), `published` (immutable), `retired` (immutable; no new sales, existing pins continue — `T-BIL-10`) |
| `effective_from`, `retired_at` | ADR-015 instants assigned by the application |
| `prices` | Zero or more (`billing_period`, `Money`) pairs in the ADR-015 object form; values are product's (`product/01-product-spec.md` §4.1) |
| `features` | The set of granted `feature_key`s (§2.2) |
| `quotas` | Quota grants for metered features (§2.3) |
| `model_allowlist` | Catalogue `model_id`s Modes A and B may name (§5) |
| `rate_limits` | Short-window admission limits per feature (§2.3) |
| `capacities` | Capacity grants (§2.3) |

Once `published`, no field changes; a change of price, grant, quota, allowlist or rate limit is a
**new version** (`T-BIL-10`, PenniLogic/api#60, owns version creation, migration with notice and
grandfathering; `T-BIL-01`, PenniLogic/api#29, writes versions immutably from the first migration).
Retirement changes `state` and `retired_at` only. Publication, retirement and every draft edit are
administrative effects recorded with before and after values in the ADR-020 audit streams
(§5 item 7 there), performed only through `admin_api` functions by the `T-ADM-07`
(PenniLogic/admin#4) surface.

#### 2.2 Feature keys

A feature is identified by a `feature_key`: lowercase dotted segments, grammar
`^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`, ≤ 64 characters, the first segment naming the capability
area. Keys live in **one closed vocabulary**, `entitlement-vocabulary.v1.json`, published by
`T-CON-03` (PenniLogic/contracts#7) and consumed unchanged by the core API, the gateway, billing and
the admin console; a plan version, a request or an admin form naming a key outside it is refused
(`T-ADM-07`: "an entitlement key not present in the published vocabulary cannot be assigned"). Each
vocabulary entry declares the key, a description and its **kind**:

- `boolean` — granted or not; nothing else to configure.
- `metered` — granted with quota grants for **both** dimensions (§3.3); every AI feature that makes
  an inference call is metered.
- `capacity` — granted with an integer cap on how many of a resource may exist.

The initial vocabulary, normative until the artifact exists, is grounded in the confirmed tier table
and access modes (`product/01-product-spec.md` §3.7, §4.1, §4.3): `ai.qna` (metered — conversational
Q&A), `ai.summary` (metered — weekly and monthly review generation), `ai.managed_inference` (boolean
— Mode A, PenniLogic's provider credentials), `ai.byok` (boolean — Mode B, the user's provider key),
`ai.custom_endpoint` (boolean — Mode C, the user's registered destination), `sharing.household`
(boolean — family sharing, Pro-only under product spec §4.3 guard 1) and `support.priority` (boolean). Further AI
features (categorisation, planning, natural-language entry) and any gated non-AI capability receive
keys under the same grammar when their tickets publish them; adding a key is an additive vocabulary
change and needs no new record. No capacity key is seeded: product principle "never paywall the
safety net" (`product/01-product-spec.md` §4) means capacity caps exist only where product later decides.

A feature key is **not** a model, a mode, a plan or a window; those are separate vocabularies (§3.4,
§5, §6). A key is never derived from a plan code and a plan code never appears in a key.

#### 2.3 What a grant says

- **Feature grant.** Membership of `feature_key` in the version's `features`. A request for a
  feature the pin does not grant is refused with `entitlement_denied` (reason
  `feature_not_in_plan`), whatever the client says.
- **Quota grant** — one per (`feature_key`, `dimension`, `window`) for a metered feature:
  `{feature_key, dimension, window, limit}` with `dimension ∈ {requests, tokens}` (§3),
  `window ∈ {calendar_day, calendar_month, subscription_lifetime}` (§3.4) and `limit` a
  non-negative integer (§3.5). A metered feature grant carries **both** dimensions for every window it
  uses; a version that grants one without the other fails validation (§3.3). A version may grant the
  same dimension in more than one window (a daily cap inside a monthly allowance); admission checks
  every granted window and the first exhausted one is the refusal (§4).
- **Mode grant.** Modes are ordinary boolean features (`ai.managed_inference`, `ai.byok`,
  `ai.custom_endpoint`). A request in a mode the pin does not grant is `entitlement_denied` (reason
  `mode_not_in_plan`).
- **Rate limit** — `{feature_key, max_admissions, window_seconds}`: a short-window admission
  throttle inside the allowance (`architecture/03-stack-and-monetization.md` §9 item 2; `T-BIL-02`
  "short-window rate limiting independent of the periodic allowance"). It is **not** a quota
  dimension: it counts admissions rather than settled consumption, it is not ledgered, its state may
  live in a volatile store, and it applies to every mode. Exceeding it is `rate_limited` with the
  limit, its window and the lift time (§9). If the limiter's store is unavailable the admission is
  refused with `dependency_unavailable` (fail closed); quota exactness is unaffected because quota
  never lives in that store.
- **Capacity grant** — `{feature_key, capacity}` for a `capacity` feature: creating an item beyond
  `capacity` is refused with `capacity_exceeded`; items that already exist stay readable and
  exportable.
- **Read-only degradation.** When a pin changes to a version that lacks a feature, lowers a capacity
  or lowers a quota, everything the user produced remains readable, searchable and exportable; the
  feature's write operations are refused with `entitlement_denied`, creation beyond a capacity with
  `capacity_exceeded`, and **nothing is deleted or hidden** (`T-CON-03`: "a downgrade makes excess
  data read only and never deletes it"; `product/01-product-spec.md` §4A.3). Usage already consumed
  in the current period stays consumed: the period belongs to the person and the calendar, the
  limit belongs to the pin at admission (§8.4).

#### 2.4 Resolution: the pin, and deny when nothing resolves

1. Resolution runs on the server for every request that touches a gated feature or a metered
   action, from the authenticated principal alone. It reads the principal's **current
   subscription** — by invariant at most one row is current at any instant, whatever billing channel created it —
   and takes its pinned `plan_version_id` if the subscription's lifecycle state is declared
   *entitling*. The contract (`T-CON-03`) enumerates the states `active`, `grace`, `dunning`,
   `expired` and `downgraded` with an explicit `entitles` flag per state; `active` and `grace`
   entitle, `expired` does not, `dunning` entitles only for the bounded duration the lifecycle
   contract publishes, and `downgraded` is the state of a superseded row whose successor row carries
   the new pin. A state without the flag fails contract validation.
2. **No plan resolves → deny.** No subscription row, a row in a non-entitling state, a pin to a
   version that does not exist, or two current entitling rows (an invariant violation that is
   alerted and resolved by `T-BIL-08`, PenniLogic/api#52, whose precedence rule selects the single
   pin) all return `entitlement_denied` with reason `no_plan` or `subscription_not_entitling`. The
   resolver never substitutes a default, never falls back to the Free version and never unions the
   grants of two versions. The Free tier is a real plan version assigned by an **explicit**
   subscription row written in the same transaction as the account at signup and again on downgrade
   (`T-BIL-01`, `T-BIL-10`); a user who has no
   row — a half-completed signup, an erased account, a billing pipeline fault — has nothing, and
   `entitlement.no_plan_total` (§12) measures how often that happens.
3. The pinned version wins over any newer version of the same `plan_code` until an explicit
   migration (`T-BIL-10`: "a new version's entitlements never reach an unmigrated subscriber").
4. The **resolved entitlement** — pin, features, quota grants, allowlist, rate limits, capacities —
   may be cached by the core API and mirrored into the gateway's per-user virtual key (`T-AI-01`,
   PenniLogic/ai-service#2) for at most `entitlement_cache_ttl_seconds = 60`, with explicit
   invalidation on every subscription or version event, so a plan change reaches the gateway within
   the published time. **Counters are never cached**: headroom is read transactionally at
   admission (§4). The virtual key and any in-process LiteLLM budget object (ADR-022 §2.1) mirror the
   entitlement; they never decide it and never hold the count.
5. Sharing does not share quota. A household member's AI request over data shared with them consumes
   the **requester's** allowance under the requester's pin, never the sharer's (ADR-005; ADR-022 §2.1
   bounds what such a request may send).
6. Operators have no quota. The administrative surface reads and adjusts entitlement only through
   `admin_api` functions (ADR-020 §4.1, §5 item 7); it never resolves entitlement on a customer's
   behalf and never sees an individual's usage outside the masked, audited path (`T-ADM-07`: "no
   screen here exposes an individual user's usage").

### 3. The two quota dimensions

#### 3.1 `requests`

| Property | Value |
|---|---|
| Unit | One admitted request for one metered feature. A request that internally makes several provider calls (a tool loop) or streams is still one request; a batch operation that fans out is one request per item the contract admits separately |
| Type and rounding | Integer count. No fraction can arise, so no rounding rule is needed; the contract types it as a non-negative integer |
| Measurement point | **Admission**: the instant the gateway's admission check passes fixes the period the request belongs to (§8.4) and counts it for the rate limit. One unit is **reserved** at that instant |
| Settlement | **Committed** when the first byte of the result is delivered to the client (for a non-streaming feature, when the result is returned; a delivered refusal answer counts). **Released** when nothing was delivered: a control that returns no answer (kill switch, egress denial, an internal failure), a provider or destination failure before the first byte, or reservation expiry (§4.3) |
| Consumed in | Every mode (§6) |

The first-delivered-byte rule is the line between "the user received a response" and "the user
received nothing": it keeps the sketches' promise never to charge for an undelivered response, and it
makes a failing own endpoint unable to obtain answers for free, because anything delivered is
counted. Repeated admissions that release are visible as `quota.reservation_total{outcome=released,
reason}` per mode and feed the abuse rules of §6.

#### 3.2 `tokens`

| Property | Value |
|---|---|
| Unit | One provider-reported token. The count is the sum of every token quantity the provider's usage report gives for the call — input (including any cached prompt portion the provider reports as input) and output (including reasoning tokens the provider reports as output) — mapped by the model catalogue entry's usage-field mapping (§5) so a provider that reports both a subtotal and its parts is not double counted. A request that makes several provider calls sums them all |
| Type and rounding | Integer. Provider counts are used verbatim. Any estimate — the admission reservation, or a catalogue-declared conversion for a provider whose usage report is not already in tokens — is rounded **up** to the next integer; nothing is ever rounded down. A catalogue entry that declares no token usage report and no conversion is not enabled for Mode A |
| Measurement point | **Completion**: the committed value is the provider-reported total available when the last provider response of the request has been read. A **reservation** is taken at admission (§4.2) |
| Settlement | Committed to the provider-reported total on completion; released when the response was not delivered or the provider produced no usage report (§4.3) |
| Consumed in | Mode A only; recorded uncharged in Modes B and C (§6) |

Internal model calls the gateway makes on PenniLogic's own credentials as controls — the
prompt-injection screening sidecar, redaction helpers (`T-AI-05`) — are **not** the user's inference:
their tokens are neither reserved against nor committed to the user's allowance and their cost
accounting belongs to `T-AI-06` (PenniLogic/ai-service#7). Only the provider calls that produce the
user's answer count.

#### 3.3 Independence

`requests` bounds PenniLogic's per-call orchestration cost and the abuse surface of many small calls;
`tokens` bounds inference cost and the abuse surface of few enormous calls. A cap on either alone is
gamed through the other. Therefore:

- neither dimension is ever computed from the other — no average tokens per request, no
  requests-equivalent of a token count — and a contract, gateway or billing component that derives
  one from the other fails review;
- every quota grant for a metered feature declares **both** dimensions for each window it uses
  (§2.3), and every entitlement, usage and refusal payload reports **both** (§10); an endpoint that
  reports only one fails contract verification (`T-CON-03`);
- admission requires headroom in **every** enforced dimension of every granted window (§4.1), and
  `quota_exhausted` names the first dimension that lacked it.

Where a plan version's `tokens` limit is inert because the version grants no Mode A
(`ai.managed_inference` absent — the BYOK Pro tier), product sets it to `0`; the grant still exists
so that the payload shape and the validation rule are uniform and a later Mode A grant starts from a
stated ceiling rather than an absent one.

#### 3.4 Windows

| `window` | Period | Zone |
|---|---|---|
| `calendar_day` | One local calendar day, `[00:00:00.000 local, next 00:00:00.000 local)` | The period's quota zone (§8.2) |
| `calendar_month` | One local calendar month, `[day 1 00:00 local, day 1 of the next month 00:00 local)` | The period's quota zone (§8.2) |
| `subscription_lifetime` | From the instant the current pin took effect until it is unpinned (migration, expiry, downgrade) | None |

These are the "daily, monthly and total windows the entitlement record defines" that `T-ADM-07`
configures. Adding a window is an additive vocabulary change; changing the boundary rule of an
existing window is not (§14).

#### 3.5 Zero, absent and finite

- **Absent** grant (feature or dimension not in the pin) → `entitlement_denied`.
- **`limit = 0`** → granted and permanently exhausted for that window: `quota_exhausted` with
  `limit 0, used 0, remaining 0`. This is how a version deliberately switches a metered feature off
  while keeping it visible (`T-ADM-07`: "a quota set to zero is distinguishable from a quota that is
  unset").
- **`limit = N > 0`** → bounded.
- **There is no unlimited sentinel.** `null`, `-1` and "unlimited" are rejected by the vocabulary
  lint. A tier marketed as "unlimited" carries the finite ceiling product chooses — the confirmed
  tier table already gives Pro+ and BYOK Pro soft caps (`product/01-product-spec.md` §4.1, §4.3
  guard 4) — because a missing row that grants everything is the failure ADR-007 exists to prevent.
- A grant's `limit` for `tokens` must be at least the feature's largest possible reservation (§4.2)
  unless it is `0`; otherwise the feature is unusable by construction and the version fails
  validation.

### 4. Admission, reservation and settlement

#### 4.1 Fixed check order

Checks run in this order and the **first failure is the refusal**, so every refused request has
exactly one code (§9) in every implementation:

1. Request schema (strict, `additionalProperties: false`): an unknown member, or any member of the
   forbidden set in §11, is `validation_rejected` (`T-CON-12`, ADR-015 §1.5).
2. Principal (ADR-019) — outside this record.
3. Subscription resolution (§2.4) → `entitlement_denied{no_plan | subscription_not_entitling}`.
4. Feature grant → `entitlement_denied{feature_not_in_plan}`.
5. Mode grant → `entitlement_denied{mode_not_in_plan}`; then the mode's credential or destination
   state (`T-AI-01` key states; ADR-022 §2.8 destination states) with their own codes. A request
   that names no mode runs in the only mode the pin grants; when the pin grants more than one, the
   mode is required and its absence is `validation_rejected` — never an implicit choice. The mode is
   **fixed** here for the life of the request.
6. Model (§5) → `model_not_in_plan`; for a `capacity` feature, the cap → `capacity_exceeded`.
7. Rate limit (§2.3) → `rate_limited`.
8. Quota headroom (§4.2), dimensions in vocabulary order `requests`, `tokens`, windows in order
   `calendar_day`, `calendar_month`, `subscription_lifetime` → `quota_exhausted` naming the first
   exhausted (`feature_key`, `dimension`, `window`).
9. Reservation (§4.2) in one transaction.

Only after step 9 does the gateway proceed to the kill switch and egress (ADR-022), safety filtering
(`T-AI-05`) and the provider call. A refusal by any of those releases the reservation (§4.3).

#### 4.2 Reservation

For each consumed dimension and each granted window the reservation is:

- `requests`: `1`.
- `tokens` (Mode A only): `R = input_upper_bound + max_output_tokens × max_provider_calls`, where
  `input_upper_bound` is the deterministic upper-bound estimator `T-AI-01` publishes together with
  its measured over-estimate ratio, `max_output_tokens` is the hard output ceiling the gateway sets
  on every provider call (mandatory in Mode A), and `max_provider_calls` is the feature's published
  tool-loop bound (`T-AI-04`). Every term is an integer; the estimate rounds up (§3.2).

Admission requires, for every enforced (`dimension`, `window`):
`committed_total + reserved_outstanding + R ≤ limit + adjustment_total` on that period's counter row
(§7.3). A reservation that does not fit is `quota_exhausted` carrying `remaining =
max(0, limit + adjustment_total − committed_total − reserved_outstanding)` and `required = R`, so
"remaining" is honest even when it is smaller than one request's need. The reservation transaction
opens the period if needed (§8.3), locks the counter rows in vocabulary order (so concurrent
admissions cannot deadlock), re-checks headroom under the lock, appends
one `reserved` event per (dimension, window) with a shared `reservation_id`, and updates the
projection — all or nothing. Two concurrent requests cannot both take the last unit (`T-BIL-02` race
test).

Every reservation carries `expires_at = reserved_at + reservation_ttl_seconds` with the initial
value `900`. It must cover ADR-022's 120-second total egress timeout multiplied by the tool-loop
bound plus the drain in §4.3, so `T-AI-04`'s published bound keeps `max_provider_calls × 120 s` plus
the drain inside it, or `T-BIL-02` raises the value additively. The value is published in the
parameters block (§10).

#### 4.3 Settlement outcomes

Exactly **one terminal event** — `committed` or `released` — follows each `reserved` event (§7.2).

| Outcome | `requests` | `tokens` (Mode A) | `tokens` (Modes B, C) |
|---|---|---|---|
| Completed | commit `1` | commit the provider-reported total (§3.2) | record the provider-reported total with `charged = false`; `null` when the provider reports none |
| Refused after admission by a control that returns **no answer** (kill switch, egress denial, an internal failure) or provider/destination failure **before any byte** was delivered | release | release | nothing recorded beyond the release |
| Partial delivery, then provider failure with **no usage report** | commit `1` | release (fail open: the tokens the user received are not charged because they cannot be counted honestly; the request is) | record `null` |
| Client disconnects after the first byte | commit `1` | the gateway **drains** the provider response to obtain the usage report and commits it; if the provider fails during the drain, as the row above | record as available |
| Reservation not settled by `expires_at` | released by the expiry sweep with reason `expired` | released, reason `expired` | — |
| Settlement arrives after the terminal event | recorded as `late_settlement` with `charged = false`; the terminal event is not altered and no second terminal event is written | same | — |

Draining is what closes the obvious abuse — disconnecting just before the usage chunk to obtain
uncharged tokens. A safety or advice-boundary refusal that is **delivered** to the user as an answer
is a completed request (`product/client-state-taxonomy.md` §9: a refusal is a successful response
whose content is a refusal) and is committed; only a control that returns no answer releases, so
probing the safety layer is not free and the rate limit bounds the attempts. A commit may exceed its reservation only by estimator error; it is still recorded
in full, the period may therefore end slightly above its limit (a **soft overrun**, bounded by the
estimator and measured by `quota.settlement_overrun_tokens`), and the next admission is refused. The
gateway never truncates a stream to stay inside the limit and never re-executes a request in another
mode or on another model to make it fit.

#### 4.4 Idempotency

`reserve`, `commit` and `release` are state-changing operations of the core API under the contract
and therefore carry the ADR-015 §4 `Idempotency-Key` from the gateway (a UUIDv4 per intended effect,
persisted before first send, replayed unchanged). The key layer absorbs retries of the same call; the
one-terminal-event rule (§7.2) is the independent domain guard against logic errors: a second commit
or release for a reservation that already has a terminal event is answered `reservation_not_open`;
the settlement facts a late commit carried are appended once as a `late_settlement` event (unique per
reservation) so they are not lost, and no idempotency record is stored for the refused operation
(ADR-015 §4.4 item 6), so a retry is evaluated afresh and finds the same answer. `reservation_id`, `period_id`
and `event_id` are server-assigned UUIDv4s; none is derived from content.

### 5. Model allowlist and the unlisted-model refusal

- **Model identity.** A `model_id` is a string of the form `<provider_id>/<model_name>` drawn from
  the **model catalogue**, `model-catalogue.v1.json`, a versioned machine-readable artifact owned by
  `T-AI-07` (PenniLogic/ai-service#8) whose `provider_id`s are entries of the ADR-022
  `egress-policy.json` provider allowlist. Each entry carries `model_id`, `provider_id`, `enabled`,
  `reports_token_usage` and its usage-field mapping (§3.2). The admin console enables or disables
  catalogue entries and sets routing order and spend caps (`T-ADM-08`, PenniLogic/admin#5); it cannot
  add one.
- **Allowlist.** A plan version's `model_allowlist` is a subset of the catalogue; a version naming a
  model outside the catalogue fails validation. The allowlist governs Modes A and B. Mode C has no
  catalogue: the plan's `ai.custom_endpoint` grant and ADR-022's destination controls govern it, and
  the request's model string is forwarded unchanged to the registered destination and recorded
  verbatim as `model_requested`, with no allowlist check. Because that string is user-supplied
  content that will live in the ledger, it must match `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,127}$` and
  must not match the platform's published credential-pattern list (the list the repository secret
  scan and `T-AI-01`'s planted-key test use); otherwise the request is `validation_rejected` before
  admission, so a pasted key cannot enter a usage event through this field.
- **Refusal.** A Mode A or Mode B request that names a model outside the pin's allowlist is refused
  with **`model_not_in_plan`** before any reservation and before any provider call. Whether the name
  exists in the catalogue is irrelevant and undisclosed: unknown and known-but-unlisted receive the
  same code. The gateway **never** substitutes another model, never lowers to a cheaper listed model
  and never retries the request elsewhere; `quota.model_substitution_total` (§12) exists to stay at
  zero.
- **Named versus routed.** A request that names a listed model is executed on exactly that model;
  if that model is unavailable the result is `dependency_unavailable`, not a substitute. A request
  that names **no** model is routed by `T-AI-07`'s policy within the pin's allowlist, and failover
  within that allowlist is permitted; the usage event records `model_requested` (`null`) and
  `model_used`, so a routing choice is visible in the ledger and never silent.
- **Disabling.** A catalogue entry disabled by an operator remains in plan allowlists that name it;
  a request naming it is `dependency_unavailable` (the plan includes it, the platform cannot serve
  it), and a routed request skips it. The distinction keeps `model_not_in_plan` truthful.

### 6. Bring-your-own-key and custom-endpoint treatment

The mode is a property of **whose credential paid for the inference**, fixed at admission (§4.1
step 5):

| | Mode A `managed` | Mode B `byok` | Mode C `custom` |
|---|---|---|---|
| Credential | PenniLogic's provider key | The user's key, envelope-encrypted by `T-AI-01` | The user's registered destination and optional key (ADR-022 §2.8) |
| `requests` | consumed | **consumed** | **consumed** |
| `tokens` | consumed | **recorded, not consumed** (`charged = false`, no reservation, no allowance) | **recorded, not consumed** |
| Model allowlist | applies | applies | not applicable (§5) |

`requests` is consumed in every mode because every admitted request costs PenniLogic the same
orchestration: entitlement resolution, the reservation, the safety and injection screening that
runs on PenniLogic's credentials, tool execution, audit rows and egress. That is the "soft-cap
orchestration" guard of `product/01-product-spec.md` §4.3 guard 4 and the "server-side soft cap" in
`T-BIL-01`'s scope; the BYOK Pro version's `requests` limit is that cap. `tokens` is not consumed
because the user pays their provider per token and charging a PenniLogic allowance as well would be
the double charge the domain sketch called indefensible. The tokens are still **recorded** — for
abuse detection, for the user's own usage view and for product analytics — as a usage event with
`charged = false` and no reservation.

Everything that is not an allowance still applies, unchanged, to Modes B and C: the feature and mode
grants of the pin (a BYOK Pro version that lacks `sharing.household` cannot reach it — product spec
§4.3 guard 1);
the model allowlist for Mode B; the plan's rate limits; the strict request schema; ADR-022's
gateway-only egress, destination validation, pinning, redirect and transport rules, the class-aware
proxy and the kill switch scopes; `T-AI-05` redaction and prompt-injection defences, including the
other-principals exclusion of ADR-022 §2.1; the ADR-022 §2.8 audit rows; the key and destination
lifecycle (`T-AI-01`: step-up on add or replace, suspension on account recovery, no plaintext
recovery); consent recording for user-directed transfer (ADR-022 §6, `T-CON-09`); and this record's
ledger. Two rules are specific to these modes:

- **No fallback to Mode A.** A Mode B request whose key is missing, invalid, suspended or for another
  provider, and a Mode C request whose destination is not `active`, are refused with the `T-AI-01` or
  ADR-022 §5 code for that state and are **never** re-executed on PenniLogic's credentials (product
  spec §4.3 guard 3: "a BYOK user with an empty key is rejected by the server, never the client"). The guard
  metric `quota.mode_fallback_attempt_total` must read zero.
- **Failing own endpoints.** Admissions that release because a Mode B provider or Mode C destination
  delivered nothing still cost PenniLogic the orchestration; they are bounded by the plan's rate
  limit (which counts admissions) and reported per mode as
  `quota.reservation_total{outcome=released, reason, mode}`. `T-AI-01` treats a key that returns
  `401` as invalid (the 7-day grace and downgrade of product spec §4.3 guard 2), and `T-AI-03` may suspend a
  custom destination whose release rate exceeds the threshold it publishes, under ADR-022 §2.8
  step 7.

**Keys never enter the ledger.** A usage event, a counter, a period, a refusal body, a signal or a
trace carries no key material, no key identifier, digest or fingerprint, no provider account
identifier and no destination host name — only `mode`, the opaque catalogue `provider_id` (Mode B) or
the opaque ADR-022 `destination_id` (Mode C). `ByokKeyLeakLedgerTest` (§13) plants a key and scans
every one of those surfaces.

### 7. Usage accounting: an event-sourced ledger with a derived counter

#### 7.1 Why event-sourced

The choice is the sketch-03 materialized counter (`quota_used` incremented in place and zeroed by a
cron job) against an append-only event ledger from which any counter is derived. The ledger is
chosen because every hard requirement of the dependants needs history, not a number: `T-BIL-02`
requires that "usage is reconstructible by replaying the event store" and that no in-place counter
is the source of truth; `T-BIL-07` (PenniLogic/api#51) must unwind quota on refund, chargeback and
credit note, which a bare counter cannot do without knowing what was consumed when; `T-ADM-07` and
ADR-020 §5 item 7 record a quota override as a reference to the record it created, which must
therefore exist; the boundary and open-reservation rules of §8 need each unit of consumption to carry
the period it belongs to; and an in-place counter reset by `UPDATE … WHERE quota_reset_at <= now()`
has no defence against a double run, a missed run or a race with a commit — the reset-idempotency test
`T-BIL-02` demands is unsatisfiable without history. The cost of the ledger — one row per reservation
and one per settlement — is a few thousand rows per user per month at the confirmed tiers, and
admission never scans them (§7.3).

#### 7.2 The `usage_events` ledger

Append-only. The only writer is one `SECURITY DEFINER` function in the core API's schema that inserts
the event and updates the projection in the same statement sequence; no runtime role holds `UPDATE`
or `DELETE` on the table, and the retention and erasure jobs (`T-CMP-01`, PenniLogic/api#24; ADR-021)
act on it only through their own reviewed path. Each event carries:

| Field | Content |
|---|---|
| `event_id` | Server-assigned UUIDv4 |
| `seq` | Monotonic insertion order for replay |
| `event_type` | `reserved`, `committed`, `released`, `adjusted`, `late_settlement` |
| `occurred_at` | ADR-015 instant assigned by the application |
| `user_id`, `plan_version_id`, `period_id`, `window` | The principal, the pin at admission and the period the unit belongs to (§8.4) |
| `feature_key`, `dimension` | From the vocabularies (§2.2, §3) |
| `amount` | Non-negative integer for `reserved`, `committed`, `released`, `late_settlement`; signed integer for `adjusted` |
| `reservation_id` | Shared by the `reserved` event and its terminal event; `null` for `adjusted` |
| `charged` | `false` for uncharged records (Mode B and C tokens, `late_settlement`), `true` otherwise |
| `mode`, `provider_id`, `destination_id` | The mode and the opaque provider or destination reference; never a host or a key |
| `model_requested`, `model_used` | Catalogue ids, or the verbatim Mode C model string; `null` when not named or not applicable |
| `reason` | For `released`: `refused_downstream`, `provider_failed`, `destination_failed`, `client_abort_before_first_byte`, `expired`; for `adjusted`: `admin_override`, `purchase`, `reversal` |
| `source_ref` | For `adjusted`: the ADR-020 `audit_event_id` of the administrative effect, the billing record of the purchase or refund, or the `event_id` a reversal corrects |
| `correlation_id` | The request's correlation identifier (`T-CON-12`) |

Invariants: exactly one terminal event (`committed` or `released`) and at most one `late_settlement`
per `reservation_id`, enforced by unique constraints, never by application code alone; a `committed` or `released` event references
an existing `reserved` event of the same (`user_id`, `period_id`, `feature_key`, `dimension`); an
`adjusted` event is written only by the `admin_api` override function (ADR-020 §5 item 7) or by the
billing purchase and unwind paths (`T-BIL-07` for unwind; the billing purchase-verification path for a
top-up), never by the gateway, and always carries
a `source_ref`; an erroneous event is corrected by an `adjusted` event with reason `reversal` that
names it — never by deleting or editing it (ADR-002's posture applied to usage). Excluded by
construction: key material or any key identifier, prompt or response content, host names, monetary
amounts, device or session identifiers and the profile time zone. An event is personal data
(a usage pattern); its protection follows ADR-018, its erasure ADR-021 and ADR-006, and its
retention the `T-CMP-01` profile, which retains closed-period aggregates pseudonymised for billing
evidence.

#### 7.3 The `usage_counters` projection

One row per (`user_id`, `period_id`, `feature_key`, `dimension`) holding `committed_total`,
`reserved_outstanding`, `adjustment_total`, `last_seq` and `frozen`. The ledger function updates it
in the **same transaction** as the event it projects: `reserved` adds to `reserved_outstanding`;
`committed` moves the reservation out of `reserved_outstanding` and adds the committed amount to
`committed_total`; `released` removes the reservation; `adjusted` adds to `adjustment_total`;
`late_settlement` touches nothing. Admission reads and locks this row (§4.2) and never sums events.
The row is a **derived view with no authority**: any disagreement with the ledger is a defect in the
row.

#### 7.4 Reconciliation, divergence and replay

- **Incremental verification** every `reconciliation_interval_seconds = 3600`: for every counter row
  of an open period, replay the events with `seq > last_seq` and compare; then, on a rolling sample
  that covers every user at least once per period, replay the whole period from `seq = 0`.
- **Full replay at period close**: after `period_end` plus the reservation TTL has passed, replay
  every event of the period, compare, and set `frozen = true`; billing (`T-BIL-02`, `T-BIL-07`,
  `T-BIL-09`) reads only frozen rows for closed periods. The close job is idempotent: a second run
  finds the row frozen and re-verifies without writing.
- **Divergence signal**: any mismatch increments `quota.reconciliation.divergence_total{dimension,
  window}` (expected value zero; any non-zero pages), writes a `reconciliation_findings` row (not a
  usage event) naming the counter row, the expected and actual values and the `seq` range, and
  **rebuilds the counter from the ledger** — the ledger wins, always. A divergence is a defect
  investigation, never a manual correction of the row.
- **Replay** is also the recovery path: a lost or corrupted projection is rebuilt from the ledger
  with no loss; a projection bug is fixed by re-projecting, and a ledger bug by `reversal`
  adjustments. `LedgerReplayReconciliationTest` (§13) proves replay equality on random event
  sequences and detection of an injected corruption within one interval.

### 8. Reset boundary, time zone and open reservations

#### 8.1 Calendar, not rolling

The allowance of a `calendar_month` or `calendar_day` window resets at the boundary of the local
calendar unit in the user's IANA profile zone (ADR-015 §3.2), computed by the ADR-015 §3.3 rule: a
period is the half-open interval `[start, end)` of UTC instants where `start` is the first valid
instant of the local day the unit begins on (a local midnight inside a DST gap shifts later by the
gap; one inside an overlap resolves to the earlier offset) and `end` is the `start` of the next
unit. A rolling window is rejected: its "reset time" is per event and cannot be stated to the user
in one sentence, headroom requires scanning the window, and the taxonomy requires a single
service-stated reset (`product/client-state-taxonomy.md` §3.7, whose worked example reads "Resets
1 October"). The calendar unit is also independent of the billing cycle, so a Free user and a
subscriber who paid on the 25th are governed by the same rule; the cost is that a subscriber's first
partial month carries a full allowance, bounded to one period per new subscription. ADR-015 §3.3
names this record as the owner of the quota boundary; the rule below is that decision.

#### 8.2 The period's zone is fixed when it opens

A quota period records the zone it was computed in. **The profile zone in effect when the period
opens is the period's zone for its whole life**; a later profile-zone change affects the *next*
period of each window, never an open one. This departs deliberately from ADR-015 §3.3's read-time
derivation for reports, because consumption is an *effect*, not a report: a boundary that moved with
the current zone would let a user exhaust September, switch to a zone far enough east that
"October" has already begun there, spend a fresh allowance, switch back so those events fall in September again,
and spend October a second time. With the zone pinned per period no such movement exists.

When the next period opens under a **changed** zone, its `start` is the previous period's `end`
(no instant belongs to two periods and none to none), and its `end` is the **first calendar-unit
boundary in the new zone that lies at least half a unit after `start`** (half a unit: twelve hours
for `calendar_day`, fifteen days for `calendar_month`). With an unchanged zone that boundary is the
next ordinary one and the period is an exact calendar unit. A westward change, whose next boundary
comes within hours, therefore merges the sliver into a single period no shorter than half a unit and
grants one allowance for it; an eastward change yields one period between half and one unit long.
Neither direction ever yields two allowances for what is one calendar unit in either zone, and a
period is never shorter than half a unit. The entitlement payload states each period's `start`, `end` and `time_zone`, so
the client shows exactly what the server enforces and computes nothing (`T-CON-03`: "a client renders
the same boundary the server enforces").

#### 8.3 Opening and closing periods

There is no reset job. A period row (`period_id`, `user_id`, `window`, `start`, `end`,
`time_zone`, `opened_at`, `frozen`) is opened **lazily** by the first admission whose instant lies
past the previous period's `end` (for a user's first period of a window, `start` is the ordinary
boundary containing the admission instant), inside the reservation transaction, with a uniqueness constraint
on (`user_id`, `window`, `start`) so that two concurrent first admissions and any double run yield
one row (`T-BIL-02`: "the reset job is idempotent under a double run"). A new period has no events
and therefore `used = 0` by construction; nothing is zeroed. The close job of §7.4 freezes the
period after `end + reservation_ttl_seconds`. `subscription_lifetime` periods open when a pin takes
effect and close when it ends; they carry no zone.

#### 8.4 A reservation open when the boundary passes

The `period_id` of a reservation is fixed at **admission** and every event of that reservation —
commit, release, late settlement — carries it. A request admitted at 23:59:59 on the last day of the
month and committed thirty seconds later is charged to the month that admitted it: the old period
may close slightly above its limit (the soft overrun of §4.3, bounded by the outstanding
reservations at the boundary), the new period starts at zero, and no unit is counted twice or
refused twice. Admission in the new period ignores the old period's outstanding reservations
because they are not on its counter rows. The close job waits `reservation_ttl_seconds` after `end`
precisely so that every reservation admitted before the boundary has settled or expired before the
period is frozen. `ResetBoundaryOpenReservationTest` (§13) is the named proof.

A plan-version change mid-period does not open a new calendar period: the period belongs to the
person and the calendar, the limit belongs to the pin at admission (§2.3). An upgrade therefore
raises the remaining allowance of the current period at once and a downgrade may leave it exhausted;
`subscription_lifetime` periods do end and begin with the pin.

### 11. Security and privacy consequences

**Of the chosen option.**

- **Server-authoritative, default deny.** Every decision — plan, feature, mode, model, rate, headroom
  — is computed on the server from the authenticated principal, the pinned version and the ledger. A
  client's UI may *hint* from the entitlement payload; nothing it sends is an input to the decision.
  The strict request schema refuses a smuggled `plan`, `plan_version`, `remaining`, `period_end`,
  `time_zone`, `byok`, `key` or counter field as `validation_rejected`, and a forged `mode` selection
  without the matching server-side credential or destination state is refused at step 5, never
  honoured. The absence of a grant, a row or a version denies (§2.4, §3.5).
- **No downgrade paths.** No model substitution (§5), no mode fallback (§6), no plan default (§2.4).
  A refused request has executed nothing and reserved nothing.
- **Drift is detectable.** The counter is a projection with a stated verification cadence and a
  paging divergence signal (§7.4); the ledger is single-writer and append-only, and no role holds
  `UPDATE` or `DELETE` on it, so a tampered count cannot survive an interval and a tampered ledger
  requires a privilege the application does not have.
- **Boundaries cannot be gamed.** The period is pinned at admission and its zone at opening (§8);
  neither a zone toggle, a clock, a retry nor a boundary-straddling stream produces a second
  allowance or a second charge. Idempotency keys make retries replays (§4.4).
- **Keys stay out.** A usage event, counter, period, refusal, signal or trace never carries key
  material or any key identifier or digest, a host name, a provider account identifier or prompt
  content (§6, §7.2). Mode B and C keys follow `T-AI-01` custody; the subscription row has no key
  reference (the sketch-03 `byok_api_key_ref` is discarded).
- **Personal data.** Usage events and periods are a usage pattern and are protected under ADR-018,
  erased under ADR-006 and ADR-021 and retained under `T-CMP-01`; the profile zone appears only in
  the user's own entitlement payload and refusal bodies, never in a signal or log (ADR-015 §3.2). The
  ledger carries no monetary amount, so plan prices and overage purchases live in billing in the
  ADR-015 form and are referenced by `source_ref`, never copied.
- **Disclosure.** `model_not_in_plan` does not reveal whether a model exists; `entitlement_denied`
  reveals the requester's own plan state only; a refusal never names another principal; an operator
  sees usage only through the masked, audited `admin_api` path (ADR-020 §4.2, §5 item 7) and adjusts
  it only by an audited `adjusted` event with a reference, never by editing a count. Experiments
  cannot read or vary entitlement state (`T-EXP-01`, PenniLogic/api#63).
- **Residuals.** A Mode B or C owner can make admissions that release by failing their own
  endpoint; the rate limit bounds the orchestration cost and §6 names the suspension path. Estimator
  error permits a bounded soft overrun (§4.3). A counter that under-counts because of a defect is
  exploitable for at most one reconciliation interval before it is detected and rebuilt (§7.4). A
  limiter-store outage denies AI (fail closed) for
  its duration. The reservation TTL delays reuse of abandoned headroom by up to 900 seconds.

**Of the rejected options.** *Materialized counter as truth* (sketch 03): silent drift, no replay, no
unwind for refunds, a reset cron with a double-run and race hazard. *Plan as a mutable row* (both
sketches): retroactive re-entitlement and re-pricing of existing subscribers, and disputes that
cannot be evaluated against the plan as sold (`T-BIL-10`). *`null = unlimited`*: a missing row grants
everything — the direction of the two commonest bugs. *Client-hinted plan*: spoofing. *Rolling
window*: an unexplainable per-event reset and a scan per admission. *Read-time zone for quota*: the
double-dip of §8.2. *Charging BYOK tokens*: a double charge. *Exempting BYOK requests entirely*:
uncapped orchestration cost (product spec §4.3 guard 4). *Silent model downgrade*: invisible quality change and a
cheaper model substituted for a paid one. *Deriving one dimension from the other*: each cap gamed
through the other (§3.3). *Requests committed at admission regardless of delivery*: charging for
provider failures a Free user cannot influence. *Requests released on any failure without a delivery
line*: free answers from a self-failing endpoint.

### 12. Observability

Signals that prove the decision is honoured, none carrying a user identifier, key material, prompt
content, a host, a time zone or a monetary amount:

- `entitlement.resolution_total{outcome=granted|denied, reason}`, `entitlement.no_plan_total`
  (expected near zero; a rise names a signup or billing pipeline fault),
  `entitlement.cache{hit|miss|invalidation}` and `entitlement.propagation_seconds` from a version or
  subscription event to the gateway's virtual key (must stay under 60).
- `quota.admission_total{feature_key, mode, window, outcome}` and
  `quota.refusal_total{code, reason, feature_key, dimension, plan_code}` — including
  `model_not_in_plan` per plan code (which plans' users ask for unlisted models) and
  `capacity_exceeded`.
- `quota.reservation_total{outcome=committed|released|expired|late_settlement, reason, mode}`,
  `quota.reservation_open_age_seconds` (histogram; evidence for the 900-second TTL),
  `quota.settlement_overrun_tokens` (histogram of commit minus reservation when positive — the
  estimator's quality) and `quota.soft_overrun_total{dimension, window}`.
- `quota.reconciliation.divergence_total{dimension, window}` (must be zero; non-zero pages),
  `quota.reconciliation.last_success_age_seconds` (alert above 7 200), `quota.period_opened_total{window,
  zone_changed}` and `quota.period_frozen_total{window}`.
- `quota.byok_tokens_recorded_total{mode}` — uncharged tokens, for cost transparency and abuse
  review — and `quota.rate_limited_total{feature_key, mode}`.
- Guard counters that must read zero: `quota.model_substitution_total`,
  `quota.mode_fallback_attempt_total`, `quota.client_claim_rejected_total{field}` (a non-zero value
  names a non-conforming client) and `quota.ledger_write_outside_function_total` (a schema-level
  check that the ledger and counters have exactly one writer).
- Client: the taxonomy's `client_state.quota_exceeded` and `client_state.permission_denied{cause=plan}`.
- Build-time: the count of vocabulary entries, catalogue entries and plan versions validated by the
  lint, trended so a silent narrowing shows.

### 14. Rollout and rollback

Adopted on merge; no runtime rollout. §2–§10 bind `T-CON-03`, `T-CON-12`, `T-BIL-01`, `T-BIL-02`,
`T-BIL-07`, `T-BIL-08`, `T-BIL-09`, `T-BIL-10`, `T-AI-01`, `T-AI-07`, `T-ADM-07`, `T-ADM-08`,
`T-ADM-17` and `T-EXP-01` immediately (§16). No client has been generated from a published
entitlement contract yet, so there is no compatibility window: the first published `T-CON-03` version
conforms, and **all three generated clients must be regenerated** from it — Kotlin (server stubs in
`api`, client in `android`), TypeScript (`web`, `admin`) and Python (`ai-service`) — together with
the vocabulary, catalogue and parameters artifacts. Billing paths reworked by this record: entitlement
storage loses `user_entitlements.quota_used` and any mutable plan row (`T-BIL-01`); the quota
primitive is the ledger with reserve, commit and release and periods rather than an increment and a
reset cron (`T-BIL-02`); refund, chargeback and credit-note unwind writes `adjusted` reversals
(`T-BIL-07`); cross-channel precedence selects one pin (`T-BIL-08`); the customer billing portal and
the admin plan and billing views render the entitlement payload and the frozen counters
(`T-BIL-09`, `T-ADM-07`, `T-ADM-17`).

**Rollback position.** The record is not accepted, `T-CON-03` stays blocked and no dependant starts;
nothing runtime exists to reverse. Once adopted, **additive** evolution needs no new record: a new
feature key, catalogue model, window, release reason, adjustment reason or refusal reason, a longer
reservation TTL or a shorter reconciliation interval, each as a versioned artifact change. Changing a
dimension's unit or measurement point, the mode-consumption table, the zone or boundary rule, the
one-terminal-event invariant, the ledger as the source of truth, the no-default-plan rule, the
no-substitution rule, or introducing an unlimited sentinel requires a superseding record that states
the migration cost: every published contract version, three generated clients, every plan version,
the ledger and its frozen periods, and the artifacts.
