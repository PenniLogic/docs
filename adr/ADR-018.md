## ADR-018 — Encryption scope, searchable fields, row-level security and deduplication artefacts
**Status:** ACCEPTED · 2026-09-30

**Decision.** One record settles the contradiction between "amounts are ciphertext" and "the database
sums and constrains amounts", and fixes everything that depended on it:

1. **Ledger money stays plaintext integer columns.** `entries.amount_minor`, `split_shares.share_minor`,
   `split_expenses.amount_minor`, `settlements.amount_minor`, `period_aggregates.total_minor` and every
   currency code remain `BIGINT`/`CHAR(3)` columns so `SUM(entries.amount_minor) = 0` (ADR-002) and
   `SUM(split_shares.share_minor) = split_expenses.amount_minor` execute in PostgreSQL. They are protected
   by forced row-level security, a low-privilege runtime role, storage encryption and no standing human
   access, never by application-layer encryption (§1.3).
2. **Descriptive personal data is application-encrypted** with AES-256-GCM under a per-user data
   encryption key (DEK) wrapped by a key-encryption key (KEK) class, with additional authenticated data
   binding each ciphertext to its row, column and owner, and a versioned key identifier in every
   ciphertext header (§2).
3. **Search is served by a global merchant dictionary at ingest plus a per-tenant HMAC blind index** under
   an index key that is generated, wrapped, rotated and destroyed independently of the DEK. Only the
   equality shapes in §3.3 survive; every other text search is deliberately lost server-side (§3).
4. **Row-level security on PostgreSQL 17 with `FORCE ROW LEVEL SECURITY`** on every owner- or
   member-scoped table, a runtime role with `NOBYPASSRLS`, `WITH CHECK` on every write path and
   `security_invoker` views only. A grant-mediated cross-user read is admitted solely by the policies
   `grant_mediated_read` (detail) and `grant_mediated_aggregate_read` (aggregate), whose exact predicates
   are in §4.3. Every bypass is forbidden by name and a read with no satisfied grant is a denial (§4).
5. **Session context is transaction-local and MAC-bound.** The context keys of §5.1 (`app.principal_id`,
   `app.request_id`, `app.acr`, `app.grant_set`, `app.group_set`, `app.actor`, the pre-authentication
   and administrative keys, and `app.ctx_mac` over one normative payload) are written only by the five
   `SECURITY DEFINER` setters of `app_ctx` — `begin_request`, `begin_keyops`, `begin_preauth`,
   `begin_admin_access`, `begin_redaction` — from values the API process verified (the database never parses
   a token, ADR-019); customer policies admit only `user`, `delegate` and `keyops` actors, pre-authentication
   contexts read only the row they present, administrative contexts only a recorded event's subject; a
   value the client role sets itself carries no valid MAC and admits nothing; `SET LOCAL` semantics clear
   the context before a pooled connection returns (§5).
6. **Every key class has a cryptoperiod, an overlap rule, a resumable rotation state machine, a
   retirement proof, an emergency path and a restore rule** that cannot resurrect retired material (§6).
7. **Three deduplication artefacts are distinct by name, construction and retention:** the device-local
   raw-message digest (a Keystore-keyed HMAC that never leaves the device), the server structured dedupe
   key `transactions.dedupe_key` (a keyed fingerprint over canonical structured fields, never raw text)
   and the fuzzy duplicate-candidate match, whose merge is a reversible link and audit record (§7).
8. **The migration path weakens no ledger constraint** (§8); the machine-readable inventory and policy
   identifiers this record forces are named in §10; the signals and conformance tests in §11–§12.
9. This record **clarifies one sentence of ADR-004** ("A hash of the raw message is stored for
   deduplication") by defining which artefact that sentence means and where it may live. ADR-004's
   decision that raw message content never leaves the device is preserved and strengthened, so
   `supersedes` is `null` (§7.5).

**Relationship to other records.** ADR-001 (integer minor units) and ADR-002 (append-only double entry)
are preserved unchanged: no money column changes type and no constraint is dropped. ADR-005's grants are
now enforced *in the database* by the predicates in §4.3; the ReBAC engine remains the application-level
authority for UI and coarse checks and is fed from the same `sharing_grants` rows. ADR-006's envelope
encryption is made concrete in §2 and §6; the counterparty erasure question ADR-006 left open belongs to
ADR-021 (T-ADR-ERASE-07), and this record only fixes the key *scopes* ADR-021 chooses between (§1.2,
§6.7). ADR-016 (T-ADR-CAT-02) must expose the effective category of a transaction as the column
`transactions.category_id`, because the grant predicate compares it (§4.3). ADR-019 relocates contact
values to `channels` and verifies every token in the API process, so the setter receives a verified
account UUID and `acr` value (§1.2, §5); ADR-020 decides administrative roles and audit stores; ADR-022
decides the runtime platform on which the KEK custodian (§6.1) is selected. None of those records may
loosen a classification, predicate or lifecycle rule here; they may tighten one.

### 1. Column classification

#### 1.1 The rule

Every column of every table that holds a user's data is placed in exactly one class. The rule is applied
column by column, and a migration that creates a column absent from the published inventory (§10) fails
the migration check.

| Class | Meaning | Protection |
|---|---|---|
| **constrained** | Plaintext in the database because a constraint, aggregate, ordering, uniqueness rule, foreign key, scheduler filter or row-level-security predicate must evaluate it. Opaque identifiers (UUIDv7 keys and foreign keys), enums, timestamps and ledger money are here. | Forced RLS, low-privilege role, column-level grants, storage encryption, encrypted backups, no standing human access (T-PLT-05), never written to logs, traces or analytics. |
| **encrypted** | AES-256-GCM ciphertext under the row owner's DEK (or the group/platform scope stated); the database cannot evaluate it. | Envelope encryption (§2), erasable by key destruction (ADR-006). |
| **blind-indexed** | `encrypted`, plus an HMAC-SHA-256 blind index under a *separate* index key permitting equality lookup only. | §3.2; frequency leakage acknowledged in §3.4. |
| **key material** | Wrapped keys, never plaintext, never readable by the runtime role except the row its context admits. | §2, §6. |
| **reference** | Product reference data with no owner (the merchant dictionary, system categories). Not personal data. | Read-only grant to the runtime role; no RLS. |
| **absent** | Structurally has no server column and no schema field: raw message text and any raw-derived digest. | §7.1; T-CON-02 and T-CON-15 negative fixtures. |

Ledger money is *constrained*; user-declared financial parameters that no constraint or database-side
aggregate evaluates (APR, minimum payment, expected salary, goal target, budget limit) are *encrypted*,
because the debt engine, budgets and goals read a handful of rows per user in the application.

**Default class and extension procedure.** The inventory is closed to silent additions, not to growth. A
column that a later record or ticket introduces and that §1.2 does not list is `encrypted` by default;
`constrained` must be justified by a stated constraint, aggregate, ordering, scheduler filter or
row-level-security predicate; opaque identifiers, enums and timestamps are `constrained` by the rule
above. The owning ticket adds the row to the `crypto-inventory` artefact (§10) with a version bump and
security and privacy review before the migration lands; the migration check compares against the
**current artefact version**, of which §1.2 is the v1 baseline, so adding a column is an implementation
ticket's change and only *loosening* a class, predicate or lifecycle rule below this record requires a
superseding record. Every table with an owner or subject column is under `FORCE ROW LEVEL SECURITY` with
`owner_rows` by default; a table that must be read before any principal exists receives a named policy in
the `preauth` family of §4.2 that admits only the row the presented lookup value names.

#### 1.3 Ledger amounts are not application-encrypted

`entries.amount_minor`, `split_shares.share_minor`, `split_expenses.amount_minor`,
`settlements.amount_minor`, `period_aggregates.total_minor` and their currency columns are never
application-layer encrypted. Randomised ciphertext cannot be summed, compared or constrained, and a
constraint that the database cannot execute is not a constraint. The compensating controls are:

- `FORCE ROW LEVEL SECURITY` on every table holding them, with `owner_rows` and the member/grant policies
  of §4.2; a query without a verified context sees no row.
- The runtime role `pennilogic_app` has `SELECT` and `INSERT` on `entries`, `split_shares` and
  `settlements` and no `UPDATE` or `DELETE` on any ledger table; corrections are reversing entries
  (ADR-002). Column-level `UPDATE` exists only for the mutable metadata columns named in §4.1.
- Storage encryption of volumes and encrypted backups (T-PLT-02); backups never contain a plaintext DEK
  or the KEK (§6.6).
- No standing human production access; break-glass reads are governed and recorded (T-PLT-05); no
  administrative role holds `BYPASSRLS` (§4.4, ADR-020).
- Ownership is pseudonymous at the storage layer: every money row references an opaque `owner_id`, and
  the identity columns that would name the person are encrypted (§1.2).
- Amounts never appear in logs, traces, error messages or analytics events (T-TXN-03, §11).
- Integrity: the append-only grant model plus the nightly zero-sum and hash-chain integrity job named in
  `architecture/02-security-architecture.md` §1.4 (T-12).

What this does not protect against is stated in §9: a reader who obtains a database dump or a superuser
session sees amounts, timestamps and opaque identifiers in the clear.

### 2. Cryptographic construction

- **Cipher.** AES-256-GCM with a 96-bit nonce drawn from a CSPRNG per encryption and a 128-bit tag. A DEK
  is retired before 2^28 encryptions, which keeps the random-nonce collision probability below 2^-40 for
  the key's life. `user_keys.encrypt_count` is incremented **atomically by the number of encryptions in
  each batch** by every API instance; scheduled rotation falls due at 2^27 regardless of age; at
  `2^28 − 2^24` the writer **fails closed** — it refuses to encrypt under that key, raises
  `crypto.encrypt_cap_reached` and pages — so a stalled rotation can never push a key past the bound.
- **Additional authenticated data.** `AAD = header || table_name || column_name || row_id || scope_id`
  in a fixed canonical byte encoding, where `header` is the version, key-scope and key-identifier prefix
  below and `scope_id` is `owner_id` (or `group_id` on a member-scoped table). A ciphertext moved to
  another row, column or owner, or re-labelled with another key identifier, fails authentication, so a
  writer with database access cannot transplant a value. Row identifiers are therefore generated (UUIDv7)
  before encryption, never assigned by the database afterwards.
- **Plaintext encoding inside the ciphertext.** An encrypted money column (`debts.min_payment_minor`,
  `debts.fees_minor`, `income_sources.expected_amount_minor`, `goals.target_amount_minor`,
  `budgets.limit_minor`) encrypts the canonical ADR-015 `Money` wire object as UTF-8 JSON — the same codec
  and conformance vectors every language already uses — and its currency is repeated in the row's
  constrained `currency` column (ADR-001 pairing; the two must agree, and the test
  `encrypted_money_encoding_round_trip` asserts it). Every other encrypted integer (`apr_bps`,
  `term_months`) encrypts its canonical decimal ASCII string; text encrypts UTF-8. No language-native
  binary integer encoding is ever used, so the Kotlin, TypeScript and Python codecs cannot drift.
- **Length hiding.** Plaintext is padded to a multiple of 16 bytes (a `0x80` marker followed by zeros)
  before encryption, so ciphertext length reveals only a coarse size bucket rather than the exact length
  of a merchant name or note.
- **Ciphertext header** (stored in the same `BYTEA`): `version (1 byte) || key_scope (1 byte: user,
  group, platform) || key_id (16 bytes, the `user_keys.key_id` or platform key id) || nonce (12 bytes)
  || ciphertext || tag (16 bytes)`. The key identifier is what makes overlap, resumable re-encryption and
  retirement proof possible (§6): the reader selects the key the header names, the writer always uses the
  owner's single `ACTIVE` key.
- **Envelope.** Each user has one `ACTIVE` DEK and zero or more `DECRYPT_ONLY` DEKs. A DEK is 32 random
  bytes generated in the API process (or by the custodian's data-key operation) and stored only as
  `wrapped_key = KEK.wrap(dek, aad = user_id || key_id || purpose)`. The KEK never leaves its custodian;
  the API requests wrap and unwrap operations and holds unwrapped DEKs only in process memory (§5.4 and
  §6.1 bound the cache). A `canary` column holds `Encrypt(DEK, "pennilogic-canary", AAD of the key row)`
  so a key can be proven usable without touching user data.
- **Key separation.** The per-tenant index key (IK) is 32 independent random bytes with `purpose = IK`,
  wrapped under the KEK exactly like the DEK and never derived from it; the global identity index key,
  the server fingerprint key and the context MAC key are further independent keys (§6.1). Compromise of
  any one reveals nothing about another. The blind index is `HMAC-SHA-256(IK, canonical_value)`; the
  same plaintext under the DEK produces a different ciphertext every time, so equality is visible only
  through the index and only within the tenant.
- **Where cryptography runs.** Data encryption, blind-index and fingerprint computation run in the API
  process; the database never receives a DEK, an IK, the fingerprint key or the KEK. `pgcrypto` is used
  for exactly one purpose: the context MAC of §5, whose key is database-internal by design.
- **Erasure.** Destroying a user's DEK and IK rows (ADR-006) makes every `encrypted` and per-tenant
  `blind-indexed` value of that user unreadable through the live system, within the completeness bound
  §6.7 publishes; constrained columns remain, which is why §1.2 keeps identity out of them and §6.7 severs
  the relationship rows that could re-link them.

### 3. Searchable design

#### 3.1 The merchant dictionary is used at ingest, never as a per-row link

The global `merchants` dictionary (canonical names, normalised keys, aliases, default category hints;
curated by the merchant-normalisation ticket) is reference data, not personal data. At ingest the API
normalises the parsed merchant string, looks the key up in the dictionary, obtains the canonical display
name and category hint, then stores `merchant_display` encrypted under the user's DEK and
`merchant_bidx = HMAC(IK_user, merchant_norm)`. **No user row stores a plaintext dictionary foreign
key**: a `merchant_id` column would make each user's merchant readable to anyone with database access and
would enable cross-user grouping, which is exactly the leakage the blind index avoids.

#### 3.2 The per-tenant blind index

`merchant_norm` is the dictionary's normalised key when one matches, otherwise the parser output after
NFKC normalisation, lower-casing, punctuation and whitespace stripping and trailing digit-run removal.
Blind indexes exist only for the columns §1.2 marks *blind-indexed*: `accounts.mask`,
`transactions.merchant_display`, `transactions.external_ref`, `merchant_rules.merchant_bidx` (all under
the owner's IK) and `channels.value` (under the global identity index key, GIK: `value_bidx =
HMAC-SHA-256(GIK, type || canonical(value))` with e-mail canonicalised by NFKC and lower-casing and phone
by E.164). Per-tenant indexes are composite `(owner_id, <column>_bidx)`; the identity index is
`(type, value_bidx)`, unique for verified rows. A blind index value is never returned by any API, sync or
export response; clients search by plaintext and the server computes the HMAC.

#### 3.3 Query shapes that remain possible and shapes deliberately lost

| Shape | Server-side | How |
|---|---|---|
| Own transactions by normalised merchant, exact | kept | `merchant_bidx` equality; group-by on the index for spend-by-merchant, display name decrypted from one representative row. |
| Own transactions by amount, amount range, currency, account, direction, date range, source, category, review state | kept | Constrained columns and ordinary indexes. |
| Resolve an incoming `account_ref` to an account | kept | `accounts.mask` blind index within the owner. |
| Cross-channel match by provider reference | kept | `external_ref` blind index within the owner. |
| Learned merchant rules and recurring detection | kept | Equality on `merchant_bidx` plus constrained amount and time columns; fuzzy comparison in application memory over the small candidate set (§7.3). |
| Pre-authentication lookup of an account by e-mail or phone (recovery initiation, one verified account per e-mail, phone trial-abuse check — ADR-019) | kept | Global identity blind index on `channels.value_bidx`; uniqueness by the partial unique index. |
| Grant-mediated read of another user's category detail or closed-period aggregate | kept | §4.3 predicates; filters on constrained columns only. |
| Merchant prefix, wildcard or fuzzy search | **lost** | Would need order-preserving or prefix encryption, which leaks ordering; Android searches its local SQLCipher store instead. |
| Note or description substring search | **lost** | Tokenised blind indexes leak vocabulary and co-occurrence; local search only. |
| Server-side full-text search of any encrypted column | **lost** | T-TXN-03 non-goal. |
| Cross-user merchant analytics at row level | **lost** | Per-tenant keys make identical merchants incomparable across users by design; only separately governed aggregate pipelines may answer such questions. |
| Any sort or range over an encrypted column | **lost** | Ciphertext is randomised. |

#### 3.4 Frequency-analysis leakage and its mitigation

Within one tenant, equal normalised merchants produce equal index values. A reader with database access
therefore sees, per opaque owner, how many rows share each index value and can correlate that with the
plaintext amounts and timestamps ("the recurring value on the 5th of each month with a fixed amount is
probably rent or an EMI"). The record accepts this leakage because amounts and timestamps already reveal
it, and mitigates the rest:

- the key is **per tenant**, so no rainbow table, dictionary attack or cross-user frequency comparison
  works without that user's IK, and known plaintext for one user reveals nothing about another;
- only the equality fields of §3.2 are indexed; notes, descriptions, amounts and timestamps never are;
- IK rotation (§6) re-randomises every index value, bounding the longitudinal window;
- index values are never emitted by any interface; and
- destroying the IK on erasure makes a user's residual index values meaningless, and T-SEC-06 rewrites
  or destroys them physically as defence in depth against a future IK exposure from backups.

### 4. Row-level security posture

#### 4.1 Roles

PostgreSQL 17 is the minimum; it provides `transaction_timeout`, which §5.4 relies on. Runtime roles:

```sql
CREATE ROLE pennilogic_app    LOGIN NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOINHERIT;
CREATE ROLE pennilogic_keyops LOGIN NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOINHERIT;
CREATE ROLE pennilogic_ctx  NOLOGIN NOSUPERUSER NOBYPASSRLS;
ALTER ROLE pennilogic_app SET statement_timeout = '15s';
ALTER ROLE pennilogic_app SET transaction_timeout = '20s';
ALTER ROLE pennilogic_app SET idle_in_transaction_session_timeout = '5s';
ALTER ROLE pennilogic_app SET lock_timeout = '5s';
-- No amount, ciphertext, blind-index value or bind parameter may reach a server or API log (§1.3, §3.2):
ALTER ROLE pennilogic_app    SET log_error_verbosity = 'terse';   -- no DETAIL "Failing row contains (...)"
ALTER ROLE pennilogic_keyops SET log_error_verbosity = 'terse';
ALTER ROLE pennilogic_app    SET log_statement = 'none';
ALTER ROLE pennilogic_app    SET log_parameter_max_length = 0;
ALTER ROLE pennilogic_app    SET log_parameter_max_length_on_error = 0;
-- The API additionally strips DETAIL and HINT from any database error before logging it.
```

- `pennilogic_app` — the only role the API connects as. `SELECT`/`INSERT` on ledger tables; column-level
  `UPDATE` only on **mutable descriptive metadata**: `transactions.needs_review`, `.status`,
  `.category_id`, `.note`, `.description`, `.merchant_display`/`.merchant_bidx`,
  `.external_ref`/`.external_ref_bidx`, `.source_confidence` (the columns that source-precedence enrichment
  and a "What was this?" answer may change, §7.3), `accounts.name`, `accounts.is_archived`,
  `merchant_rules.*`, `sharing_grants.revoked_at`, `duplicate_links.reversed_at`/`reversed_by`,
  `channels.verified_at`/`matured_at`/`suspect`, and `transactions.dedupe_key`/`dedupe_key_version` **only
  while `status = 'candidate'`** (the post-clarification key of §7.2; a trigger
  `transactions_dedupe_key_immutable_once_posted` rejects any later change by this role). **Never
  updatable by any runtime role:** every ledger fact — `entries.*`, `split_shares.*`, `settlements.*`,
  `transactions.owner_id`, `.occurred_at`, `.booked_at`, `.source`, `.source_event_id`, `.merchant_raw` —
  and no `DELETE` anywhere. Every enrichment writes its provenance to the dedup outcome and the audit
  stream (§7.3).
- `pennilogic_keyops` — the rotation and re-encryption worker. Column-level `UPDATE` on ciphertext,
  header and blind-index columns, on the fingerprint columns `transactions.dedupe_key`/`dedupe_key_version`
  (the `K_dedupe` rebuild of §7.2) and on `channels.value_bidx`/`value_bidx_version`, plus `user_keys`.
  Never any other constrained column, never `entries`.
- `pennilogic_ctx` — owns schema `app_ctx` (the setters and the verifiers) and schema `app_private`
  (`context_keys`). It holds `SELECT` on `sharing_grants` and `split_group_members`, admitted by the
  explicit `resolver_read` policies, plus the read of ADR-020's foundational audit event and unmask-grant
  status that §5.5 requires, and no privilege on any other table. It reads no user data.
- The migration/table-owner role is `NOLOGIN` outside the migration runner (T-MIG-01) and sets no
  context, so under `FORCE ROW LEVEL SECURITY` it sees no rows. Superuser exists only for the database
  administrator's break-glass path (T-PLT-05) and is never a credential any service holds.
- ADR-020's administrative role(s) are additional runtime roles subject to every rule in §4.4.

#### 4.2 Forced policies

Every table in §1.2 except `merchants` and `trial_fingerprints` has `ENABLE ROW LEVEL SECURITY` and
`FORCE ROW LEVEL SECURITY` from the migration that creates it (the ledger schema ticket, historically
`api#2`, owns the statement; T-SEC-01 owns the roles and policies). A CI lint on the migration set fails
any `DISABLE ROW LEVEL SECURITY`, `NO FORCE ROW LEVEL SECURITY`, `BYPASSRLS`, `SUPERUSER`, any
`SECURITY DEFINER` function whose owner owns a protected table or holds `BYPASSRLS`/`SUPERUSER`, any
`SECURITY DEFINER` function whose owner is not on the **definer-owner whitelist** published in the
`crypto-inventory` artefact (§10) — `pennilogic_ctx`, and the `NOLOGIN`, `NOBYPASSRLS` owners of ADR-020's
administrative, audit-trail and transparency-relay functions, each owning no protected table — and any view
over a protected table that is not `WITH (security_invoker = true)`. ADR-020's administrative read path is
**functions only**, which this lint admits; an owner-rights view is not sanctioned by this record, and a
record that needed one would have to give its owner the same properties as a whitelisted definer and
exclude every monetary, ciphertext, key and blind-index column. Policies are `PERMISSIVE` and combine by
OR; a table with no admitting policy for the current context admits nothing. All policy predicates call the
verifiers through uncorrelated scalar subqueries so the MAC is checked once per statement, not once per row.

Customer policies read the principal through **`app_ctx.verified_customer_principal()`**, which returns
`app.principal_id` only when the MAC verifies **and** `app.actor` is `user`, `delegate:<client_id>` or
`keyops:<job_id>`. A `preauth`, `admin:` or `redaction:` context therefore satisfies no customer policy,
whatever principal it carries; those contexts are admitted only by the narrow families named for them.

| Table group | Policies |
|---|---|
| Owner-scoped tables (`accounts`, `transactions`, `entries`, `duplicate_links`, `merchant_rules`, `period_aggregates`, `debts`, `income_sources`, `goals`, `budgets`, `user_keys`, and by default every later table with an owner column, §1.1) | `owner_rows` — `FOR ALL TO pennilogic_app, pennilogic_keyops USING (owner_id = (SELECT app_ctx.verified_customer_principal())) WITH CHECK (owner_id = (SELECT app_ctx.verified_customer_principal()))`; on `user_keys` the compared column is `user_id`, on ADR-019's tables `account_id`. |
| `transactions`, `entries` | plus `grant_mediated_read` (§4.3). |
| `period_aggregates` | plus `grant_mediated_aggregate_read` (§4.3). |
| `user_keys` | plus `grant_mediated_key_read` — `FOR SELECT TO pennilogic_app USING (purpose = 'DEK' AND state IN ('ACTIVE', 'DECRYPT_ONLY') AND user_id::text IN (SELECT split_part(g, ':', 1) FROM unnest((SELECT app_ctx.verified_grant_set())) AS g WHERE split_part(g, ':', 3) = 'detail'))`, so the API can unwrap a grantor's DEK inside the grantee's detail-level request and nothing else: no IK row (no cross-user search shape exists, §3.3), no retired or destroyed row, and no key row at all for an aggregate grant. The plaintext DEK never leaves the process and the use is recorded (§5.4). |
| Member-scoped tables (`split_groups`, `split_group_members`, `split_expenses`, `split_shares`, `settlements`) | `group_member_rows` — `FOR ALL TO pennilogic_app USING (group_id::text = ANY ((SELECT app_ctx.verified_group_set()))) WITH CHECK (group_id::text = ANY ((SELECT app_ctx.verified_group_set())))`; on `split_groups` the compared column is `id`, on `split_shares` the denormalised `group_id` of §1.2; `verified_group_set()` is empty for every non-customer actor. Split projections are copies into these tables; they never use `grant_mediated_read`. |
| `sharing_grants` | `grant_party_rows` — `FOR SELECT TO pennilogic_app USING (grantor_id = (SELECT app_ctx.verified_customer_principal()) OR grantee_id = (SELECT app_ctx.verified_customer_principal()))`; `grant_create` — `FOR INSERT TO pennilogic_app WITH CHECK (grantor_id = (SELECT app_ctx.verified_customer_principal()))`; `grant_revoke` — `FOR UPDATE TO pennilogic_app USING (grantor_id = (SELECT app_ctx.verified_customer_principal()) OR grantee_id = (SELECT app_ctx.verified_customer_principal())) WITH CHECK (same)`, with column-level `UPDATE` on `revoked_at` only, so either party can end a grant unilaterally (ADR-005 revocation and the safe-exit flow) and only the grantor can create one; `resolver_read` — `FOR SELECT TO pennilogic_ctx USING (true)`. |
| `split_group_members` | plus `resolver_read` — `FOR SELECT TO pennilogic_ctx USING (true)`. |
| `access_events` (ADR-020 transparency projection) | `owner_rows` for `SELECT` (the data subject reads their entries); no `INSERT` policy for `pennilogic_app` — the row is projected by ADR-020's relay from the `audit.event` the API inserted (§1.2). The former direct-append form is withdrawn to keep ADR-020's single-write rule. |
| `users` | `self_rows` — as `owner_rows` with `id` as the compared column. |
| **`preauth` family** (tables that must be read before a principal exists; the only policies a `preauth` context satisfies) | `preauth_lookup_rows` — `ON channels FOR SELECT TO pennilogic_app USING ((SELECT app_ctx.verified_actor()) = 'preauth' AND type = (SELECT app_ctx.verified_preauth_kind()) AND value_bidx = (SELECT app_ctx.verified_preauth_value()))` — exactly the row the presented `(type, value_bidx)` names and no other; the same shape on `credentials` (`kind = 'credential'`, compared on the credential id the assertion presents) and on `refresh_tokens` (compared on the presented token hash). `preauth_subject_rows` — `FOR SELECT TO pennilogic_app USING ((SELECT app_ctx.verified_actor()) = 'preauth' AND account_id = (SELECT app_ctx.verified_preauth_account()))` on ADR-019's identity and recovery tables only (`channels`, `devices`, push tokens, `recovery_requests`), so that once ADR-019's flow has resolved the account through `begin_preauth(..., p_account)` every channel and device can be notified. Nothing else: a `preauth` context reads no ledger, key, grant or group row, and `app.principal_id` is never set for it. |
| Administrative roles (ADR-020) | `admin_recorded_access` — `FOR SELECT TO admin_api_owner, redaction_service USING (owner_id = (SELECT app_ctx.verified_admin_subject()))` (§5.5) on the tables ADR-020 exposes, under ADR-020's redaction-by-default, justification, four-eyes and audit rules; never `TO PUBLIC`, never through `owner_rows` or `grant_mediated_*`, never a bypass named in §4.4. |

`resolver_read` is the only `USING (true)` policy that admits a customer-path role. It admits `pennilogic_ctx`
to two relationship tables so that the setter can resolve grants and memberships; it is not a read of user
data. Policies admitting administrative roles are ADR-020's and are subject to §4.4.

#### 4.3 The exact grant-mediating predicates

The stable identifiers are `grant_mediated_read` (detail level; tables `transactions` and `entries`) and
`grant_mediated_aggregate_read` (aggregate level; table `period_aggregates`). They are the values the
sharing contract's grant reference takes (T-CON-04) and the values written to
`access_events.policy_identifier`. A change to either predicate's semantics is a new identifier
(`grant_mediated_read_v2`) introduced by a superseding record, never an in-place edit.

```sql
-- transactions: compares transactions.owner_id, transactions.category_id, transactions.needs_review
-- with the verified session values app.principal_id and app.grant_set.
CREATE POLICY grant_mediated_read ON transactions
    AS PERMISSIVE FOR SELECT TO pennilogic_app
    USING (
        (SELECT app_ctx.verified_customer_principal()) IS NOT NULL
        AND transactions.owner_id <> (SELECT app_ctx.verified_customer_principal())
        AND transactions.needs_review = false
        AND (transactions.owner_id::text || ':' || transactions.category_id::text || ':detail')
            = ANY ((SELECT app_ctx.verified_grant_set()))
    );

-- entries: compares entries.owner_id and entries.transaction_id; the parent transaction must itself be
-- admitted, which under RLS means admitted by grant_mediated_read above.
CREATE POLICY grant_mediated_read ON entries
    AS PERMISSIVE FOR SELECT TO pennilogic_app
    USING (
        (SELECT app_ctx.verified_customer_principal()) IS NOT NULL
        AND entries.owner_id <> (SELECT app_ctx.verified_customer_principal())
        AND EXISTS (SELECT 1 FROM transactions t
                     WHERE t.id = entries.transaction_id AND t.owner_id = entries.owner_id)
    );

-- period_aggregates: compares period_aggregates.owner_id and period_aggregates.category_id.
CREATE POLICY grant_mediated_aggregate_read ON period_aggregates
    AS PERMISSIVE FOR SELECT TO pennilogic_app
    USING (
        (SELECT app_ctx.verified_customer_principal()) IS NOT NULL
        AND period_aggregates.owner_id <> (SELECT app_ctx.verified_customer_principal())
        AND (period_aggregates.owner_id::text || ':' || period_aggregates.category_id::text || ':aggregate')
            = ANY ((SELECT app_ctx.verified_grant_set()))
    );
```

`app.grant_set` is a comma-separated list of tokens `<grantor_id>:<category_id>:<detail_level>`,
one per active grant row the setter resolved (§5.2). The token form is injection-safe because every
component is UUID text or the `detail_level` enum; none can contain `:` or `,`. Consequences of the exact
form: a transaction with a
`NULL` category or with `needs_review = true` is never admitted to anyone but its owner; an aggregate grant
admits no `transactions` or `entries` row and a detail grant admits no `period_aggregates` row (ADR-005:
the two levels are independently grantable); `accounts` has no grant policy, so a grantee obtains amounts
and opaque account identifiers but never an account name, institution or mask, and the sharing projection
omits `account_id` (T-CON-04). The `entries` policy does not repeat the category comparison; it inherits
it through the parent-row subquery, which the database evaluates under the same policies.

#### 4.4 Bypasses forbidden by name

- **No `BYPASSRLS` role.** No runtime, administrative, reporting, migration or replication role has the
  attribute; `SELECT rolname FROM pg_roles WHERE rolbypassrls` must return only bootstrap superusers, and
  the T-SEC-01 test asserts it.
- **No superuser connection** from any service, job, dashboard, migration runner or admin console.
- **No `SECURITY DEFINER` read that skips a predicate.** A definer function bypasses row-level security
  only when its owner owns the table without `FORCE ROW LEVEL SECURITY`, holds `BYPASSRLS` or is a
  superuser; every one of those is forbidden. A definer whose owner is a `NOLOGIN`, `NOBYPASSRLS`,
  non-superuser role that owns no protected table remains subject to the policies written for that role
  under `FORCE ROW LEVEL SECURITY` and is permitted. The whitelisted owners are this record's
  `pennilogic_ctx` (setters and verifiers in `app_ctx`, reading only `sharing_grants`,
  `split_group_members`, `app_private.*` and the ADR-020 audit event and unmask-grant status of §5.5) and
  the `NOLOGIN`, `NOBYPASSRLS` owners of ADR-020's administrative, audit-trail and transparency-relay
  functions, each owning no protected table and reading customer rows only under `admin_recorded_access`
  (§5.5); the list is published in the artefact (§10). The lint fails any other definer owner and
  any definer whose owner owns a protected table or holds `BYPASSRLS`.
- **No disabling of `FORCE ROW LEVEL SECURITY`**, no `DISABLE ROW LEVEL SECURITY`, no `USING (true)`
  policy for a customer-path role on a data table (only `resolver_read` on the two relationship tables),
  no policy `TO PUBLIC`.
- **No owner-rights view or materialized view** over a protected table: every view is
  `security_invoker = true`, materialized views are not created over owner-scoped tables, and the
  administrative read path is functions only (ADR-020). Any future owner-rights view would need an owner
  with the properties of a whitelisted definer and could expose no monetary, ciphertext, key or blind-index
  column; none is sanctioned here.
- **No prepared-transaction path**: `max_prepared_transactions = 0`, so no context or recorded event can
  outlive or be joined from another session.
- **No cross-user read through application code** (an API code path that connects as the owner, elevates
  a role or copies rows) — the predicate in the database is the only admitting path (T-SEC-01).
- **No logical replication or foreign-data-wrapper path** that exposes protected tables to another
  database without the same policies.

#### 4.5 Denial, not emptiness

A cross-user read with no satisfied grant predicate is a **denial**. The decision is taken before any row
is read: `app_ctx.begin_request` raises `SQLSTATE 42501` (`insufficient_privilege`, message
`grant_not_active`) when any named target owner has no active grant at the requested level (§5.2). The
API maps that error to the refusal shape T-CON-12 publishes with the sharing cause `grant_not_active`,
which clients render as `permission_denied` (`product/client-state-taxonomy.md` §3.6 and §9); the copy is
identical for an absent, revoked, expired or never-existing grant. The API never interprets an empty
result set of a cross-user query as "nothing to show": if a request names another owner and the verified
grant set contains no token for that owner, the API returns the denial regardless of what the query
returned. The row-level policies remain the last line of defence, filtering rows when an application bug
lets a query through; they are not the mechanism that tells the user "no".

### 5. Session context and the trusted setter

#### 5.1 Context keys

| Key | Content | Written by |
|---|---|---|
| `app.principal_id` | UUID of the authenticated reading principal — the account UUID the API verified (the delegated `sub` for tool calls, ADR-019); on a key-operations job the owner the job acts for; empty on a pre-authentication or administrative context | setter only |
| `app.request_id` | Correlation UUID for audit and access events (T-CON-12) | setter only |
| `app.acr` | The authentication-context value the API verified for this request, as ADR-019 defines it (`^[a-z0-9_]{1,32}$`); carried and audited, and evaluated by the setter for the one rule the database can enforce (§5.2) | setter only |
| `app.grant_set` | Comma-separated `<grantor_id>:<category_id>:<detail_level>` tokens resolved for this request, empty for own-data requests | setter only |
| `app.group_set` | Comma-separated split-group UUIDs the principal is an active member of | setter only |
| `app.actor` | `user`, `delegate:<client_id>` (a tool call acting for the principal, ADR-019/ADR-022), `preauth` (recovery or sign-in lookups before any principal exists, ADR-019), `keyops:<job_id>`, or the administrative values `admin:<audit_event_id>` / `redaction:<unmask_grant>` of §5.5; the setter accepts only `^(user\|preauth\|delegate:[A-Za-z0-9._-]{1,64}\|keyops:<uuid>\|admin:<uuid>\|redaction:<uuid>)$` | setter only |
| `app.preauth_kind`, `app.preauth_value`, `app.preauth_account` | Pre-authentication contexts only: the lookup kind (`email`, `phone`, `credential`, `refresh_token`), the presented lookup value (`value_bidx`, credential id or token hash) and, once ADR-019's flow has resolved it, the account UUID; the `preauth` family compares exactly these | setter only |
| `app.admin_event`, `app.admin_subject` | Administrative contexts only (§5.5): the recorded foundational audit event or unmask grant, and the subject it names; never set together with `app.principal_id` | setter only |
| `app.recorded_admin_events` | Comma-separated audit event ids inserted **by this transaction** through ADR-020's audit insert path, appended by `app_ctx.record_admin_event` (§5.5); its own MAC is `app.recorded_admin_events_mac` | `record_admin_event` only |
| `app.ctx_mac` | Hex HMAC-SHA-256 under the context key over the **one normative payload** `v2\|principal\|request\|acr\|grant_set\|group_set\|actor\|preauth_kind\|preauth_value\|preauth_account\|admin_event\|admin_subject\|pg_backend_pid()\|transaction_timestamp()` — every field present in every context, empty when not applicable, each field constrained to a charset that excludes `\|` and `,` | setter only |

Only the setters may write these keys. The client role may not: the migration and application-code
lint forbids any `SET app.`, `SET LOCAL app.` or `set_config('app.` outside schema `app_ctx`, and the
prohibition is also self-enforcing — PostgreSQL cannot stop a session from setting a custom GUC, but a
value not covered by a valid `app.ctx_mac` is invisible to every policy, because policies read the context
only through the verifiers. All values are written with `set_config(name, value, is_local => true)`: they
exist only inside the current transaction. **The database never receives or parses a token** (ADR-019):
token, DPoP, step-up, workload and delegation verification happens in the API process, which then calls
the setter with the verified account UUID and `acr` value.

#### 5.2 Setter and verifier

The normative behaviour is the SQL below; an implementation may restructure the PL/pgSQL but not the
compared values, the fail-closed paths or the MAC binding.

```sql
CREATE SCHEMA app_ext;
CREATE EXTENSION IF NOT EXISTS pgcrypto WITH SCHEMA app_ext;   -- app_ext.hmac() for the context MAC only (§2);
                                                             -- schema-qualified because search_path is pinned
CREATE SCHEMA app_private AUTHORIZATION pennilogic_ctx;   -- context_keys(key_id, key bytea, valid_from, valid_to)
CREATE SCHEMA app_ctx     AUTHORIZATION pennilogic_ctx;
REVOKE ALL ON SCHEMA app_private FROM PUBLIC;
GRANT SELECT ON public.sharing_grants, public.split_group_members TO pennilogic_ctx;  -- with resolver_read (§4.2)
-- Every table reference inside app_ctx is schema-qualified because search_path is pinned to pg_catalog, pg_temp.

-- One normative payload for every context. Each field is charset-constrained so that no field can contain
-- the '|' or ',' separators; empty strings stand for fields a context does not use.
CREATE FUNCTION app_ctx.payload(p_principal text, p_request text, p_acr text, p_grants text,
                                p_groups text, p_actor text, p_pre_kind text, p_pre_value text,
                                p_pre_account text, p_admin_event text, p_admin_subject text)
RETURNS bytea LANGUAGE sql STABLE AS $$
  SELECT convert_to(format('v2|%s|%s|%s|%s|%s|%s|%s|%s|%s|%s|%s|%s|%s',
      p_principal, p_request, p_acr, p_grants, p_groups, p_actor, p_pre_kind, p_pre_value,
      p_pre_account, p_admin_event, p_admin_subject, pg_backend_pid(), transaction_timestamp()), 'UTF8')
$$;

CREATE FUNCTION app_ctx.write_context(p_principal text, p_request text, p_acr text, p_grants text,
                                      p_groups text, p_actor text, p_pre_kind text, p_pre_value text,
                                      p_pre_account text, p_admin_event text, p_admin_subject text)
RETURNS void LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, pg_temp AS $$
DECLARE v_key bytea;
BEGIN
    IF p_acr !~ '^[a-z0-9_]{1,32}$'
       OR p_actor !~ ('^(user|preauth|delegate:[A-Za-z0-9._-]{1,64}|(keyops|admin|redaction):'
                      || '[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12})$')
       OR p_pre_kind !~ '^(|email|phone|credential|refresh_token)$'
       OR p_pre_value !~ '^[0-9a-f-]{0,2048}$'                       -- hex-encoded bidx, credential id or hash
       OR (p_grants <> '' AND p_grants !~ ('^[0-9a-f-]{36}:[0-9a-f-]{36}:(detail|aggregate)'
                                            || '(,[0-9a-f-]{36}:[0-9a-f-]{36}:(detail|aggregate))*$'))
       OR p_groups !~ '^[0-9a-f,-]*$' THEN
        RAISE EXCEPTION 'context_invalid' USING ERRCODE = '22023';    -- no separator can enter the MAC
    END IF;
    SELECT k.key INTO STRICT v_key FROM app_private.context_keys k
     WHERE k.valid_from <= now() AND (k.valid_to IS NULL OR k.valid_to > now())
     ORDER BY k.valid_from DESC LIMIT 1;
    PERFORM set_config('app.principal_id',    p_principal,     true);
    PERFORM set_config('app.request_id',      p_request,       true);
    PERFORM set_config('app.acr',             p_acr,           true);
    PERFORM set_config('app.grant_set',       p_grants,        true);
    PERFORM set_config('app.group_set',       p_groups,        true);
    PERFORM set_config('app.actor',           p_actor,         true);
    PERFORM set_config('app.preauth_kind',    p_pre_kind,      true);
    PERFORM set_config('app.preauth_value',   p_pre_value,     true);
    PERFORM set_config('app.preauth_account', p_pre_account,   true);
    PERFORM set_config('app.admin_event',     p_admin_event,   true);
    PERFORM set_config('app.admin_subject',   p_admin_subject, true);
    PERFORM set_config('app.ctx_mac', encode(app_ext.hmac(app_ctx.payload(p_principal, p_request, p_acr, p_grants,
        p_groups, p_actor, p_pre_kind, p_pre_value, p_pre_account, p_admin_event, p_admin_subject),
        v_key, 'sha256'), 'hex'), true);
END $$;
REVOKE ALL ON FUNCTION app_ctx.write_context FROM PUBLIC;   -- callable only by the setters below (same owner)

CREATE FUNCTION app_ctx.begin_request(p_principal uuid, p_request_id uuid, p_acr text,
                                      p_actor text DEFAULT 'user',
                                      p_targets uuid[] DEFAULT '{}', p_level text DEFAULT 'detail')
RETURNS void LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, pg_temp AS $$
DECLARE v_grants text[]; v_groups text[]; v_target uuid;
BEGIN
    IF p_principal IS NULL OR p_request_id IS NULL OR p_acr IS NULL THEN
        RAISE EXCEPTION 'context_incomplete' USING ERRCODE = '42501';
    END IF;
    IF p_principal = ANY (p_targets) OR p_level NOT IN ('detail', 'aggregate')
       OR NOT (p_actor = 'user' OR p_actor LIKE 'delegate:%') THEN
        RAISE EXCEPTION 'context_invalid' USING ERRCODE = '22023';
    END IF;
    -- The one acr rule the database enforces (ADR-019's post-recovery restricted period): a restricted
    -- acr may read the principal's own data but admits no cross-user grant.
    IF p_targets <> '{}' AND p_acr IN (SELECT acr FROM app_private.restricted_acr) THEN
        RAISE EXCEPTION 'acr_restricted' USING ERRCODE = '42501';
    END IF;
    SELECT coalesce(array_agg(format('%s:%s:%s', g.grantor_id, g.category_id, g.detail_level)
                              ORDER BY g.grantor_id, g.category_id, g.detail_level), '{}')
      INTO v_grants
      FROM public.sharing_grants g
     WHERE g.grantee_id = p_principal AND g.grantor_id = ANY (p_targets)
       AND g.detail_level = p_level AND g.revoked_at IS NULL
       AND (g.expires_at IS NULL OR g.expires_at > now());
    FOREACH v_target IN ARRAY p_targets LOOP                       -- denial, not emptiness (§4.5)
        IF NOT EXISTS (SELECT 1 FROM unnest(v_grants) t WHERE t LIKE v_target::text || ':%') THEN
            RAISE EXCEPTION 'grant_not_active' USING ERRCODE = '42501';
        END IF;
    END LOOP;
    SELECT coalesce(array_agg(m.group_id::text ORDER BY m.group_id), '{}') INTO v_groups
      FROM public.split_group_members m WHERE m.user_id = p_principal AND m.left_at IS NULL;
    PERFORM app_ctx.write_context(p_principal::text, p_request_id::text, p_acr,
        array_to_string(v_grants, ','), array_to_string(v_groups, ','), p_actor, '', '', '', '', '');
END $$;
REVOKE ALL ON FUNCTION app_ctx.begin_request FROM PUBLIC;
GRANT EXECUTE ON FUNCTION app_ctx.begin_request TO pennilogic_app;

-- group sets, actor 'keyops:<job_id>'; EXECUTE granted only to pennilogic_keyops.

-- principal '', acr 'none', actor 'preauth', preauth_kind/preauth_value = the presented lookup

-- app_ctx.begin_admin_access / begin_redaction / record_admin_event: §5.5.

CREATE FUNCTION app_ctx.verified_actor() RETURNS text
LANGUAGE plpgsql SECURITY DEFINER STABLE SET search_path = pg_catalog, pg_temp AS $$
DECLARE v_mac text := current_setting('app.ctx_mac', true); k record;
BEGIN
    IF v_mac IS NULL OR current_setting('app.actor', true) IS NULL THEN RETURN NULL; END IF;
    FOR k IN SELECT key FROM app_private.context_keys
              WHERE valid_from <= now() AND (valid_to IS NULL OR valid_to > now() - interval '1 hour') LOOP
        IF encode(app_ext.hmac(app_ctx.payload(
               coalesce(current_setting('app.principal_id', true), ''),
               coalesce(current_setting('app.request_id', true), ''),
               coalesce(current_setting('app.acr', true), ''),
               coalesce(current_setting('app.grant_set', true), ''),
               coalesce(current_setting('app.group_set', true), ''),
               current_setting('app.actor', true),
               coalesce(current_setting('app.preauth_kind', true), ''),
               coalesce(current_setting('app.preauth_value', true), ''),
               coalesce(current_setting('app.preauth_account', true), ''),
               coalesce(current_setting('app.admin_event', true), ''),
               coalesce(current_setting('app.admin_subject', true), '')), k.key, 'sha256'), 'hex') = v_mac
        THEN RETURN current_setting('app.actor', true); END IF;
    END LOOP;
    RETURN NULL;
END $$;

-- Derived verifiers, all STABLE and all NULL / '{}' unless verified_actor() IS NOT NULL:
--   verified_principal()          -> app.principal_id::uuid when non-empty (raw; used only by §5.5 helpers)
--   verified_customer_principal() -> app.principal_id::uuid only when actor is 'user', 'delegate:%' or
--                                    'keyops:%' — the only principal customer policies ever compare (§4.2)
--   verified_grant_set(), verified_group_set() -> string_to_array(... , ',') for customer actors, else '{}'
--   verified_preauth_kind(), verified_preauth_value(), verified_preauth_account() -> only when actor = 'preauth'
--   verified_admin_subject()      -> app.admin_subject::uuid only when actor LIKE 'admin:%' OR 'redaction:%'
```

Binding the MAC to `pg_backend_pid()` and `transaction_timestamp()` means a captured context cannot be
replayed in another transaction, and the setter and the queries it protects must run in one transaction.
`context_keys` rows are generated in the database (`app_ext.gen_random_bytes(32)`) by
`app_ctx.rotate_context_key()`, a definer function executable only by `pennilogic_keyops` that inserts the
new row and sets `valid_to` on the previous one; the key bytes are never selected by any role, are rotated
every 90 days with a one-hour verification overlap, are readable only by `pennilogic_ctx`, and are
rotated as the first step of every restore because the key lives in the database and therefore in every
backup (§6.6). `app_private.restricted_acr` holds the `acr` values ADR-019 publishes as restricted (for
example `recovering`): a restricted `acr` reads the principal's own data but `begin_request` denies any
cross-user target for it, so ADR-019's post-recovery window is a database denial, not a code-path promise.
The residual trust is explicit and is ADR-019's design: the API process asserts the principal and `acr` it
verified; the database performs no token verification.

#### 5.3 Connection pooling

The API uses transaction-mode pooling (PgBouncer or the driver pool). Because every context value is
`SET LOCAL`, a server connection returns to the pool at `COMMIT`/`ROLLBACK` with no context; the next
transaction on that connection has no verified principal until its own `begin_request`, and a query issued
before it sees no rows. Session-mode poolers must set `server_reset_query = DISCARD ALL`. No code path may
use non-local `SET` for any `app.*` value, and the connection wrapper runs `begin_request` as the first
statement of every transaction and refuses to hand out a connection outside a transaction. The T-SEC-01
pooled-connection test opens two logical connections through one server connection in sequence and asserts
the second sees nothing of the first.

#### 5.4 Grant resolution, request-scoped caching and the revocation bound

- The grant set is resolved by the setter from `sharing_grants` on the **primary** at the start of every
  request transaction, for the target owners the request names, at the level it names.
- It is cached **only for that transaction**. There is no cross-request cache of grant resolutions in the
  API, no cache in the ReBAC engine consulted by the database, and no reuse of a context across
  transactions (the MAC forbids it).
- Revocation is the first-class operation of T-CON-04: it sets `sharing_grants.revoked_at` and removes the
  ReBAC tuple in one unit of work. The next `begin_request` on any connection sees the revocation.
- The database's contribution to the **online revocation bound** is therefore `transaction_timeout`
  (`20s` for `pennilogic_app`); T-CON-04 publishes the online bound as a number no smaller than that plus
  the API's own request handling, and the offline lease bound separately (`01-domain-model.md` §3 rule 3).
  Neither is "immediate".
- Unwrapped DEKs and IKs are cached in API process memory for at most five minutes, keyed by
  `(user_id, key_id)`, invalidated on any key-state event and on erasure, never written to disk, and
  zeroised on eviction. The custodian records every unwrap; the API additionally records, in the
  foundational `audit.event` of every use of a key on behalf of a principal other than its owner, the
  admitting policy identifier, which ADR-020's relay projects into the subject-visible `access_events`
  entries (§1.2).

#### 5.5 Administrative and redaction access contexts (form owned here, semantics owned by ADR-020)

ADR-020 binds its administrative path to this record's setter and predicate form. The concrete object
names below (`admin_api_owner`, `redaction_service`, `audit.event`, `audit.confirmation_status`) are the
names ADR-020's draft uses and are ADR-020's to fix; this record binds to their roles — the `NOLOGIN`,
`NOBYPASSRLS` definer owner that owns no customer table, the redaction identity in the customer zone, the
foundational audit event, and the chain-confirmed unmask-grant status function. Administrative roles
never execute `begin_request`, never obtain `app.principal_id` and never satisfy `owner_rows` or
`grant_mediated_*`: an administrative role that could assume the customer-subject context would be
impersonation. Instead, two further setters mint a distinct, MAC-bound context:

- `app_ctx.record_admin_event(p_audit_event_id uuid)` — `EXECUTE` only for `admin_api_owner`, called by
  ADR-020's audit insert path (a `BEFORE INSERT` trigger on `audit.event` or ADR-020's insert function) in
  the same statement that writes the event. It appends the id to the transaction-local key
  `app.recorded_admin_events` and re-signs that list as `app.recorded_admin_events_mac` under `K_ctx`
  together with `pg_backend_pid()` and `transaction_timestamp()`. The binding is therefore **structural**:
  membership in a list only the insert path can extend, valid in this transaction only. It does not depend
  on tuple visibility, so an event inserted inside a `SAVEPOINT` or a PL/pgSQL `EXCEPTION` block (whose
  `xmin` is a subtransaction id) is admitted, and no XID-wraparound coincidence can admit a historical row.
  An `xmin` comparison may be kept as a secondary sanity check, never as the binding.
- `app_ctx.begin_admin_access(p_audit_event_id uuid, p_request_id uuid, p_acr text)` — `EXECUTE` only for
  `admin_api_owner` (ADR-020's `NOLOGIN`, `NOBYPASSRLS` definer owner). It raises `42501` unless
  `p_audit_event_id` is present in the verified `app.recorded_admin_events` of this transaction, so a read
  without its recorded event is impossible; it then writes, through `write_context` (§5.2), principal `''`,
  `app.acr = p_acr` (the administrative `acr` ADR-020 verified — an explicit parameter, never inferred),
  `app.admin_event` (the event id), `app.admin_subject` (the subject the recorded event names, read from
  the event row) and `app.actor = 'admin:<audit_event_id>'`.
- `app_ctx.begin_redaction(p_unmask_grant uuid, p_request_id uuid, p_acr text)` — `EXECUTE` only for
  `redaction_service`. It raises `42501` unless ADR-020's `audit.confirmation_status(p_unmask_grant)`
  reports an active, chain-confirmed unmask grant; it writes `app.admin_event` and `app.admin_subject`
  from the grant and `app.actor = 'redaction:<unmask_grant>'`. The DEK unwrap the redaction service then
  performs is recorded with the grant identifier (ADR-020's unmask path); no administrative identity holds unwrap
  permission.

`app.admin_event` and `app.admin_subject` are fields of the single normative `v2` payload of §5.1, so a
`set_config('app.admin_subject', …)` after one legitimately recorded event invalidates the MAC and admits
nothing; `app_ctx.verified_admin_subject()` returns `app.admin_subject` only when the MAC verifies **and**
the actor is `admin:` or `redaction:`. The policy family is **`admin_recorded_access`** — `FOR SELECT TO
admin_api_owner, redaction_service USING (owner_id = (SELECT app_ctx.verified_admin_subject()))` on the
tables ADR-020 exposes, with the compared column `owner_id` (or the table's owner column named in §1.2).
Which tables and columns the masked views expose, the justification, four-eyes, redaction and transparency
semantics, and the audit and unmask functions are ADR-020's; this record fixes only that the context is
recorded-event-bound, MAC-bound, transaction-local, never a customer context and never a bypass named in
§4.4.

### 6. Key lifecycle

#### 6.1 Key classes, custody and cryptoperiods

Cryptoperiods follow NIST SP 800-57 Part 1 guidance (symmetric data-encryption and key-wrapping keys:
originator-usage period of at most two years) and are shortened where the key is shared across users.

| Class | Scope | Custody | Generation | Cryptoperiod (originator use) | Also rotated on |
|---|---|---|---|---|---|
| **KEK** | platform (versioned) | KEK custodian (§6.1.1); never exported in plaintext | inside the custodian | 12 months | suspected compromise, custodian migration |
| **DEK** | per user | wrapped in `user_keys`; plaintext only in API memory | API CSPRNG or custodian data-key operation | 24 months or 2^28 encryptions | KEK compromise (forces DEK rotation), suspected DEK exposure; destroyed on erasure |
| **IK** (per-tenant index key) | per user | wrapped in `user_keys`, `purpose = IK` | independent CSPRNG | jointly with the DEK (24 months) | index-key compromise; destroyed on erasure |
| **GIK** (global identity index key) | platform | custodian-wrapped, unwrapped into API memory | custodian | 12 months | compromise; indexes `channels.value` only (ADR-019); rotation rewrites the whole `channels` index in one transaction (§6.2) |
| **CK** (channel key) | platform | custodian-wrapped, unwrapped into API memory | custodian | 12 months | compromise; encrypts `channels.value` (§1.2) so the pre-authentication path never unwraps an account DEK; rotation re-encrypts the small `channels` table in one transaction |
| **K_abuse** (trial-abuse fingerprint key) | platform | custodian-wrapped | custodian | the abuse window the T-CMP-04 profile publishes (fingerprints older than the window are deleted, and the key is rotated when the window rolls) | compromise; keys `trial_fingerprints` only (§1.2) |
| **K_dedupe** (server fingerprint key) | platform (versioned; `transactions.dedupe_key_version`) | custodian-wrapped | custodian | 24 months | compromise |
| **K_ctx** (context MAC key) | database-internal | `app_private.context_keys` | `gen_random_bytes(32)` in the database | 90 days | compromise |
| **K_install** (device raw-message digest key) | per Android install | Android Keystore HMAC key, StrongBox when available, non-exportable | on first run, in hardware | lifetime of the install; no rotation, replaced by reinstall | uninstall, Keystore reset |
| Backup encryption key | platform | custodian | custodian | per T-PLT-02 | per T-PLT-02 |

**6.1.1 KEK custody requirements (vendor-neutral).** The custodian must: keep the KEK non-exportable and
perform wrap/unwrap on request; support key versions, scheduled and on-demand rotation and destruction
with an attestable record; log every wrap and unwrap with the caller identity and expose the log to the
alerting stack; be administratively separate from the database hosts and their backups; be reachable
under an availability objective at least as strict as the API's; and hold the KEK inside India for
production data where the counsel-reviewed jurisdiction profile requires it (`T-CMP-04`). HSM-backed
managed key services and self-hosted vaults with a sealed root of trust both qualify; a software
custodian with a file-held root qualifies only for environments that never hold real data. **Selecting
the production custodian is a platform decision (ADR-022 runtime platform, T-PLT-03) with explicit owner
approval for any spend; this record creates no purchase and names no vendor.**

#### 6.2 Rotation state machine and overlap

Every KEK version, DEK, IK, GIK and fingerprint key row carries a state:

```
ACTIVE ──rotation starts──▶ DECRYPT_ONLY ──retirement proof (§6.4)──▶ RETIRED
  │                              │
  └─────── erasure ──────────────┴──────────────────────────────────▶ DESTROYED_BY_ERASURE
```

- Exactly one key per (scope, purpose) is `ACTIVE`; writers always encrypt with it. Rotation first creates
  the new `ACTIVE` key, then moves the old key to `DECRYPT_ONLY`. Readers select the key the ciphertext
  header names, so old and new ciphertext coexist and **there is no read gap at any point**.
- **Overlap** lasts until the retirement proof exists: for a DEK/IK until re-encryption is complete *and*
  the backup retention window has elapsed (§6.4, §6.6); for a KEK version until zero wrapped rows reference
  it and the same window has elapsed; for the per-tenant IK indexes, the API queries both `HMAC(old)` and
  `HMAC(new)` until the rebuild is complete; for `K_dedupe`, lookups compute both versions until every row
  carries the new `dedupe_key_version`. The **GIK and CK have no dual-lookup overlap**: `channels` is small,
  so a rotation rewrites every `value_bidx` (stamping `value_bidx_version`) and, for CK, every ciphertext in
  **one transaction**, which keeps the partial unique index `(type, value_bidx) WHERE verified_at IS NOT
  NULL` authoritative — only one index version ever exists in the table, so an old verified row and a new
  verification can never live in different index spaces — and the old key becomes `DECRYPT_ONLY` only for
  the backup window. Channel verification writes are paused for the duration of that one transaction.
- A `compromised` flag may be set on a `DECRYPT_ONLY` key; it never returns to `ACTIVE`.
- Scheduled rotation is spread across the cryptoperiod (users are due at `created_at + 24 months`),
  so steady-state load is a small daily fraction of the population; emergency rotation runs the whole
  population at maximum throughput (§6.5).
- Rotation events are journaled (§6.6) with old and new key identifiers, never key material in plaintext.

#### 6.3 Resumable re-encryption

- A rotation is a `key_rotation_jobs` row (`job_id`, key class, subject, `old_key_id`, `new_key_id`,
  `priority`, `state`) with one `key_rotation_progress` row per (table, column group) holding a
  primary-key **watermark** (UUIDv7 keys are time-ordered).
- The worker (`pennilogic_keyops`, context from `app_ctx.begin_keyops` per owner, §5.2) processes
  batches above the watermark in one transaction each: read rows whose header names `old_key_id`, decrypt
  with the old key, re-encrypt under the new key with a fresh nonce, recompute blind indexes when the IK
  rotates, `UPDATE` only ciphertext, header and index columns, advance the watermark in the same
  transaction.
- **Idempotency comes from the header.** A row already naming `new_key_id` is skipped, so a crash and
  restart from the watermark never re-encrypts a row twice, and a restore of an older progress row only
  repeats work harmlessly.
- New writes during rotation use the new `ACTIVE` key; completion requires a **zero-reference scan** of
  every encrypted column for `old_key_id` performed after the DEK cache lifetime (five minutes) has
  passed since the state change, so no in-flight writer can leave a late row behind.
- A progress row not advanced for 15 minutes raises `crypto.rotation_stalled`; a job in `FAILED` leaves the
  old key `DECRYPT_ONLY` forever until an operator resumes it. **Rotation failure never retires a key and
  never leaves ciphertext without a usable, authorized key.**
- Rows whose key was destroyed by erasure are skipped and counted, never re-keyed (T-SEC-06).

#### 6.4 Retirement proof

A key moves to `RETIRED` (wrapped material destroyed in `user_keys` and the custodian) only when a signed
retirement record exists in the key journal containing: the key identifier and class; the zero-reference
scan result per table and column group with its timestamp; proof that the timestamp of re-encryption
completion plus the backup retention period (T-PLT-02) is in the past, so no restorable backup contains
ciphertext under the key; a successful decrypt of the successor key's `canary`; and the approver or
automation identity. Any failing element **denies retirement** and raises `crypto.retirement_refused`. An
early retirement (before the backup window) is only permitted under a recorded incident decision with
two approvers (§6.5).

#### 6.5 Emergency rotation

Triggered by a recorded suspicion of compromise of any key class. It differs from the scheduled path in
speed and scope, not mechanism: the affected key is flagged `compromised` and moved to `DECRYPT_ONLY`
within minutes; a KEK compromise rewraps every wrapped key (minutes) **and** forces DEK and IK rotation for
every user, because a compromised KEK plus a dump exposes every DEK; the job runs at `priority =
EMERGENCY` across all shards with no cryptoperiod spreading and must complete materially faster than the
scheduled path (the drill records the ratio). Backups taken before the emergency rotation completed are
treated as compromised material: under the incident decision they are destroyed ahead of schedule or
quarantined so that any restore from them immediately re-runs rotation before serving traffic. Signals:
`crypto.emergency_rotation_active`, rate of `crypto.rotation_progress_ratio`.

#### 6.6 Backups and restore

- Backups (T-PLT-02) contain ciphertext, wrapped keys and constrained columns; never a plaintext DEK, IK,
  GIK, CK, fingerprint key or the KEK. They are encrypted under the backup key. They do contain
  `app_private.context_keys`, which is why §6.6 rotates `K_ctx` first on restore and why no
  non-production copy may include `app_private`.
- The **key journal** is an append-only store outside the database backup set with the same properties
  as the erasure tombstone journal (T-SEC-07): independent retention, write-once policy, restricted access.
  It records every key creation, state transition, retirement proof, destruction and approver identity
  **by identifier only — never wrapped or plaintext key material**. A journal copy is therefore useless
  to an attacker and cannot resurrect a destroyed key.
- **Restore replays the key journal before erasure tombstones and before readiness**: `K_ctx` is rotated
  first (`rotate_context_key()`), so a context key carried in the backup can never mint a valid context;
  key rows the journal marks `RETIRED` or `DESTROYED_BY_ERASURE` are re-destroyed; a key the journal marks
  `DECRYPT_ONLY` is never promoted back to `ACTIVE`; where the journal's `ACTIVE` key for a scope is
  **absent from the restored backup** (a backup older than a rotation), the restore mints a **fresh**
  `ACTIVE` key, journals its creation, records the absent key as unrecoverable and starts a rotation job
  from the surviving `DECRYPT_ONLY` key — no restorable row needs the absent key, because every row
  encrypted under it postdates the backup. Retired material therefore never becomes usable again after a
  restore, and a backup taken during a rotation still decrypts every row because the retirement rule of
  §6.4 guarantees the old key is still `DECRYPT_ONLY`.
- A resumed rotation after restore continues from the restored watermark (§6.3).
- Readiness requires zero outstanding tombstones, zero key rows contradicting the journal, a rotated
  `K_ctx` and a successful canary decrypt for a sample of users; the journal being unavailable fails the
  restore (T-SEC-07).

#### 6.7 Erasure interplay and residue (boundary with ADR-006 and ADR-021)

Erasure destroys the user's DEK and IK rows immediately, writes the journal event and the T-SEC-07
tombstone, and makes every encrypted and per-tenant blind-indexed value of that user unreadable through
the live system. **Its completeness bound is the backup retention window**: `user_keys.wrapped_key` and
the ciphertext persist in backups until T-PLT-02 retention elapses, and until then a party holding a
pre-erasure backup **and** custodian unwrap rights on that KEK version could recover them; the journal
holds no material (§6.6), so it adds no window. The record publishes that bound to T-CMP-04 and T-SEC-02
as the erasure-completeness period, and §9 lists it as residue; ADR-021 inherits it as a premise.

Values under a **platform** key are not protected by DEK destruction, so erasure (T-SEC-02) physically
clears them: the `channels` rows of the subject (CK ciphertext and GIK index values), push tokens, and any
other platform-scoped value §1.2 marks as cleared on erasure; `trial_fingerprints` link to no subject and
are governed by their own retention (§1.2); `dedupe_key` values remain with the constrained ledger rows.

**Relationship residue (MVP single-user rule).** Constrained ledger rows survive erasure under the opaque
`owner_id`; the pseudonymity argument of §1.3 holds only if no surviving row joins that identifier to an
identified counterparty. Erasure therefore also: revokes and tombstones the subject's `sharing_grants` in
both directions; ends every split-group membership — the link is severed here, and ADR-021 decides only
the shape of the placeholder that preserves other members' balances; rotates the erased identifier to an
erasure pseudonym in `access_events.viewer_id` (the counterparty keeps "an erased account viewed this" and
nothing more) and deletes the subject's own `access_events`, `duplicate_links` and `period_aggregates`
(derived data, not ledger facts). The T-SEC-07 restore replay repeats every step. What still survives —
amounts, timestamps, opaque account and category identifiers under an unlinkable `owner_id`, and the
statutory records counsel requires (T-CMP-04) — is published to the T-CMP-04 profile as what erasure does
not remove and why. Whether a shared row is rewrapped to a surviving grantee's key or left unreadable is
ADR-021's decision, implemented by T-SEC-02 and T-SEC-06; this record only requires that any such rewrap
uses the envelope, header and AAD rules of §2 and is journaled like any other key event.

### 7. Deduplication artefacts

Three artefacts exist. They have different names, constructions, keys, locations and retention, and no
contract may conflate them (T-CON-02, T-CON-15).

#### 7.1 `raw_event_digest` — device-local, never leaves the device

- **Construction.** `HMAC-SHA-256(K_install, canonical(sender_id || normalised_body || channel))`, computed
  inside Android Keystore (the HMAC key is generated in and never leaves hardware; StrongBox when
  available). Canonicalisation strips whitespace runs and case-folds; it does not remove digits, because
  two genuine messages differing only in amount must not collide.
- **Purpose.** Exact deduplication of the *same raw message* delivered twice (dual SIM, restore, listener
  re-delivery) before parsing, and linking a parsed transaction to its raw event for parser regression
  debugging.
- **Location and retention.** Only the column `raw_events.raw_digest` of the on-device SQLCipher store.
  The digest lives no longer than the raw-event store's retention published by the Android capture ticket;
  it may outlive the message body but never the install. `allowBackup=false` and the backup exclusion
  rules keep the store out of Android cloud backup. A reinstall creates a new `K_install`, so exact
  raw-message deduplication restarts and the server's structured and fuzzy stages (§7.2–§7.3) carry the
  duplicate protection across reinstalls.
- **Structurally absent** from every API, sync and export schema: the capture, sync and export contracts
  reference `source_event_id` (T-CON-15) and contain no `raw_hash`, `message_digest` or any raw-derived
  field; a planted field fails schema verification (T-CON-02). `source_event_id` is an opaque UUID
  generated before first enqueue and is not derived from message content.

#### 7.2 `transactions.dedupe_key` — server structured dedupe key

- **Construction.** `HMAC-SHA-256(K_dedupe[v], canonical(owner_id || account_id || amount_minor ||
  currency || direction || occurred_at truncated to the minute in UTC))`, computed by the server at
  ingest from the structured candidate after the account has been resolved (§3.3). When the account
  cannot be resolved, the canonical form carries the sentinel `account:unresolved` and the candidate enters
  review; the key is fixed when the transaction is posted after clarification and never changes afterwards
  except by key rotation. It is **output-only**: a client cannot supply or override it (T-CON-02).
  `dedupe_key_version` names `v`.
- **Not raw text.** No input is or derives from message text; the merchant is not an input because
  channels disagree on it (§7.3 handles it). Changing the raw message while keeping the structured fields
  leaves the key unchanged, which the preimage test asserts (§12).
- **Key class and rotation.** `K_dedupe` is a platform key (§6.1) rotated every 24 months or on
  compromise; because every input is a constrained column, rotation is a pure recompute in batches with no
  decryption and no backup dependency, and lookups compute both versions during the rebuild.
- **What a dump plus the shipped parser templates can recover.** The constrained inputs are already
  plaintext in a dump, so the key reveals nothing beyond them; without `K_dedupe` an attacker cannot
  confirm a guessed tuple against a key, and with it learns only what the plaintext columns already say.
  Parser templates map raw text to structured fields; they cannot be run backwards against the key to
  recover a message, because no message-derived value enters it. The merchant, description, note, account
  mask and raw text remain unrecoverable.
- **Semantics.** Equal keys within an owner mark a **duplicate candidate**, never an automatic merge and
  never a `UNIQUE` violation, because two genuine identical charges (two coffees in one minute) legitimately
  collide. The key is the first, cheap stage of §7.3.

#### 7.3 Fuzzy duplicate-candidate match and the reversible link

- **Candidate window.** For an incoming `TransactionCandidate` (T-CON-15) the server selects existing rows
  of the same owner with equal `amount_minor`, `currency` and `direction`, `occurred_at` within a
  source-pair window (published with the confidence bands of T-CON-10; notification-vs-SMS is minutes,
  import-vs-SMS is days), and an equal or unresolved account. Selection uses constrained columns only.
- **Comparison.** Over that small set the server compares `merchant_bidx` equality (strong signal),
  `external_ref` equality (decisive), and, after decrypting the candidates in memory, normalised merchant
  similarity. Nothing text-like is searched in the database.
- **Outcome.** A match above the confidence threshold creates a **reversible link**: a `duplicate_links`
  row (`surviving_id`, `linked_id`, `reason`, `confidence`, `decided_by`) plus an audit record. Source
  precedence (`AA > IMPORT > SMS > NOTIFICATION > MANUAL-guess`) decides which record survives and which
  fields it enriches; a user-confirmed value always wins. Enrichment and a "What was this?" answer write
  only the mutable descriptive columns §4.1 grants (`description`, `merchant_display`/`merchant_bidx`,
  `external_ref`/`external_ref_bidx`, `source_confidence`, `category_id`, `needs_review`, `status`,
  `note`) and never a ledger fact (`owner_id`, `occurred_at`, `account_id`, amounts, currency, `source`,
  `source_event_id`, `dedupe_key`); every enrichment records its provenance in the dedup outcome and the
  audit stream so the value's origin stays reconstructible. **Neither record is deleted.** If the linked
  candidate had not been posted, its posting is suppressed; if both had already posted entries, the merge
  posts a reversing transaction for the non-surviving one (ADR-002), never an `UPDATE` or `DELETE` of an
  entry.
- **Unmerge.** Reversing a link sets `reversed_at`/`reversed_by`, posts the suppressed candidate (or a
  re-posting transaction), and writes the audit record; the false-merge test of two genuine identical
  charges asserts both remain and both balances are correct afterwards. Below the threshold the candidate
  enters the clarification inbox ("What was this?") with the dedup-outcome shape of T-CON-10.

#### 7.4 Reconciliation of the three artefacts

| Artefact | Where | Key | Inputs | Exactness | Retention |
|---|---|---|---|---|---|
| `raw_event_digest` | device only | `K_install` (Keystore) | raw sender and body | exact | raw-event store retention; dies with the install |
| `transactions.dedupe_key` | server column | `K_dedupe[v]` (platform) | canonical structured fields | exact on structure | life of the row; recomputed on key rotation |
| fuzzy candidate match | server pipeline, `duplicate_links` | none (decision record) | constrained window + decrypted merchant | probabilistic, reversible | life of the link; reversal is a new fact |

The device stops exact raw duplicates; the server stops exact structured duplicates and reconciles the
rest fuzzily and reversibly. No artefact is derived from another and no raw-derived value reaches the
server.

**The ADR-015 `Idempotency-Key` is a fourth, distinct thing — a request-replay artefact, not a
deduplication artefact.** A replayed request (same key, same payload) is served from the idempotency store
and creates no candidate, evaluates no `dedupe_key` and mints no link; a re-capture with a new key and a
new `source_event_id` (a reinstall re-parsing the same message, a re-typed manual entry) enters §7.2 and
§7.3 exactly once. Manual and import sources receive a `dedupe_key` like every other source. T-CON-15
keeps the four identifiers — request idempotency key, device-local raw digest, server fingerprint,
`source_event_id` — in separate components.

**Every deduplication outcome is shown, never silently applied** (ADR-015). A link with
`decided_by = system` is emitted in the T-CON-10 dedup outcome of the request that created it and appears
in the owner's sync feed as the suppressed record with `status = suppressed_by_link`, the link identifier
and an unmerge affordance, so a false-positive suppression of a legitimate charge is visible in the product,
not only reversible in the database. Below-threshold candidates reach the clarification inbox as §7.3 states.

#### 7.5 Clarification of ADR-004

ADR-004 says "A hash of the raw message is stored for deduplication; the text itself never is." **This
record supersedes that sentence, and only that sentence, of ADR-004:** the hash is `raw_event_digest` of
§7.1, keyed per install, held only in the device-local raw-event store, and structurally absent from every
server-facing schema. The server never receives, stores or computes a raw-message hash; its deduplication
uses §7.2 and §7.3 over structured fields. ADR-004's decision — raw message content never leaves the
device and the API has no field that could carry it — is preserved and extended to raw-derived digests, as
ADR-004's own pending clarification required. Because a `supersedes` link in this layout replaces a whole
record and would mark ADR-004 `SUPERSEDED` (`adr/LAYOUT.md`), and ADR-004 remains in force as a whole,
the header link is `null` and the replacement of the single sentence is recorded here. The restriction in
ADR-004 that no capture or sync contract may add a raw-derived digest until this record is accepted becomes
permanent.

### 8. Migration path

No environment holds real data before T-SEC-01 lands (`compliance/01-regulatory-landscape.md` O-12), so
the primary path is greenfield and there is no plaintext-to-ciphertext conversion of production data.

1. Ledger schema with every constraint, foreign key, `ENABLE`/`FORCE ROW LEVEL SECURITY` and default deny
   (historically `api#2`), through the migration runner (T-MIG-01).
2. Roles, `app_private`, `app_ctx`, `user_keys`, `key_rotation_*`, the key journal integration and the
   policies of §4.2 (T-SEC-01). Descriptive columns are created as `BYTEA` ciphertext and blind-index
   columns from their first migration; no plaintext descriptive column ever exists in a database that
   holds real data.
3. Where a development or staging database already holds synthetic plaintext, T-SEC-01 migrates one column
   group at a time: add ciphertext and index columns, dual-write, backfill under `pennilogic_keyops`,
   verify by decrypt-and-compare, switch reads, drop the plaintext column. Ciphertext is never discarded
   during the window; rollback returns to dual-read.
4. `sharing_grants`, `access_events` and `period_aggregates` with their policies land with T-SEC-01 so
   T-CON-04 can bind to `grant_mediated_read` and `grant_mediated_aggregate_read` before any sharing code.
5. Rotation (T-SEC-06) ships disabled and is enabled per key class after a non-production rehearsal;
   backup and restore orchestration (T-SEC-07, T-PLT-02) adds the journal replay before any environment
   with real data is restorable.

**No ledger constraint is weakened.** No `CHECK`, `FOREIGN KEY`, `UNIQUE`, `NOT NULL` or trigger on
`entries`, `split_shares`, `split_expenses` or `settlements` is dropped or relaxed by any step; the
migration lint fails a migration that does, and the T-SEC-01 constraint-retention test inserts an
unbalanced transaction after encryption is enabled and expects rejection. No runtime role can `UPDATE` or
`DELETE` a row of `entries`, `split_shares` or `settlements`. Apart from the mutable descriptive metadata
columns listed in §4.1 (the owner's edits, source-precedence enrichment and clarification answers, each with
recorded provenance) and the candidate-phase fingerprint of §7.2, re-encryption and the `K_dedupe`
fingerprint rebuild are the only in-place `UPDATE`s permitted on any table that carries ledger facts; they
touch ciphertext, header, index and fingerprint columns only, are restricted by column-level grants to
`pennilogic_keyops`, leave every plaintext fact unchanged and are recorded per batch, so the append-only
meaning of ADR-002 is intact.

### 9. What each choice leaks and what it does not protect against

| Choice | Leaks to a reader with database or dump access | Does not protect against |
|---|---|---|
| Plaintext ledger money and timestamps | Every amount, currency, direction, account identifier, time and rhythm of activity per opaque owner; counts of shared relationships. | A superuser session, a stolen dump or a stolen volume without its storage key; an insider with break-glass access (governed, recorded, T-PLT-05). |
| Application-encrypted descriptive columns | Ciphertext length (rounded by padding to 16-byte multiples in the API), write times. | Compromise of the API process, which holds unwrapped DEKs in memory for up to five minutes; a compromised KEK plus a dump (§6.5). |
| Per-tenant blind index | Within-tenant equality and frequency of merchants, masks and provider references (§3.4). | Inference from amounts and timestamps, which are plaintext anyway. |
| Global identity blind index | Which opaque accounts share an e-mail or phone value (`channels.value_bidx`), and equality of a guessed contact if the GIK is exposed. | A GIK compromise: the index is then a deterministic map of contacts; rotation re-randomises it. |
| Forced RLS with MAC-bound context | Nothing in itself. Residual: foreign-key checks run with the table owner's rights, so an insert naming a guessed foreign row can reveal by its error class whether that exact `(id, owner_id)` pair exists; opaque UUIDv7 identifiers and the composite keys of §1.2 make the probe impractical. An own-data query issued without a context returns no rows rather than an error; the connection wrapper of §5.3 makes that path unreachable and `rls_missing_context_admits_nothing` asserts it. | An API that verifies the wrong principal or `acr` (the setter trusts the API's assertion, which is ADR-019's design, §5.2); a superuser; a hostile migration reviewed and merged in violation of §4.4. |
| Grant-mediated read | The grantee sees admitted rows' amounts, dates, descriptions, merchants and opaque account identifiers (§4.3); the data subject sees each access (T-TRU-04). | A grantee who screenshots or remembers what was legitimately shared; the offline lease bound (T-CON-04) governs cached copies. |
| Server structured dedupe key | Nothing beyond the constrained inputs (§7.2). | — |
| Device-local raw digest | Nothing off-device; on a rooted device, that two raw messages were equal. | A compromised device, which already holds the raw store (T-07 in the security architecture). |
| Envelope encryption and crypto-shredding | Whether a user has been erased (destroyed key rows and tombstones exist). **Residue after erasure:** the constrained ledger rows (amounts, timestamps, opaque account and category identifiers) under an unlinkable `owner_id`; `dedupe_key` values; `trial_fingerprints` (no subject link); and, until T-PLT-02 backup retention elapses, the wrapped keys and ciphertext inside backups — the published erasure-completeness bound (§6.7). | A party holding a pre-erasure backup **and** custodian unwrap rights on that KEK version within the retention window; statutory records counsel requires to survive erasure (T-CMP-04), which are classified and retained separately. |

### 13. Options considered and rejected

| Option | Why rejected |
|---|---|
| Encrypt amounts and constrain in the application | Randomised ciphertext cannot be summed or constrained; the zero-sum and share-sum invariants would become application promises, which ADR-002 forbids. |
| Deterministic encryption for searchable columns | Leaks equality and frequency like a blind index but *also* lets ciphertext be transplanted and offers no separate index key to rotate; no AAD binding. |
| Order-preserving, prefix or tokenised searchable encryption | Leaks ordering, vocabulary and co-occurrence; the product needs equality only (§3.3). |
| Plaintext `merchant_id` foreign key per transaction | Readable merchant per row and cross-user grouping for anyone with database access. |
| One global blind-index key for merchants | Cross-user frequency analysis and a single key whose exposure maps every user's merchants. |
| Database-side encryption (`pgcrypto` columns, transparent data encryption only) | Keys or plaintext would exist inside the database; TDE alone does nothing against database-level access. |
| End-to-end encryption | Incompatible with web access, server-side matching and grant-mediated reads (`02-security-architecture.md` §4.3). |
| ReBAC engine as the only enforcement of cross-user reads | Application-only enforcement; a bug or bypass in one code path exposes rows. The engine remains the application authority and is fed from the same rows. |
| Per-tenant schemas or databases | Sharing across tenants becomes cross-database; operational cost; no better isolation than forced RLS with a MAC-bound context. |
| Plain GUC session variables trusted by policies | Any session can set a custom GUC, so the client role could forge a principal; hence the MAC-bound context. |
| Temporary-table or context-table request state | Forgeable by the application role or heavier per request than a transaction-local MAC. |
| Wall-clock expiry on the context | Races long statements and still allows replay inside the window; binding to `transaction_timestamp()` and `pg_backend_pid()` is exact. |
| `USING (true)` policy for batch roles | A bypass by another name; the key-operations role acts per owner through its own setter instead. |
| Storing a raw-message hash on the server | A raw-derived value at the boundary ADR-004 protects; T-CON-15 already rejects it. |
| Automatic merge (delete) of fuzzy duplicates | Destroys a legitimate charge on a false positive and breaks the append-only ledger. |
| Immediate destruction of a rotated-out key | Would make backups taken before completion unrestorable; retirement waits for the backup window (§6.4). |
