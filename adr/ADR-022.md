## ADR-022 — AI egress, runtime platform and Mode C custom endpoints
**Status:** ACCEPTED · 2026-10-05

**Effective on protected merge, not on local preparation.** This is the source decision for
[PenniLogic/docs#42](https://github.com/PenniLogic/docs/issues/42), not evidence of deployed
controls, independent approval or completed implementation tickets. The runtime choice below
uses the owner's delegated autonomous technical decision authority of 2026-10-05; it does not
claim a separate owner endorsement of this particular topology.

**Decision.** Select **R4: self-managed Linux hosts, Docker Engine/Compose, isolated network
namespaces and host-owned nftables**, with an authenticated, destination-aware forward proxy as
the **only internet path for every AI mode**. This is a **future runtime target**, not a new
deployment. Existing development containers do not yet implement it. No cloud vendor, account,
machine, region purchase, paid service, inference or production credential is authorized here.
Real-data deployment remains gated by the residency, key-custody and operational requirements
below. Kubernetes `NetworkPolicy` is not part of this non-Kubernetes decision.

Every remote AI call follows **client -> authenticated core API -> AI gateway -> egress proxy
-> approved destination**, including BYOK, custom endpoints, routing retries and validation
probes. Client-direct Mode C and a base address in an inference request are prohibited. The
server owns authorization, quota, destination approval, audit, address validation, pinning,
revocation and kill switches. Local, on-device parsing under ADR-003 is not provider egress.
For scheduled bodyless revalidation, an authenticated server maintenance trigger replaces the
client; it never fabricates a live customer request or an ADR-019 delegation.
Arbitrary custom destinations remain **OFF** until registration, approval and pinning are
implemented and **all** application and real-runtime gates pass. Provider traffic also starts
OFF with an empty allowlist. Source tests in this repository cannot enable either.

### 2. Decisions binding every AI mode

#### 2.1 Gateway-only egress, identity and quota

The gateway has no public address or client-facing listener. Core API calls carry ADR-019
`wl+jwt` plus the API-minted `dlg+jwt`, with its subject, request binding, audience, type, replay,
expiry and live-session checks. The AI service holds its workload signing key, **not** the API
delegation-minting key. A customer access token alone never authenticates to the gateway or
proxy. [PenniLogic/api#87](https://github.com/PenniLogic/api/issues/87) owns the existing
assistant delegation path; this record creates no replacement ticket.

The `EgressClient` is the gateway's sole provider transport. LiteLLM may be an in-process
translation/routing library only if **all** its calls use this transport. A separately dialling
LiteLLM Proxy, SDK fallback, telemetry exporter, remote tokenizer/download, URL-fetching tool
or proxy environment override is not an exception. Dependencies/models are prepared at build
time; private telemetry uses an inventoried internal collector. Source import checks are useful
but the namespace tests must also try raw sockets and a deliberately bypassed validator.

Mode A uses a server-held provider credential; Mode B a user's encrypted credential at an
approved code-managed provider; Mode C a registered custom destination with an optional
user-owned credential. Keys are enrolled under fresh ADR-019 step-up, envelope-encrypted under
ADR-018, suspended on recovery and never returned in plaintext. The client may transiently
enter its own host/key during enrollment and display its own registration, but must not persist
a key, receive a provider routing URL or dial a provider. This is not a prohibition on the
separate host-registration form.

ADR-023 remains the quota authority: all modes consume the `requests` dimension; Mode A
consumes `tokens`, whereas Modes B/C record tokens uncharged. Admission, atomic reservation,
first-delivered-byte settlement, release, deadline and model checks remain server-side. A
missing/suspended key, denied destination, exhausted quota or unavailable state is a refusal,
**never fallback to Mode A or another unapproved model**. Retry/redirect attempts remain inside
the original request's bounded cost, deadline and audit envelope.

Outbound headers are constructed, not copied from the caller. The base set is `Host`,
`Content-Type`, `Accept`, `Content-Length`, `User-Agent`; provider additions come from that
entry's reviewed header set. Custom credentials use exactly one registered `CredentialHeader`:
`authorization_bearer` -> `Authorization: Bearer <key>`, `x_api_key` -> `x-api-key`, or `api_key`
-> `api-key`. Reject control bytes in keys. No cookies, workload/delegation/capability tokens,
trace baggage, forwarded headers or internal identifiers reach a destination. The user agent
is a fixed product string without account, device or request identifiers.

Payloads contain only minimized question text, tokenized account/person references, redacted
merchant strings, categories, necessary amounts/dates and deterministic tool results. Even a
question quoting an identifier is redacted before egress. Raw SMS/email, raw-derived digests,
account/card/loan numbers, government identifiers, VPAs, counterparty/household names and
phone/contact details, device/account/session/tenant identifiers, credentials and unredacted
memos are forbidden. T-AI-05 enforces this at the final transport boundary, not just in logs.
Mode A may use shared data within its existing authorized
grant; Modes B/C additionally require the other principal's **per-grant AI-egress permission,
default off**. Recheck live grants before emission; a sharing grant is not blanket permission
to transfer someone else's data to a user-controlled endpoint.

#### 2.2 Destination classes and the authenticating proxy

| Class | Identity and approval | Egress authorization |
|---|---|---|
| `code_managed_provider` (Modes A/B) | Reviewed provider ID mapped to exact hosts, region, models/features, paths, credential audience and allowed headers; unexpired `retention_evidence_ref` from T-AI-07 and `processor_agreement_ref` from T-CMP-04 | Empty until evidence is accepted. Console can disable/configure an existing entry, never add a host. Fresh public resolution and one request-scoped address pin |
| `runtime_registered_custom` (Mode C) | Opaque destination ID owned by one account; step-up registration, TLS validation, consent, approved lifecycle state and exact address-set pin | No operator-created registrations or promotion into provider class. Inference uses the ID, not a host or base URL |

The proxy is mandatory for **both** classes. It does not accept unauthenticated general-purpose
CONNECT. The gateway presents its workload identity and an **API-issued**, single-use
`egress+jwt` capability with a separate key class and audience `pennilogic-ai-egress`.
Required bindings are `sub`, `azp = ai-service`, `actor_kind`, originating request/maintenance
trigger digest, admission ID, destination ID/class/version, operation (`inference` or
`tls_probe`), hop, policy version, unique `jti`, issued time and expiry of at most 120 seconds.
A `user_request` capability is further bounded by the originating delegation and live request
deadline. `scheduled_revalidation` may authorize **only** a TLS probe of an existing
owner-bound registration, under an API-authorized maintenance job, never inference, new
registration, re-pinning, activation or customer delegation. The proxy independently verifies
that job and the registration's current authorization. Inference admission references the
ADR-023 reservation; probe admission references a bounded registration/maintenance rate budget,
not an invented inference reservation. Neither model output nor the gateway may mint or widen
this capability. Type/key class, presenter, issued request/job membership, operation and
admission are checked before opening a connection; failure or unverifiable state is denial.

Single use is coordinated, not checked independently against contradictory replay caches:
the host controller atomically claims `jti` once and returns a one-connection lease receipt
bound to the proxy identity, capability digest, address and expiry. The proxy consumes that
receipt once for its tunnel/probe; repeated CONNECT, another proxy or another hop cannot
reuse it. Renewal extends that same live connection only, not authority for a second dial.

The proxy independently reads the approved provider/registration and control-state snapshot;
it does not trust an endpoint, tenant or address set asserted by the gateway. Snapshot freshness
is at most 15 seconds, with no stale-on-error extension. It verifies capability ownership,
destination version, enabled class, quota admission reference, exact validated address and
registered name. Provider and custom classes cannot borrow each other's approvals.

For inference, CONNECT names a **canonical validated IP literal and port 443**, not a DNS name.
The proxy itself rechecks all A/AAAA answers and the address/policy before accepting that
literal. It buffers at most 64 KiB for at most 5 seconds to peek the TLS ClientHello before
opening the upstream path and requires SNI equal to the approved A-label.
Missing/unparseable SNI, non-TLS bytes, ECH and a different
name are denied. It then splices the tunnel without TLS termination; the gateway verifies
the provider certificate end-to-end. Stock Squid/Envoy name filtering alone does **not**
implement this capability, ownership, pinning and revocation protocol; T-AI-02 owns the adapter.
Do not claim an off-the-shelf proxy already satisfies these gates.

Registration has no active destination yet. The server creates a short-lived, owner-bound
**validation candidate**, not an `active` row or a provider allowlist addition. A `tls_probe`
capability authorizes only that candidate's independently validated/pinned endpoint, or an
existing owner-bound registration for scheduled revalidation as specified above. The proxy
performs a TLS handshake and certificate check itself, sends **no HTTP request, key or prompt**,
closes the socket, and returns a coarse result. It accepts no opaque client tunnel/data for
this operation. Thus a bootstrap probe cannot become an unaudited CONNECT escape hatch.
Candidates expire after 120 seconds and cannot be used for inference; rate limits, both
relevant kill switches, network denies and audit apply before any DNS or TLS probe.

#### 2.3 Denied addresses and names

The exact range lists are in the hash-bound consequences artifact (section 5); parse CIDRs
strictly, compare packed 4-byte or 16-byte addresses, and fail closed if **any** A/AAAA answer
is denied. Do not filter out private answers and then use the remaining public ones.

IPv4 denies: `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10`, `127.0.0.0/8`,
`169.254.0.0/16`, `172.16.0.0/12`, `192.0.0.0/24`, `192.0.2.0/24`, `192.88.99.0/24`,
`192.168.0.0/16`, `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`,
`224.0.0.0/4`, `240.0.0.0/4`.

IPv6 denies all addresses outside `2000::/3`, plus `::/128`, `::1/128`, `::/96`,
`::ffff:0:0/96`, `64:ff9b::/96`, `64:ff9b:1::/48`, `100::/64`, `2001::/23`,
`2001:db8::/32`, `2002::/16`, `3fff::/20`, `5f00::/16`, `fc00::/7`, `fe80::/10`,
`fec0::/10`, `ff00::/8`. IPv4-compatible/mapped, NAT64, 6to4 and Teredo forms are
**denied outright**, never unmapped to bypass policy, even if the embedded IPv4 is public.
An interpreter's `is_global` is an additional fail-closed check, not a replacement for these
explicit lists. Native IPv4 is required. IPv6 is entirely blocked by default until native
equivalent packet-path enforcement is qualified on the target; unqualified IPv6 cannot carry
either AI or control traffic.

Explicitly deny and individually test **`169.254.169.254` (instance metadata)**,
**`169.254.170.2` (container credentials)**, `169.254.170.23`, `fd00:ec2::254` and
`fd00:ec2::23`, on **every port**. This runtime admits no metadata/resolver exception.
Also deny `localhost` and suffixes `.localhost`, `.local`, `.internal`, `.arpa`,
`.localdomain`, `.onion`, `.test`, `.example`, `.invalid`, their bare suffix names, and
every single-label name (including `metadata`/`instance-data`). Suffix matching is at a DNS
label boundary, not substring matching.

The `self` class additionally denies every PenniLogic domain and address prefix, including
private dependencies, public ingress/load balancers/NAT, host/bridge interfaces and
provider-assigned **global-unicast IPv6**. T-PLT-01 publishes the complete, versioned inventory
and keeps it current. An absent, empty, stale or contradictory required deployment inventory
is **not** an empty deny list: startup and all new AI egress fail closed. Control-plane
exceptions below never authorize an AI destination in these ranges.

#### 2.4 Normalization before every comparison

1. Strictly parse the constructed registration URL or redirect URI. HTTPS only; port absent
   or canonical `443`; no userinfo, query (even empty `?`), fragment, backslash, whitespace,
   controls or percent-encoded host. DNS host required, no empty labels; remove at most one
   trailing dot. Prefixes are absolute, bounded to 256 UTF-8 bytes, percent-decoded exactly
   once, checked for `.`/`..` segments and re-encoded canonically. Reject malformed escapes,
   remaining `%` (nested encoding), encoded path separators, backslashes, controls, `?` and
   `#`; ordinary `/` separates segments. Match a prefix at a **segment boundary**, never
   string-prefix-match `/v1` against `/v10`.
2. Reject every IP-literal host before DNS: brackets, colon/zone ID, or a last label composed
   of ASCII digits or `0x`-prefixed hexadecimal, plus any form a platform legacy literal parser
   accepts. This rejects dotted IPv4, integer/short/octal/hex/leading-zero encodings, bracketed
   IPv6 and mapped/compatible forms; a strict `ip_address` parse failing does not make a
   numeric-looking host safe.
3. Perform IDNA **UTS-46 non-transitional** processing with STD3 rules, lowercase the A-label,
   enforce 63-byte labels and 253-byte total, then repeat literal, empty-label, special-use and
   self-name checks. Fullwidth digits/ideographic dots that become `127.0.0.1` are refused.
   IDNA2003 from the Python standard-library codec is not an equivalent implementation.
4. Resolve **all A and AAAA** using only the controlled resolver, with a 5-second timeout
   covering the complete resolution (not a new timeout per record),
   maximum 64 answers and 8 CNAME hops. Empty/partial/error/timeout, a special-use or self
   CNAME, a loop, truncation without a complete validated retry, or mixed denied/public answers
   denies the whole destination. No search suffix, hosts-file, mDNS, alternate resolver,
   DNS-over-HTTPS or HTTPS/SVCB service-binding path may change the result.
5. Parse address text canonically (dotted-quad IPv4, RFC 5952 IPv6), compare packed addresses
   to the full current deny/self sets, then apply the extra `is_global` check. Noncanonical
   text, zone IDs and malformed encodings are rejected, not silently normalized to allowed
   values. Equivalent binary mapped addresses remain denied regardless of parser formatting.
6. Pin that validated address through connection, TLS handshake, entire request/response and
   teardown. Repeat this process for every retry, redirect and registration/revalidation probe.

#### 2.5 Address pinning and DNS rebinding

The gateway and proxy dial the validated **numeric address**, with no library/OS hostname
lookup between validation and `connect`. SNI, `Host` and certificate verification remain the
registered A-label. TLS never verifies the literal as though it were the registered identity.
The observed peer must equal the authorized address; unexpected NAT/DNAT is a runtime failure.

For custom destinations the complete current canonical DNS answer set must **equal** the
registration pin set before each request, hop and revalidation. Adding a new public answer,
removing an old one, retaining only an overlapping subset, or adding any denied answer
suspends as `suspended_resolution_changed`, alerts and requires fresh step-up re-confirmation
before re-pinning. Never silently extend the set. For providers each attempt resolves and pins
afresh within its exact reviewed host and credential audience. Independently observed but
different gateway/proxy answer sets deny; availability does not justify accepting stale pins.

One fresh upstream connection/tunnel per attempt; at most **three outbound attempts per
logical request**, counting the initial dial, redirects and retries together. No cross-request
pool reuse, HTTP/2 origin coalescing, HTTP/3/QUIC, Alt-Svc, ECH, Happy Eyeballs or hidden SDK
retry. Multiple validated
addresses may be attempted sequentially inside the same bounded request budget, with a new
capability for each attempt. A newly denied address, revoked key/grant or stale policy closes
existing tunnels within the total revocation bound; `established` must not bypass that check.

#### 2.6 Redirect handling

Automatic redirects are disabled. Follow at most **two** hops and only `307`/`308` with an
absolute HTTPS URI on 443, **the same registered A-label and credential audience**, and an
approved normalized path. This same-origin rule also applies to providers: being another
allowlisted provider is not authority to receive the first provider's key or prompt.
Reject relative/protocol-relative targets, `301`/`302`/`303`, scheme/port/origin changes and
multiple/ambiguous Location values. Redact Location and upstream errors from public output.

Every permitted hop repeats section 2.4 in full against the same deny/self lists, obtains a new
single-use capability, checks current flags/ownership and pins its connection. A same-host
custom redirect with any changed answer set is **not followed** and suspends the destination;
it does not first dial the old or new address. Rebuild only the registered outbound headers.
No credentials are copied to a changed origin. Redirects do not reset the total timeout, quota
reservation, byte/cost budget or revocation deadline.

#### 2.7 Transport and resource limits

HTTPS over TCP 443 only; TLS 1.2 minimum, 1.3 preferred; normal trusted roots and hostname
verification, with no user trust anchors/insecure toggle. Initially use HTTP/1.1 to avoid
unimplemented multiplexed capability/pool semantics. Connect and TLS timeouts are 5 seconds
each, first-byte 30 seconds, **whole logical outbound request including redirects/retries
120 seconds**, response maximum 4 MiB after decoding. Limit decompression as well as wire size.
ADR-023's reservation/delegation deadline may shorten this, never extend it.

At most four concurrent requests per account and eight per registered A-label **across
accounts**, with a separate bounded Mode C worker/connection budget so slow custom destinations
cannot exhaust provider capacity. Refuse excess with `destination_busy`, not an unbounded queue.
The owning runtime must publish and test its finite process-wide capacity before enablement;
source defaults alone are not a load test. Ignore proxy environment/PAC variables, HSTS,
Alt-Svc, SVCB/HTTPS and preconnect hints. Responses are untrusted input to T-AI-05.

#### 2.8 Custom registration, approval, lifecycle and erasure

1. Through the authenticated core API, the owner enrolls a DNS `host`, optional `pathPrefix`,
   `credentialHeader`, optional previously enrolled `providerKeyRef`, and `models` (1 to 16).
   There is **no full URL/base address, scheme or port field**. No inference request can use
   this operation as a proxy. A raw key is enrolled only in the separate step-up key operation.
2. Verify account ownership, fresh single-use phishing-resistant ADR-019 step-up, live session,
   explicit versioned transfer consent, both relevant flags and registration limits (5/hour,
   20/day/account). Reject before DNS if any fails; denial responses expose only reason classes.
3. Create the expiring candidate, resolve/validate/pin and execute the section 2.2 TLS-only
   probe. A successful probe is **not approval by itself**. Store candidate data privately;
   no public resolver answers, timing detail or raw exception text.
4. Bind the key reference to this owner, destination and credential audience; encrypted key
   material is never echoed. Under ADR-023 section 5, assign each permitted registered model
   name a `custom_model_id`; model names and credential-looking strings never enter telemetry.
5. Atomically approve as `active` only after all registration checks pass, or keep
   `pending_activation` for 24 hours with a verified-channel notification/cancel link after
   recovery, reset, an untrusted device or takeover signal. Expiry of time alone is not
   approval: recheck consent, step-up confirmation where required, flags and current
   validation. A database constraint allows at most one active destination per account.
6. Inference uses only owner-bound `destinationId` and registered `custom_model_id` (the
   latter optional only for a single registered model, per ADR-023). UUID possession is not
   authorization; wrong-owner, pending, unknown or revoked IDs are denied before egress.
7. Revalidate every 24 hours, on any registration/policy/inventory change, before first use
   after suspension, **and resolve/check pins before every attempt**. Invalid TLS/address
   policy suspends as `suspended_validation_failed`; changed DNS as
   `suspended_resolution_changed`. Notify on a verified channel without exposing the key.
8. The owner may revoke immediately; an authorized operator may suspend/revoke for abuse;
   recovery/reset suspends as `suspended_recovery` before a recovered session can invoke AI.
   A kill switch causes `suspended_kill_switch`. Admission reads authoritative state for
   every new request and refuses if unavailable; stale cached approval never authorizes a
   new request. Gateway, proxy and kernel leases terminate in-flight traffic within **60
   seconds end-to-end**, including polling/freshness/shutdown delays. Retain fail-closed
   behavior during partitions. Revocation is terminal. Recovery/validation/resolution
   suspension needs fresh owner step-up and complete re-registration checks; kill-switch
   suspension can recover only after authorized ON plus fresh validation.
9. Durable foundational audit (ADR-020) records attempts, approval, use, revalidation,
   suspension, revocation and control changes using its typed opaque identifiers and closed
   vocabulary only. Literal addresses and their evidence belong to the separate classified,
   erasable boundary in section 2.8.1, linked by an opaque reference, **never** to the trail,
   chain or transparency projections. No new egress if required pre-egress recording fails;
   an emergency OFF must still stop traffic.
10. Host/prefix/pins/model names and key references are personal data, protected under ADR-018
    and ADR-021. T-CMP-01's versioned retention profile, with T-CMP-04 counsel input, supplies
    independent live/post-revocation/evidence-resolution retention values before real-data
    use. Erasure deletes resolving destination and evidence data and shreds the owner's keys,
    without rewriting the immutable trail or chain; section 2.8.1 specifies the boundaries.
    Terminate leases and prevent backup restore from resurrecting evidence links, keys,
    active destinations or ON flags. Do not invent statutory retention periods in this ADR.

Closed states: `pending_activation`, `active`, `suspended_resolution_changed`,
`suspended_validation_failed`, `suspended_recovery`, `suspended_kill_switch`, `revoked`.
The ephemeral validation candidate is not a new public destination state.

#### 2.8.1 Opaque audit reference and separate address evidence

ADR-020 sections 4.4, 8.7 and 10 remain authoritative and unchanged. Opaque event metadata is
still personal data; an IP's public routability does not make a user's destination or usage
association anonymous. "Restricted audit" is **not** permission to place an address in an
immutable stream. T-SEC-03 owns the following additive source mapping, not a deployed store:

| Boundary | Required representation |
|---|---|
| Foundational link | `audit.event.resource.type = ai_egress_evidence`; `audit.event.resource.id = evidence_id`, a fresh server-CSPRNG UUIDv4 independent of every address, owner and destination value. Keep ADR-020's UUIDv7 `audit_event_id`; correlate phases with `related_event_id`. These use existing typed fields, not a new payload |
| Immutable streams and copies | Only ADR-020's existing opaque identifiers, closed vocabulary and permitted time/count/schema fields. No host, URL, literal pinned/peer address, DNS answer set, address hash/HMAC, address ciphertext or digest of plaintext address evidence. `origin` remains the opaque operator-origin identifier, not the target. Relay/chain/transparency projections never dereference the evidence |
| Separate evidence relation | Core-owned `ai_egress_evidence` in the primary cluster; **not a fourth authoritative audit stream**. Constrained columns are `evidence_id`, `audit_event_id`, `owner_id`, creation/expiry instants, retention-profile version, phase and key identifier. The encrypted part holds request/job/destination resolution links, canonical host and complete resolved set, authorized pin and observed peer, TLS identity/verdict, namespace/rule-path and synthetic-sink observations, bytes/status/timing and last-byte/confirmed-close evidence |
| Excluded from audit and evidence | Keys, credential headers, prompts, raw Location values, response text and packet payload. Verification retains typed observations/counters, not a full packet or application-content dump |

**Writers and atomicity.** Customer consent/registration/use/revoke events stay in the
`consent.*` namespace through `pennilogic_app` with real owner authority. Scheduled
revalidation/enforcement verification uses `audit.verification.*`, a `system` actor and the
existing `chain_verifier`, which checks an authenticated, operation-bound job; it must not
pretend to be a user or mint a user delegation. Administrative controls remain `admin.*`
through `admin_api_owner`; disclosures remain `redaction.*` through `redaction_service`;
broker access remains `broker.*` through T-PLT-05. T-SEC-03 publishes the added closed action,
reason, resource and data-class vocabulary with a forward schema version. Preserve ADR-020's
one role per namespace, plain INSERT with FORCE RLS, chain-scope predicate and relay-only
projection writes. No gateway/proxy/controller gains a database role, `audit.*` INSERT,
customer trail SELECT or custodian unwrap; no new audit insert function or shared writer
credential is introduced.

The authenticated core intake accepts only the typed, bounded observation for the recorded
owner/request or system job. Seal the evidence row first; the existing authorized writer
then commits the corresponding opaque event in the primary database. A customer/admin state
change and its event share that writer's action transaction, as ADR-020 requires. The system
verifier writes **only its verification event**: no domain admission/flag/destination write
or evidence/ciphertext permission is added to it. The separate existing admission authority
checks the committed verification receipt; it cannot treat an uncommitted stage as success.
Return an admission receipt only after event commit and a still-valid evidence stage; a
failed event commit leaves a non-authoritative expiring stage, never a successful action or
a reusable reference. A phase's intent must be durably recorded **before** its
DNS/probe/connection operation; observed results are recorded **after** that phase, not
fabricated in the intent. A result-recording failure stops the attempt, closes its connections
in both directions before another phase or further provider application bytes, and alerts;
emergency OFF is never delayed by storage.
The event and address observation are distinct: an immutable intent alone is not proof of
the socket peer, packet denial or completed stop bound.

**Encryption and access.** Per-customer evidence and resolution links use the owner's
ADR-018 DEK, AES-256-GCM and record/column/owner/key-bound AAD; no platform-key or other-user
rewrap keeps an address association decryptable after owner erasure. Normal request sealing
uses the authorized core context. An unattended per-owner maintenance observation is sealed
by an **evidence-only key-operations job**, under `begin_keyops(owner, evidence job)` with an
empty grant set; it may seal/rekey the new evidence relation, not infer, enroll, re-pin, grant
consent or perform a general customer read. This is an explicit additive evidence-job and
table-policy input to T-SEC-03's crypto inventory, not a claim that ADR-018 already implements
it. The verifier receives the opaque staging receipt, not a DEK or ciphertext-read permission.
Deployment-only synthetic verification evidence uses a separate custodian-wrapped,
deployment-scoped evidence DEK under ADR-018's primitives/custody rules, a maximum 12-month
originator cryptoperiod and compromise rotation. It must contain **no customer link or copy
of customer evidence**; expiry destroys obsolete keys after the applicable backup bound.
These deployment-only rows have no customer owner and are admitted only for a verified
deployment job, not by a nullable-owner wildcard or a customer's request context.
T-PLT-03 owns that future custody qualification; no production custodian is provisioned here.

Force RLS on the new relation, with verified owner/evidence-job scope and separately recorded
administrative subject scope. Runtime observation intake is write-only; audit/chain readers,
relays and verifiers cannot resolve addresses. Administrative review sees masked non-value
metadata through ADR-020's function-only path; any customer-address disclosure uses its
recorded, chain-confirmed, purpose/subject-bound redaction-service path and notifications,
never direct admin ciphertext SELECT or human KMS access. Cross-owner lookup and treating
possession of `evidence_id` as authority are denied. No standing support/export access is
added; T-PLT-05 remains the human-access authority.

**Retention, erasure and missing evidence.** T-CMP-01 with T-CMP-04 counsel input supplies a
versioned, finite profile for live and post-revocation evidence, uncommitted stages, resolution
links and the backup-expiry bound. These are independently justified periods, **not inherited
trail/chain write-once locks**; an absent or invalid profile denies new egress but not OFF.
At expiry, delete the ciphertext and every resolving row/derived copy. On the ADR-021
journaled erasure, revoke traffic, delete that owner's evidence and resolution links and
destroy the owner DEK. Merely pseudonymizing `owner_id` while keeping its address is not
erasure. The scoped key-operations extension permits cleanup of this new relation under the
verified owner/job and journal only; no existing table grant or audit-stream delete is widened.
Retained audit identifiers then resolve to nothing. The trail/chain stay byte-unchanged;
an evidence-row deletion cannot cascade to, update, or require deletion of an audit row.
Transparency receives **only** ADR-020's specified subject-row deletion and counterparty
`viewer_id` pseudonym update, not a new rewrite rule.

T-SEC-03 and T-CMP-01 own evidence/link deletion and access/erasure conformance. T-PLT-02 owns
finite encrypted backup retention and erasure/expiry replay before restored data is readable;
include queued observations, caches and any approved derived artefacts, not just the live row.
Never recover a deleted mapping from audit copies, a shared key or an export, or restore an
active destination/ON flag. An expired, erased or unavailable row is reported as such; do not
reconstruct it or call the remaining opaque event network proof. T-AI-01/02/03 and T-PLT-01
retain the actual peer, packet-path and stop observations within this boundary for runtime
verification. These are H1/H2 and T14/T17 implementation obligations **before exposure**, not
additional runtime-completion requirements for accepting this source decision.

#### 2.9 Server kill switches and operators

The primary-database platform flag store owns `ai_egress_global`,
`custom_destinations_class` and per-destination state. Both class/global rows are explicitly
seeded **OFF**. Absent, malformed or deleted rows are OFF plus an alert, not defaults.
Gateway/proxy roles are read-only; runtime/admin roles cannot DELETE scope rows. A flag-cache
read is at most 15 seconds old, with **no 300-second stale-on-error grace**; startup or loss
of readable fresh state closes admission and expires existing leases. The 60-second total
stop bound includes that 15-second window and connection teardown.

Global OFF stops every provider/custom request, DNS/TLS validation probe and retry. Custom
OFF also blocks registration and all custom traffic; per-destination revoke blocks its
candidate, requests and streams. Host-controller lease removal and namespace isolation are
the break-glass OFF path when the flag store or admin service is unavailable. That operation
cannot enable traffic or erase its audit evidence.

On-call platform or security operators may turn a global/class scope OFF with fresh step-up;
the owner may revoke their own destination without a cooling period. **ON requires two
independently eligible operator principals**, fresh step-up, durable audit and all gate
evidence. No delayed single-operator ON, direct database edit, developer flag or deploy can
bypass this requirement. With only one eligible human/operator, production AI remains OFF.
Multiple AI sessions or one GitHub account do not supply two-human operational approval.
Operator eligibility and administrative auth remain ADR-020's authority.

Class/global ON checks implementation, runtime, privacy and operator readiness; it does not
require an active user registration to already exist. Once those gates pass, custom-class ON
allows the bounded enrollment/probe operation, **not arbitrary inference**. Every probe and
inference additionally checks its own live owner/consent/admission; inference requires that
destination's current active approval and pins. Provider-specific evidence is required for a
provider entry, not borrowed to approve a custom destination. This ordering avoids making
registration require a pre-existing active registration while keeping both switches OFF in
this source-only delivery.

Before ON, the runtime verifies a short-lived signed suite-pass manifest (maximum seven days)
bound to environment, build/image digest, source-consequences digest, policy and inventory
digests, kernel/Docker/nftables configuration, suite run and expiry. T-PLT-01 owns an
offline-verifiable signing identity restricted to the actual verification stage and pinned
verification material; no provider credential, new paid KMS, Governance App or custom GitHub
CheckRun is introduced here. A row claiming `passed`, a Docs unit test, a signature without
real namespace/application results, or a report from a different environment is not proof.
Missing signer provisioning or evidence means OFF. Policy/image/inventory changes and restore
invalidate old evidence and require the suite again. This runtime manifest is not independent
code review and does not replace native CI or protected integration.

#### 2.10 Why client-direct Mode C is rejected

An untrusted client cannot authoritatively enforce quota, audit its own provider use, apply
server prompt minimization, honor recovery revocation or block requests into the user's LAN.
Endpoints/keys would become extractable client state and the server kill switch would be
ineffective. The same rejection applies to BYOK, "advanced" settings, embedded provider SDKs,
browser service workers and a client-side fallback during gateway outages.

### 3. Selected runtime and exact enforcement

#### 3.1 R4 topology and startup boundary

The deployable unit is the existing Kotlin API plus Python AI gateway and a separately
isolated egress proxy on **self-managed Linux/Docker**, supervised by host systemd units.
Use dedicated gateway and proxy network namespaces with controlled veth links; do not use
host networking, a general Compose bridge as a security claim, privileged containers,
Docker sockets, host PID namespaces, or `CAP_NET_ADMIN`, `CAP_NET_RAW` or `CAP_SYS_ADMIN`
inside workloads. Run non-root with read-only filesystems and no-new-privileges.

A minimal namespace-holder container starts with **no network**. The trusted host supervisor
installs the default-drop nftables rules before attaching/routing its veth, then starts the
gateway/proxy containers in their respective prepared namespaces (Compose
`network_mode: service:<namespace-holder>` or Docker's equivalent namespace sharing).
Holder recreation, Docker restart, interface replacement or a missing/mismatched policy stops
the affected workload and repeats this closed startup sequence. Health probing comes from
the inventoried control network; do not add a blanket outbound localhost exemption.

The host supervisor alone holds network administration. It renders one versioned policy from
the source consequences and complete deployment inventory, installs changes atomically
(`nft -f` transaction), reads back the effective ruleset and namespace identity, and refuses
readiness on mismatch. The gateway cannot write its rules or allowlist. Namespace OUTPUT
filtering is mandatory: host FORWARD alone misses loopback, same-bridge and namespace-local
paths. Host INPUT/FORWARD rules additionally guard host/bridge access and Docker forwarding;
Docker-generated ACCEPT/NAT chains must not bypass an earlier drop or namespace OUTPUT.

#### 3.2 Ordered packet and name policy

The following order is normative in **both address families**, in each namespace and in the
corresponding host path. There is no unrestricted `established,related accept` shortcut.

| Order | Enforcement |
|---|---|
| 1 | Drop invalid/spoofed source traffic and every hard-denied destination: metadata/credential addresses, loopback, link-local, multicast, reserved and transition classes. None is an inventory exception, including port 53 |
| 2 | Permit only exact inventoried **control-plane** peer/address/protocol/port tuples for that workload: core API/tool path, read-only policy/state/audit/key broker, private collector, controlled resolver and (gateway only) proxy. Replies require an admitted inbound tuple/connection mark, not merely any `established` state. Validate inventory exceptions before installing rules |
| 3 | Drop every remaining denied/private/self destination. RFC 1918 or self unicast dependencies can pass only through order 2's role-bound tuple; the proxy's **AI destination** path never gets that exception |
| 4 | Gateway: no direct internet allowance at all. Proxy: TCP 443 only to exact public address/port tuples in short-lived, independently authorized egress lease sets. Check current set membership on **every packet**, including established flows; no broad internet-443 rule |
| 5 | Drop everything else, including UDP/QUIC, arbitrary DNS/DoT, alternate proxies and unconfigured IPv6; forwarding inside workload namespaces is disabled |

For this ordering, hard-denied means every section 2.3 special-use range except RFC 1918
and self-inventoried ULA; non-self ULA remains denied at order 3. Self-inventoried native
global-unicast IPv6 and public IPv4 may be control peers only at their exact approved tuples.
CGNAT, documentation, transition, loopback, link-local and named metadata addresses can
never become dependencies. Prefix membership alone is insufficient for an exception.

T-AI-02's **host egress controller** verifies the API-issued capability and its own
provider/registration snapshot, resolves/validates the complete DNS set and checks policy,
owner, quota admission, flags and expiry before installing a proxy lease. It is a privileged
part of the host supervisor, not an application-owned rule-writing API. It accepts destination
IDs/capabilities, never arbitrary CIDRs or addresses from the gateway. Its approved address
must agree with the gateway/proxy pin. Leases expire within 15 seconds unless all state is
still fresh and authorization remains live; they cannot outlive the request/capability.
Multiple leases sharing an address cannot outlive the last valid reference or bypass the
proxy's per-tunnel owner check. Revocation removes affected leases and explicitly closes
the relevant tunnels/conntrack entries; membership checks precede any reply-state allowance
for internet traffic. Controller failure, expired evidence or an unreadable registry stops
renewal, not security checks. Hard denies take precedence even over a planted lease.

Only a dedicated controlled resolver is reachable on TCP/UDP 53. It serves the bounded
provider/registration names admitted by the same control plane, not arbitrary application
queries; upstream resolution belongs to its separately confined host service. It returns a
complete A/AAAA/CNAME result for validation, not a partially filtered "safe" set. No other
53/853 route, host resolver alias or Docker embedded-DNS bypass is allowed. This reduces DNS
exfiltration; registration still reveals a bounded query to a destination's authoritative
server. T-AI-02 must prove the effective resolver route, not trust `/etc/resolv.conf`.

`169.254.169.254`, `169.254.170.2`, `169.254.170.23`, `fd00:ec2::254`, `fd00:ec2::23`
are blocked in namespace OUTPUT before any control exception and on the host paths. There
is **no accepted metadata filtering gap** on R4. Do not assign ambient instance/task
credentials to these workloads. Mount least-privilege workload key material read-only through
the platform secret-delivery path; a cloud SDK's metadata lookup is a defect, not an exception.
If a future host needs metadata for its own administration, its isolated host role does not
grant either AI namespace access; disable IMDS there where available as additional defense.

#### 3.3 Real deployment prerequisites, not another runtime choice

T-PLT-01/T-AI-02 implement and prove the selected topology. A Linux kernel/Docker/nftables
combination that cannot enforce it is **ineligible**, not an undocumented managed-platform
substitution. Production runs within the counsel-approved India residency profile; there is
no chosen vendor or purchased region. Host patching, backups, availability, least-privilege
access, capacity, restore and on-call are real obligations of the existing platform tickets.
The admin zone remains on separate hosts/auth/network per ADR-020.

ADR-018 still forbids a file-held software root for real data. T-PLT-03 must select and prove
an India-resident non-exportable KEK custodian (sealed-root self-hosted vault or compliant
managed service) with explicit approval for any spend. Until then only synthetic data and
test keys qualify; no BYOK credential, user financial data or real inference is admitted.
Likewise provider retention/DPA, transfer consent, retention profiles, two eligible operators
and the suite-signing path are deployment gates, not capabilities this document supplies.

There are two explicit implementation gaps: **H1**, application consumers (authentication,
EgressClient, registration, key custody, quota, proxy authorization, minimization and revocation)
do not exist in the inspected health-only scaffolds; **H2**, actual Linux rules, deployment,
verification/signed-evidence and pipeline consumers are not implemented here. The separate
source-only Docs56 draft is neither imported nor claimed to close either gap. Source acceptance
removes the architecture-choice blocker only; it does not complete H1/H2 or enable traffic.

### 6. Security and privacy consequences

Two independent enforcement paths (gateway transport and proxy/controller/kernel) restrict
SSRF, rebinding, metadata access and credential forwarding. Authorization binds account,
destination, mode, request and current policy; approved public destinations are still
untrusted processors. A compromised host root/controller can replace kernel rules, and a
compromised gateway can misuse data already in its memory within authorized destinations.
Isolation is not a proof of protection from host/kernel compromise or malicious approved
providers. The proxy sees network metadata and SNI, not inference plaintext; registration
TLS probes carry no inference plaintext at all.

Custom registration remains a limited public-443 reachability and DNS timing oracle. Rate
limits, coarse errors, TLS-only probes and durable audit reduce, not eliminate, that leakage.
Custom host/pin/model data and per-user usage never become metric labels. Immutable audit is
opaque-only under ADR-020; address evidence and its separately erasable resolution data obey
section 2.8.1's classification, custody and access boundary. Audit-read permission never grants
address resolution or unmask. Ordinary logs carry bounded reason codes and class/mode only.
Debug logging and HTTP traces cannot include addresses, credentials, raw message data or
request/response text.

Provider approval requires exact, unexpired model/region/endpoint/feature retention evidence
and processor agreements. "No training" is not "zero retention". User-directed BYOK/custom
transfers require versioned, withdrawable consent and truthful destination/disclosure copy;
they are not covered merely by a Mode A processor agreement, and consent does not waive
applicable law or another principal's grant. T-CMP-04 may refuse a provider/region for either
class. Raw content never reaches the server; deterministic financial arithmetic and ledger
writes remain outside the model's authority.

The price of fail-closed behavior is loss of optional AI during resolver/policy/audit/proxy/
controller outages, DNS rotation, missed verification or unavailable dual-operator ON.
Manual capture, ledger, budgets and debt calculations remain usable. Native global IPv6,
NAT/bridge behavior, TLS transports, DNS libraries and provider changes must be exercised on
the real runtime; a network-free source test cannot establish any of those properties.

### 7. Observability and failure signals

Use bounded class/mode/reason labels for `egress_requests_total`, `egress_denied_total`,
`egress_in_flight`, `custom_destinations`, `class_aware_proxy_denied_total`,
`resolution_change_suspensions_total` and `redirect_denied_total`. No host, IP, URL, model
name, destination/account ID or key-derived value appears as a metric label or routine trace.
Audit joins use only opaque event/evidence references. Authorized evidence resolution, outside
all immutable streams, obtains the actual canonical pin, observed peer and typed packet/stop
observations under section 2.8.1. No audit, chain or transparency copy embeds those values.

Observe configured **and effective** kill states, missing/stale rows, rejected capabilities,
stale policy/inventory, evidence verification failures, controller lease expiries and effective
ruleset/namespace drift. Measure `kill_switch_effect_seconds` from the authoritative OFF/
revocation commit until **every affected socket/tunnel is confirmed closed and no bytes in
either direction are admitted**. Use the later of the last admitted byte and confirmed close,
not the last denial (denials may continue forever) or the last outbound request byte while
an inbound stream continues. Fail the gate if that exceeds 60 seconds; also measure time to
refusal of the next admission. A quiet destination proves no stop bound.

Run T1/T8/T10/T19 in the exact gateway **and proxy** network contexts after each deployment,
policy/inventory/kernel change and at least every 24 hours. A failed enforcement probe, no
successful run within 25 hours, or expired suite evidence closes admission and revokes live
leases/tunnels within the same 60-second total bound, with an alert; neither a failure nor
an overdue check renews evidence. Compare running hashes against
approved source/generated inputs, with attributable rule changes and tested on-call routing.
Real synthetic sink observations/packet counters in the classified evidence boundary, linked
to durable opaque audit, establish the attempted path during their permitted retention;
unreachable external hosts or a firewall config file alone do not prove denial.

### 9. Rollout, rollback and reversal

On protected merge this dated record and hash-bound artifacts settle the design. The layout
owner's unchanged generator updates only the reserved ADR-022 index/pending slots and registry
entry. No source merge seeds ON, provisions a host, enables a provider or waives review.
Implementation first consumes the pinned contract in synthetic isolated environments, closes
H1/H2, then qualifies real runtime/operations and provider/privacy evidence. Custom remains
OFF until every gate and each destination's current registration/approval/pin is valid.

Emergency rollback is **OFF, lease/tunnel revocation and retained audit**, not removal of
network denies or restoration of stale ON state. Roll back application/rule versions only to
an independently qualified compatible pair while OFF; revalidate source/inventory and rerun
gates before ON. Provider bytes already transmitted cannot be recalled, and rollback cannot
erase their provider-side retention; disclosures and incident handling must state this.

Reversing the runtime, destination trust model or gateway-only requirement needs a
**superseding ADR with migration cost**: new host/rules/identity/custodian qualification,
additive producer/consumer migration, re-pinning or revoking registrations, credential
rotation, audit/retention continuity, new adversarial evidence and an OFF migration window.
A client-direct proposal must also revisit ADR-007, ADR-009, ADR-023 and product privacy

calculation, persisted user embedding, provider choice, statutory retention number or

real-world limitations requiring their named owners.
