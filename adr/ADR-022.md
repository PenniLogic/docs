## ADR-022 — AI egress, runtime platform and Mode C custom endpoints
**Status:** PENDING · 2026-09-30

**Decision.** Every AI request in every mode — app-managed (Mode A), bring-your-own-key (Mode B)
and custom endpoint (Mode C) — leaves PenniLogic only from the backend **AI gateway** (the
`ai-service` egress component, ADR-009), reached through the authenticated path
*client → core API → AI gateway*. No client ever holds a provider endpoint, a provider key or a
custom endpoint address. A client-direct custom endpoint mode is **rejected on every runtime**.
Outbound destinations belong to exactly two classes: **code-managed provider destinations**
(an allowlist held as reviewed code) and **runtime-registered custom destinations** (registered
once, validated, resolved, pinned, audited, re-validated and revocable; never carried in a request
body). Every egress comparison, on every layer and on every redirect hop, runs the same
normalisation — parse → IDNA → resolve all A/AAAA → canonical binary compare — against one
published deny list, and denies the destination if **any** resolved address is denied. The
resolved address is pinned for the life of the connection; automatic redirects are disabled and
each hop is re-validated under a hop limit; TLS SNI, the `Host` header and certificate
verification are pinned to the registered name. Custom-class traffic leaves the network only
through a class-aware forward proxy that independently enforces the registered destination set.
The outbound payload is bounded by named data classes, and another principal's shared data leaves
for a user-chosen destination only under that principal's explicit grant. A server-side kill
switch with named scopes, seeded rows, a signed suite-pass attestation and named operators stops
AI egress without a deploy, and Mode C stays switched off until the adversarial suite in §8 passes
on the chosen runtime. All of that is decided now and does not depend on the runtime. **The
runtime platform itself is an owner spend and vendor decision that has not been made**; §3 fixes
the requirements any runtime must meet and gives, per candidate runtime, the exact primitive that
denies private-range egress on it. This record is `PENDING` until the owner names the runtime
(§3.3); nothing in §2, §4–§11 changes when that happens.

**Why.** The AI research (`ai/01-ai-harness-research.md` §4.3) assumed a Kubernetes
`NetworkPolicy` for the network-layer defence, and it offered a client-direct Mode C. Neither
survives: no accepted document commits to Kubernetes — `architecture/03-stack-and-monetization.md`
records that "nothing in this document settles the runtime platform" and defers the question of
ECS versus its alternatives to this record — and a client-direct mode cannot satisfy
server-authoritative entitlements (ADR-007), the quota primitive (ADR-023), audit, safety
filtering, revocation after account recovery, or request-forgery controls. A user-supplied base
URL is a server-side request forgery primitive by construction; the only defence that has held
historically is layered: register-once with validation, pinned dialling, network-layer default
deny, an address-level deny at the egress path, and a suite that *attempts* the known bypasses
rather than asserting they are handled.

### 2. Decisions that hold on every runtime

#### 2.1 Gateway-only egress

- The AI gateway is the **only** component permitted to open a connection to an AI provider or a
  custom destination. It runs inside the private network, has no public address and accepts
  requests only from the core API over authenticated workload identity with a delegated user
  context (T-AI-01, T-CON-06). Clients talk to the core API only.
- Mode A uses PenniLogic's provider credentials against code-managed destinations. Mode B uses the
  user's envelope-encrypted key (T-AI-01) against a code-managed destination chosen from the
  provider allowlist — the user picks a provider, never a host. Mode C uses a runtime-registered
  custom destination and, optionally, a user key stored through the same envelope-encrypted path.
- The gateway holds **one** outbound HTTP client (`EgressClient`). Every outbound request in
  `ai-service` goes through it; a boundary test fails if any other module imports an HTTP client
  or opens a socket. The delivered `ai-service` scaffold (health-only, runtime dependency set
  `fastapi` + `uvicorn` enforced by `tests/test_boundaries.py`, no outbound network client,
  `proxy_headers=False`) contains no egress code; T-AI-01 and T-AI-03 add the `EgressClient` as a
  reviewed runtime-dependency change, not as an ad-hoc import.
- **LiteLLM (ADR-009, ADR-014).** ADR-009 places "the AI harness and LiteLLM proxy" in
  `ai-service`. Under this record LiteLLM may be used only as an **in-process routing and
  translation library** whose every provider call executes through the `EgressClient` transport
  (pinned dial, header policy, redirect and transport rules of §2.4–§2.7). A separately dialling
  LiteLLM Proxy process — or any library path that resolves names, follows redirects or opens
  sockets on its own — is not an acceptable egress component. This **narrows** ADR-009's "hosts …
  LiteLLM proxy" to that form without superseding it; T-AI-01 records how virtual-key budgets and
  metering are provided under this rule (its own tables against the ADR-023 quota primitive, or
  LiteLLM's in-process budget objects — never a second network hop). Adding `litellm` to the
  runtime dependency set is the reviewed change that also updates `tests/test_boundaries.py`.
- The gateway never attaches its own workload identity, internal service tokens, trace headers or
  any credential other than the requesting user's own key to a Mode B or Mode C request. The
  outbound header set is a **closed allowlist per destination**:
  - **Custom class (Mode C) — the maximum set:** `Host`; exactly one credential header chosen at
    registration from the closed `CredentialHeader` enum and carrying the registered key only —
    `authorization_bearer` sends the `Authorization` header using the `Bearer` scheme (RFC 6750:
    the scheme token, one space, the key), `x_api_key` sends the `x-api-key` header with the bare
    key, `api_key` sends the `api-key` header with the bare key; `Content-Type`; `Accept`;
    `Content-Length`; `User-Agent`.
  - **Provider class (Modes A and B):** the `headers` field of that provider's
    `code_managed_provider` allowlist entry in `egress-policy.json` (for example
    `["x-api-key", "anthropic-version"]`, `["api-key"]`, `["x-goog-api-key"]`, or
    `["Authorization"]`), plus `Host`, `Content-Type`, `Accept`, `Content-Length`, `User-Agent`.
    Widening a provider's set is a reviewed artifact change, never a code-path exception.
  - `User-Agent` is one fixed product string carrying no user, device, tenant, build or request
    identifier. Every header not in the applicable set is stripped. Query-string credentials are
    impossible because §2.4 refuses any query. T15 asserts the applicable set and nothing beyond it.
- **What leaves the gateway (all modes).** Request bodies contain only the prompt payload the
  gateway builds under T-AI-05's minimisation, bounded by these data classes, which are also
  published as `outbound_data_classes` in `egress-policy.json` (§5) and planted and asserted at the
  egress boundary by T14:
  - **Permitted:** the user's question text **after** it has passed the same T-AI-05 redaction as
    every other field (a question that quotes an account number, a VPA or a person's name leaves
    with those spans tokenised, not verbatim); tokenised account references (`[ACCT_REF_A]`) and
    tokenised counterparty and household-member placeholders (`[PERSON_A]`); merchant strings
    redacted to category or a stable pseudonym; categories; amounts and dates needed for the
    answer; deterministic tool results (T-AI-04, T-CON-06) in the same tokenised form.
  - **Forbidden:** account, card and loan numbers; PAN, Aadhaar, tax and other government
    identifiers; UPI VPAs and phone numbers; names and contact details of counterparties or
    household members; device, user, account, session and tenant identifiers; raw message content
    or any raw-derived digest (ADR-004, ADR-018); any credential or key; free-text memos that
    T-AI-05 has not passed through redaction.
  - **Other principals' data:** a Mode B or Mode C payload contains only data the requesting
    principal owns. Data shared with the requester under ADR-005 (household aggregates, details,
    joint goals, split-group entries) is included only where the sharer's grant carries an explicit
    **AI-egress flag** (default **off**, per grant, published in the sharing contract T-CON-04 and
    enforced by the ReBAC model T-FAM-01). Mode A, whose processors are PenniLogic's own approved
    sub-processors under contract, may include shared data within the existing grant. The sharer
    consented to a person, not to that person's provider or endpoint; a controlling household
    member must not be able to route another person's data to a destination they control
    (PRODUCT.md coercive-control concern). T-AI-05 owns the exclusion when building the prompt.

#### 2.2 Two destination classes

| | Code-managed provider destination | Runtime-registered custom destination |
|---|---|---|
| Used by | Mode A, Mode B | Mode C |
| Identity | Provider id → exact host names, approved region, retention-mode evidence reference, per-provider `headers` set | Destination id → registered host (A-label), optional path prefix, credential header, pinned address set |
| Where it lives | `egress-policy.json` allowlist in `PenniLogic/infra`, consumed by the gateway and the egress path as a versioned machine-readable artifact (§5) | A row in the gateway's destination table, created by the registration flow (§2.8) |
| Who adds one | A reviewed code change in `infra` reviewed as a security change, with the evidence attached: provider, model and region approved for the required retention mode (zero data retention where user data is sent) — owned by **T-AI-07** (PenniLogic/ai-service#8, whose allowlist is "approved for zero data retention") — and the signed processor agreement plus sub-processor disclosure — owned by **T-CMP-04** (PenniLogic/docs#44). The allowlist starts **empty** and stays empty until both owners have produced their evidence for an entry. A console, API or runtime action cannot add a host to this class; the attempt is refused and audited | The account owner, for their own account, through the registration flow with a fresh phishing-resistant step-up; operators cannot register a destination for a user |
| Admin console (T-ADM-08) may | Enable or disable providers and models that are already in the allowlist, set routing order, spend caps and the kill switch | View counts and states by class, suspend or revoke a destination for abuse — never create one |
| Pinning | Resolve → validate → connect atomically per request; the connection uses exactly the address that passed the check | Address set pinned at registration; a later change of resolution is denied and alerted, never followed (§2.5) |
| Network-layer enforcement (§3.1 RQ4) | The runtime's SNI/FQDN primitive or the class-aware proxy passes only allowlisted provider names | Only through the **class-aware forward proxy** (below); never through the provider SNI allowlist |
| Promotion between classes | Impossible at runtime: a console or runtime action cannot add a host here | Impossible at runtime: a custom destination can never widen the provider allowlist |

Both classes are evaluated against the same deny list (§2.3) on every layer. They are reported
separately so an operator can see how many custom destinations exist without reading the code
allowlist (§7).

**Class-aware egress at the network layer.** The network layer sees only (source, destination
address, SNI); a Mode C flow carries the user's registered A-label as SNI, which is by construction
not in the provider allowlist, so a plain SNI allowlist would either drop every Mode C flow or have
to pass any SNI, which is no control at all. This record therefore decides: **custom-class traffic
egresses only through a class-aware forward proxy**, on every runtime, and the proxy is mandatory
in any environment where `custom_destinations_class` is on. The gateway authenticates to the proxy
per request with a short-lived, audience-bound token that names the destination id; the proxy
independently checks that the destination is `active`, that the `CONNECT` literal is a member of
its `pinned_addresses`, and that the tunnelled ClientHello SNI equals its registered A-label — from
its own read of the destination table (replica or pushed set, current within the 60 s bound), never
from anything the gateway asserts. The SNI check is strict about what it can read: a tunnel whose
first bytes are not a parseable TLS ClientHello, a ClientHello that carries no `server_name`
extension, or one that carries an Encrypted Client Hello extension (which hides the real name) is
**denied**, not passed as "unknown". If the proxy's view of the destination table is older than
the 60 s bound, or it cannot verify the gateway's token, it **fails closed for the custom class**
— every Mode C `CONNECT` is refused until the view is current again; no high-availability pairing,
cache extension or in-flight grace is assumed, and an already-open tunnel is closed when the view
goes stale. A gateway compromise can therefore reach only destinations users have registered, and
only at their pinned addresses. Provider-class traffic uses the runtime's native SNI/FQDN primitive,
the same proxy, or both. Registration-driven proxy-set updates are logged as such so RQ9 alerting
can distinguish them from rule edits. The proxy never terminates or inspects TLS (§3.1 RQ4). If an
environment has no such proxy, `custom_destinations_class` is off there by construction, whatever
the flag store says.

#### 2.3 Denied destination classes

The deny list below is normative. It is published as `denied_ipv4`, `denied_ipv6`,
`denied_addresses_named` and `denied_special_use_suffixes` in `egress-policy.json` (§5) and is
applied by every layer that evaluates a destination address: the in-process validator at
registration, re-validation, request time and each redirect hop; the egress firewall or forward
proxy on the address it actually connects to; the runtime's network primitive where it can express
the range (§3.2); and the in-workload verification job (§8, T8). Comparison is on the binary
address after §2.4; string comparison is forbidden.

`*.local`, `*.internal` (including
`metadata.google.internal`), `*.arpa` (including `home.arpa`), `*.localdomain`, `*.onion`,
`*.test`, `*.example`, `*.invalid`, every single-label name, and the `self` class — every
PenniLogic production zone and every address prefix PenniLogic controls or occupies: VPC or VNet
IPv4 and IPv6 ranges **including provider-assigned global-unicast IPv6 prefixes**, which no

`ipaddress.ip_address("5f00::1").is_global` are both `True`, so NAT64 and SRv6 addresses are
denied only by the explicit list (verified while writing this record).

#### 2.4 Normalisation and evaluation order

Applied identically at registration, at scheduled re-validation, at request time and to every
redirect target. Any failure at any step is a **deny**, never a fallback to a default provider.

1. **Parse** the destination with a strict RFC 3986 parser. Refuse: scheme other than `https`;
   userinfo; empty host; an **empty label** anywhere in the host (for example `host..example`, or
   what remains after the single trailing-dot strip); port other than absent or `443`; query;
   fragment; any percent-encoding in the host; whitespace anywhere; percent-encoded or raw control
   characters, CR, LF, NUL, `/`, `?` or `#` in the path; a path prefix longer than 256 bytes. The
   path is percent-decoded **exactly once** and only **then** checked for `.` and `..` segments
   (so `/%2e%2e/` is refused) and re-encoded canonically. A trailing dot on the host is stripped.
2. **Reject IP-literal hosts.** A registered or redirected host must be a DNS name. A host **is an
   IP literal, and is refused,** if any of the following holds: it is bracketed; it contains `:`
   or `%`; its last label consists only of digits or matches `0[xX][0-9a-fA-F]*` (the WHATWG
   "ends in a number" rule); or the platform `inet_aton`/`inet_pton` accepts the whole string.
   That rule, not an "is it an address?" parse, is what refuses every textual encoding at the
   parser: decimal (`2852039166`), octal (`0251.0376.0251.0376`), hexadecimal (`0xA9FEA9FE`,
   `0xA9.0xFE.0xA9.0xFE`, `0x7f.0.0.1`), short-form (`169.254.43518`, `127.1`), leading-zero
   forms (`0127.0.0.01`), bracketed IPv6, zone identifiers (`%eth0`), IPv4-mapped and
   IPv4-compatible IPv6 text, and mixed encodings — strings that a strict address parser
   classifies as names while the platform's `inet_aton` silently converts them to
   `169.254.169.254`, `127.0.0.1` or `87.0.0.1` with no DNS query. The rule is re-applied after
   step 3. Wherever an address does appear as text (resolver answers, `Location` headers, proxy
   `CONNECT` targets, verification probes) it is accepted **only** in canonical form — dotted-quad
   IPv4 or RFC 5952 IPv6 — proven by round-tripping through the address parser
   (`str(ip_address(text)) == text`); any other spelling is a parse failure and therefore a deny.
   The round-trip is a fail-closed **precondition**, not the denial itself: every denial is
   asserted on the 4- or 16-byte compare of step 5, independent of spelling, because the canonical
   text of an IPv4-mapped address is interpreter-dependent (Python 3.14 renders
   `::ffff:a9fe:a9fe` as `::ffff:169.254.169.254`; Python ≤ 3.12 does the opposite).
3. **IDNA.** Convert the host to its A-label form with UTS-46 non-transitional processing,
   lowercase, labels ≤ 63 bytes, total ≤ 253 bytes. Re-apply step 2 to the result: UTS-46 maps
   fullwidth digits and ideographic full stops to ASCII, so a name such as `１２７。０。０。１`
   becomes the literal `127.0.0.1` only after mapping and must be refused there. The A-label is
   the canonical registered name: it is what is stored, displayed to the user, compared against
   the allowlist and the special-use list, and used for SNI, `Host` and certificate verification.
   Apply the special-use and `self` name denial here, before any resolution.
4. **Resolve all A and AAAA records** through the runtime's resolver with a bounded timeout. An
   empty answer, a timeout or a resolver error is a deny.
5. **Canonical binary compare.** Convert every answer to its 4- or 16-byte form and test it
   against every denied range and named address. If **any** resolved address of either family is
   denied, the whole destination is denied — a name that resolves to one public and one private
   address is refused, not partially used.
6. **Pin** (§2.5) and connect to a validated address only. No resolution happens between the
   check and the connect.

#### 2.5 Address pinning

- The address a connection uses is exactly an address that passed §2.4 in the same evaluation.
  The HTTP client is handed the validated IP address; it never resolves the name itself. This
  closes the validate-then-resolve gap that DNS rebinding exploits. When a forward proxy is in
  the egress path, the gateway issues `CONNECT` to the validated address literal, never to the
  name, so the proxy performs no resolution of its own and applies the deny list to that literal.
- Before every connection the chosen address is re-checked against the **current** policy version
  (a binary compare), so a range added to the deny list takes effect on the next request, not on
  the next re-validation cycle.
- **Custom destinations** additionally pin the address set resolved at registration
  (`pinned_addresses`). Every connection goes to a member of that set; DNS TTL is deliberately
  ignored. Scheduled re-validation (§2.8) re-resolves; if the resolved set no longer intersects
  the pinned set, or any answer is denied, the destination moves to `suspended_resolution_changed`,
  the user is notified on a verified channel, an alert is raised, and no request routes until the
  owner re-confirms with a fresh step-up (which re-runs §2.4 and re-pins). A change of resolution
  is never followed automatically.
- **Provider destinations** resolve at request time because providers rotate anycast addresses;
  the validated address is pinned for that connection and the SNI is pinned to the allowlisted
  name.
- Connection pools are keyed by (registered name, pinned address) and are never coalesced across
  origins (no HTTP/2 connection reuse for a different name, whatever the certificate covers). A
  pooled connection to an address that is no longer pinned, or belonging to a suspended or
  revoked destination, is closed within the revocation bound (§2.8). Parallel connection racing
  ("Happy Eyeballs") is disabled; when a pinned set has several addresses they are tried in
  deterministic order, each already validated.

#### 2.6 Redirect handling

- Automatic redirect following is **disabled** in the `EgressClient`; the gateway handles `3xx`
  itself.
- A redirect is followed only if all of the following hold: hop count ≤ **2**; status is `307` or
  `308` (a `301`, `302` or `303` that would turn a `POST` into a `GET` is refused); the target is
  `https` on port 443; the target host is a DNS name that passes §2.4 in full — parse, IDNA,
  resolution of all records, deny check — before any connection; for a **custom** destination
  the target host equals the registered A-label; for a **provider** destination the target host is
  in the allowlist. A protocol-relative, IP-literal, userinfo-bearing or non-`https` `Location` is
  refused. Exceeding the hop limit is refused.
- **Same-host redirect, custom class.** The fresh resolution of the redirect target is a **check
  only**: the connection for the hop dials a member of the destination's `pinned_addresses`,
  never an address the fresh resolution returned. If any fresh answer is denied, or the answer set
  does not intersect `pinned_addresses`, the hop is refused (`redirect_denied`) and the destination
  moves to `suspended_resolution_changed` (§2.5). A redirect can never follow a resolution change.
- **Provider class.** The hop pins the freshly validated address for that connection, as any
  provider request does (§2.5).
- Every refused redirect is audited with the hop index, the target host and the reason class.

#### 2.7 Transport

- `https` only, TCP port 443 only, TLS 1.2 minimum (1.3 preferred). The certificate chain is
  verified against the platform trust store; hostname verification, SNI and `Host` all use the
  registered A-label. No user-supplied trust anchors and no insecure or self-signed option exist.
- Bounded connect, TLS, first-byte and total timeouts and a maximum response size are mandatory;
  initial values are in `egress-policy.json` and may be tuned by T-AI-03 under review.
- **In-flight caps.** Those bounds are per connection; a malicious or broken custom endpoint that
  accepts and then drips bytes could otherwise hold many gateway connections for the whole `total`
  window and starve Mode A. The gateway enforces two caps: `max_in_flight_per_user` (initial 4)
  over one account's outbound requests, and `max_in_flight_per_destination_host` (initial 8)
  aggregated over **every** destination row whose registered A-label is the same host, across
  accounts — the case the per-user cap cannot see, several accounts pointing at one misbehaving
  public host. (A per-row cap would be redundant at MVP: with one active destination per account it
  can never bind before the per-user cap.) Initial values are in the artifact and are set by
  T-AI-03 under review; a request over either cap is refused with `destination_busy`, never queued
  indefinitely. `egress_in_flight` is published per class (§7) and T18 proves both caps bind and
  the pool recovers.
- HTTP-to-HTTPS upgrades, HSTS, proxy auto-configuration and proxy environment variables
  (`HTTPS_PROXY`, `NO_PROXY` and their variants) are not consulted — the egress path is configured
  explicitly in code. `Alt-Svc` headers, HTTPS/SVCB DNS records, Encrypted Client Hello and
  `Link: preconnect` hints are ignored: the gateway resolves only A and AAAA records and only ever
  dials what §2.4 validated, with the SNI visible to the egress path's allowlist.
- A response from a custom destination is untrusted input; its handling, including
  prompt-injection defence, is T-AI-05's, and its size and duration are bounded here.

#### 2.8 Custom destination registration model (Mode C)

Arbitrary custom destinations are **disabled by default**. A destination can carry traffic only
when all of the following hold: it is registered through the flow below, validated under §2.4,
approved (state `active`, including any pending-activation wait), pinned under §2.5, reachable
only through the class-aware forward proxy of §2.2, the `custom_destinations_class` switch (§2.9)
is on for that environment with a verified suite-pass attestation, and every egress gate in §8 has
passed there. Absence of any one of these is a refusal, not a fallback.

The registration flow replaces any per-request address:

1. The account owner opens the custom endpoint setting on web or Android and submits the host
   (DNS name), an optional path prefix, the credential header the endpoint expects (one value of
   the closed `CredentialHeader` enum, §2.1; default `authorization_bearer`) and, optionally, a key
   for that endpoint. There is no scheme, port or address field; `https` and 443 are implied and
   enforced.
2. The core API requires a fresh phishing-resistant step-up assertion (ADR-019 defines the
   mechanism) and forwards the request to the gateway over the authenticated internal path.
3. The gateway runs §2.4, then a TLS probe to a pinned address on 443 with SNI and certificate
   verification for the registered name and no request body. Any failure returns a coarse reason
   class (`destination_denied`, `unreachable`, `tls_verification_failed`,
   `registration_rate_limited`) and nothing else — resolver answers, timings and ports are not
   echoed. Registration attempts are rate-limited (initial bound 5 per hour and 20 per day per
   user) and audited, because each attempt is an outbound probe.
4. Any submitted key is accepted only as printable ASCII of bounded length (CR, LF and other
   control bytes are refused, so it cannot inject headers), is stored through the Mode B
   envelope-encrypted key path (T-AI-01) and is referenced by identifier only; it is never
   returned by any endpoint or shown in any console.
5. The destination is created as `active` on a trusted device with no risk signal, or as
   `pending_activation` for 24 hours with a verified-channel notification and a cancel link when
   the change follows account recovery, credential reset, an untrusted device or a takeover signal
   (the T-AI-01/T-AI-03 rule). At most **one** active custom destination per account at MVP,
   enforced by a database uniqueness constraint rather than an application-level check alone.
6. Inference requests reference the destination by id (or implicitly, as the account's single
   active destination). No request body anywhere in the AI contract carries a URL, host or base
   address (§5).
7. **Re-validation** runs every 24 hours, on every registration change, whenever the egress policy
   version changes, and before the first use after a suspension. It re-runs §2.4 at the current
   policy version and the TLS probe. A destination that now hits a denied range, whose resolution
   changed, or whose certificate no longer verifies is suspended (`suspended_validation_failed` or
   `suspended_resolution_changed`) and the user is notified.
8. **Revocation and suspension** are immediate and require no cooling period. The user revokes
   their own destination; an operator suspends or revokes for abuse through the admin console;
   the system suspends automatically on account recovery or credential reset
   (`suspended_recovery`), on failed re-validation or endpoint-integrity failure
   (`suspended_validation_failed`), on a change of resolution (`suspended_resolution_changed`) and
   on kill-switch activation (`suspended_kill_switch`). New requests are refused at once and
   in-flight streams are aborted within **60 seconds**; the same bound applies to cached
   configuration and pooled connections. Leaving a suspended state: `suspended_kill_switch`
   returns to `active` when the scope is turned back on and re-validation passes; every other
   suspended state returns to `active` only through the owner's fresh step-up re-confirmation,
   which re-runs §2.4, re-pins and is audited (T-AI-01: re-enrolment after recovery requires a new
   step-up). `revoked` is terminal; the owner registers again from step 1.
9. **Audit.** Registration attempts (outcome, reason class, resolved addresses), activation,
   every use (destination id, pinned address used, bytes in and out, status, duration — no
   content), re-validation outcomes, suspensions, revocations and kill-switch changes are recorded
   in the foundational audit trail, whose store and write semantics ADR-020 (`T-ADR-ADMIN-06`)
   decides. Registration, suspension and revocation events are visible to the user in their own
   security log.
10. **Retention and erasure.** The registered host identifies the user's own infrastructure and the
   per-use rows form a usage pattern; both are personal data with a stated life. The destination
   row lives while the destination is `active` or suspended and for one bounded period after
   `revoked`; per-use and re-validation audit rows follow the security-log retention class of the
   ADR-020 store. On account erasure (ADR-006) the host, path prefix, credential-header choice and
   `pinned_addresses` are crypto-shredded or pseudonymised — the destination id and event types
   remain so the audit chain stays intact — subject to the statutory security-log floor. That
   floor, the post-revocation period and the audit-row class are **values of the versioned
   retention profile**, not of this record: the profile is owned by **T-CMP-01**
   (PenniLogic/api#24) with counsel input from T-CMP-04, which also fixes the current CERT-In and
   DPDP Rules sources it derives them from (`compliance/01-regulatory-landscape.md` §2). The
   retention jobs T-CMP-01 owns delete or pseudonymise on schedule and record what they did. The
   user's security log shows the events until then.

States: `pending_activation`, `active`, `suspended_resolution_changed`,
`suspended_validation_failed`, `suspended_recovery`, `suspended_kill_switch`, `revoked`.

#### 2.9 Kill switch: location and operators

- **Location.** The switch state is a row per scope in PenniLogic's own flag store — the
  T-PLT-01 "flag and kill switch mechanism usable without a deploy", held in the primary
  database — read by the gateway at most 15 seconds stale. It is not a client setting, not a
  vendor feature-flag service (ADR-007 excludes vendors from the entitlement path; the egress
  switch is a security control and is treated the same way; PostHog remains a release-flag tool
  only), and not a deploy.
- **Row semantics (fail closed on absence).** An **absent** scope row — never seeded, dropped by a
  migration, or deleted by any principal — means **off** for that scope and raises an alert; it is
  never read as a default. The flag-store migration **seeds every scope row explicitly**
  (`ai_egress_global = on` is a seeded value, not a fallback). Rows are never deleted: state
  changes happen only through the audited path, and the database roles used by the gateway and by
  the admin service cannot `DELETE` from the table (the gateway's role is read-only on it). The
  admin surface exposes on/off only, so a single-operator OFF cannot be undone by removing the
  row. T7 deletes a row and asserts the scope is effectively off within 60 seconds with an alert.
- **Scopes.** `ai_egress_global` (all provider and custom traffic and every outbound probe,
  including registration and re-validation probes; T-ADM-08's "stops all provider traffic
  immediately, independent of the caps"), `custom_destinations_class` (all Mode C traffic and
  registration; **default OFF**), and `destination` (one registration — the suspension and
  revocation of §2.8).
- **Suite-pass attestation (integrity-protected).** `custom_destinations_class` may be turned on
  in an environment only after the §8 suite has passed there on the chosen runtime, and the
  gateway enforces that rather than trusting the operator: it treats the scope as **off** unless
  the flag store also carries a **signed** suite-pass attestation. The attestation is the object
  `{environment, build_version, policy_version, suite_run_id, expires_at}` signed by the pipeline's
  verification stage — the in-workload probe job (RQ6, T8) together with the CI run of the §8
  application suite against the deployed build — with a key only the pipeline can use (a KMS
  asymmetric signing key whose sign permission is granted to the pipeline identity alone, or
  Sigstore keyless signing bound to the workflow identity). The gateway verifies the signature
  against the pinned public key or identity and refuses an attestation that is unsigned, expired,
  signed by any other identity, or whose environment, build version or policy version does not
  match its own. A row anyone can insert with database access is therefore not an attestation;
  T7 inserts a forged, an expired and a mismatched attestation and asserts the scope stays off.
  Attestations are short-lived (initial 7 days) so a stale pass cannot outlive a policy change.
- **Operators.** Turning `ai_egress_global` or `custom_destinations_class` **off** is a
  single-operator action available to the on-call platform operator and the security operator
  through the admin console (separate service and auth domain, ADR-014, ADR-020) with a fresh
  step-up, and through the pipeline-run break-glass command owned by T-PLT-01. Turning either of
  those scopes back **on** requires two independently eligible operators (four-eyes), because that
  is the unsafe direction. The `destination` scope is **not** subject to four-eyes: it follows
  §2.8 step 8 — the account owner (or an operator, for abuse) turns it off, and it returns to
  `active` only through the owner's fresh step-up re-confirmation or, for `suspended_kill_switch`,
  when the class scope returns and re-validation passes. Every change is audited with actor,
  scope, previous state and origin.
- **Operability with few operators.** Operator eligibility is defined by ADR-020 (`T-ADR-ADMIN-06`,
  PENDING), and the organisation currently has one human owner, so four-eyes ON must not become an
  indefinite self-inflicted outage or an invitation to bypass by database write. Two rules: (a)
  T-PLT-01's pre-production check permits enabling AI egress in production only when at least two
  eligible operators are enrolled; and (b) a **time-delayed single-operator re-enable** exists as
  the fallback for either scope — one eligible operator requests ON; the request is notified at
  once to the security channel and to the owner; ON takes effect after a fixed delay (initial 30
  minutes, set by T-PLT-01 under review) unless any eligible operator vetoes it within the delay;
  the request, notification, veto or expiry are all audited. The break-glass command offers ON
  only through those two paths (two operators, or the delayed single-operator request) — never an
  instant single-operator ON. An approved ON (two operators, or delay expired) takes effect within
  the same 60-second bound as OFF.
- **Effect and failure mode.** A change takes effect within 60 seconds, measured rather than
  assumed (§7). If the flag store is unreachable, or returns a value the gateway cannot parse, the
  gateway honours its last-read state for at most 300 seconds and then **fails closed** for the
  affected scopes; at startup with no readable state every scope is treated as off. The gateway
  logs the switch state with every denial it causes.

#### 2.10 Mode C client-direct: rejected

A client-direct custom endpoint mode — the client calling the user's endpoint itself — is rejected
regardless of runtime because the controls this product depends on are server-side and cannot be
reproduced on an untrusted client:

- **Quota and entitlement.** Entitlements are enforced server-side and never trusted from the
  client (ADR-007); the quota primitive is server-consumed (ADR-023). A client-side count is a
  suggestion.
- **Audit.** Destination, pinned address, bytes and outcome are recorded only where the connection
  is made. A client cannot produce a trustworthy audit row for itself.
- **Safety and minimisation.** Prompt-injection defences, tool dispatch and data minimisation
  (T-AI-05) run in the gateway; a client-direct call would carry unminimised context to an
  arbitrary destination.
- **Revocation.** Recovery-triggered suspension, kill switches and operator revocation act on the
  gateway. A client with its own endpoint keeps working after account recovery and after the
  switch is thrown.
- **Request forgery.** The client's network position is the user's LAN and phone; a client-direct
  mode turns the app into a request-forgery vector into that network and puts provider endpoints
  and keys into extractable client storage (contradicting PRODUCT.md: "AI traffic is
  backend-routed. Provider keys and custom endpoints are step-up protected, revocable and
  suspended after account recovery").

Consequently every BYOK and custom-endpoint request traverses the authenticated gateway path, and
the client contract has no operation that returns a provider endpoint, key or destination address.

#### 3.3 Owner decision required: runtime platform — and what becomes ACCEPTED automatically

**The owner decides:** the runtime (one row of §3.2, or a new row in the same format), the region
within the committed residency set, and — for R1 — the variant (R1-proxy or R1-firewall; for R3
the credential variant R3a, R3b or R3c). That is the whole decision; it is the single owner-gated
element of this record. Choosing a row that carries a **recorded RQ5 gap** (R1, R1b, R2, R3b, R3c,
R5) is the owner's explicit acceptance of that compensated gap: the "Chosen runtime" line states
"owner accepts the RQ5 gap recorded for this row; gap owner T-PLT-01", so acceptance is a visible
decision rather than an inference.

**What flips to ACCEPTED automatically once the owner names the runtime.** Every decision in §1,
§2, §4–§11 is final as written and is reviewed once, with this record. When the owner names the
runtime, the chosen §3.2 row becomes the named runtime and its exact private-range deny mechanism
(the first acceptance criterion of `T-ADR-AIEGRESS-08`), and the record's status becomes
`ACCEPTED` without any change to, or second review of, the runtime-independent controls. The
ADR-022 author performs that flip in one follow-up pull request scoped to this file plus the
generated `adr/README.md` slots: add a "Chosen runtime" line under §3 naming the row, the variant,
the owner's decision date and the gap-acceptance sentence where it applies; mark the other rows
"rejected alternative"; set `status: ACCEPTED` and `date` to the decision date in the header and in
the status line; run `python -B scripts/validate_adr_layout.py render --ticket T-ADR-AIEGRESS-08`
and `check`. For rows **R1–R5** the independent review of that pull request is limited to
confirming the named row and variant match the owner's decision and that no other bytes of §1, §2
or §4–§11 changed. A **new row** written after this review has never had its RQ2–RQ6 claims checked
independently: it requires a full **infra** review of that row (and security review of its RQ5

satisfies each RQ on that runtime, and T-AI-02 implements the row.

**Until then:** T-AI-01, T-AI-03, T-CON-06, T-ADM-08 and the contract work proceed on §2 and §5,

| Option | Verdict | Why |
|---|---|---|
| O1 — Client-direct Mode C (client calls the user's endpoint) | **Rejected** | §2.10: defeats quota, audit, safety, revocation and request-forgery controls; puts endpoints and keys in clients |
| O2 — Backend-routed with the base URL supplied in each request body | **Rejected** | Every request is a fresh forgery attempt; nothing can be pinned, re-validated or revoked; forbidden by the acceptance criteria |
| O3 — Backend-routed register-once with an application-layer validator only | **Rejected as insufficient** | A single layer has been bypassed repeatedly through redirects, resolution tricks and encodings; T-AI-02 exists because the network layer was unimplemented |
| O4 — Backend-routed register-once, pinned dial, network default deny, address-level deny on the egress path, class-aware proxy for Mode C, kill switch, adversarial gate | **Chosen** | §2; the only option in which each layer's failure is caught by another, the network layer can tell a Mode C flow from exfiltration, and the mode can be switched off without a deploy |
| O5 — No custom endpoints at all | Not chosen, but it is the **shipped state** until the gates pass | Mode C is a differentiator the research found no competitor offers; it stays off by default (§2.9) and is enabled only per environment after the suite passes |
| O6 — Kubernetes `NetworkPolicy` as the assumed network primitive | **Rejected as an assumption** | The runtime is undecided; the mechanism must be the chosen runtime's (§3) |
| O7 — Network-layer name allowlist as `provider allowlist ∪ registered custom A-labels`, pushed by the gateway | **Rejected** | Gives the gateway write access to its own network rules, so a compromised gateway could widen them; the class-aware proxy (§2.2) enforces the registered set from its own read instead |
| O8 — Mode C with address-deny-only network control (no SNI check for the custom class) | **Rejected** | Leaves exfiltration to any public host indistinguishable from Mode C at the network layer; O4's proxy closes it on every runtime |
| O9 — A separately dialling LiteLLM Proxy process as the egress component | **Rejected** | It resolves names, follows redirects and opens sockets outside the `EgressClient`, so §2.4–§2.7 cannot be applied; LiteLLM remains usable as an in-process library (§2.1), narrowing ADR-009 |

### 5. Contracts and schema consequences

This record is the contract input; the consequences it forces are:

1. **No address-bearing field in any AI request.** No request schema in the AI contract groups
   (T-CON-06 and the assistant, BYOK and custom-endpoint groups that follow) may contain a URL,
   host, base address, `api_base`, `endpoint` or port field, and request schemas are strict
   (`additionalProperties: false`) so a smuggled field is refused rather than ignored. The
   contracts CI enforces this with a schema lint owned by the contracts scaffold and lint ticket
   **T-SCA-CON-01** (PenniLogic/contracts#2) and exercised by **T-QA-02** (PenniLogic/contracts#3);
   T-CON-06 applies the strict-schema rule to its own tool group; T-AI-03's contract test attempts
   to send an address field.
2. **Registration is a separate operation group** on the core API (exact paths owned by the
   contracts repository): register (`host`, optional `pathPrefix`, `credentialHeader`, optional
   `providerKeyRef`), read state, confirm after suspension, cancel pending activation, revoke.
   Responses expose the A-label host, path prefix, credential header, state, last validation time
   and reason class — never a key and never resolver detail beyond the reason class. Inference
   requests reference `destinationId`. **Owner:** this group and the enumerations in item 3 fall
   outside T-CON-06's boundary ("the AI tool specification group only"); they are owned by the
   contracts ticket **PenniLogic/contracts#27** — *Publish the custom-destination registration group
   and egress enumerations (ADR-022)* — which is blocked by this record and by the contracts
   scaffold (contracts#2).
3. **Enumerations** published as shared schema components: `CustomDestinationState` (§2.8 states);
   `EgressDenialReason` (`destination_denied`, `destination_not_registered`,
   `destination_suspended`, `destination_revoked`, `destination_busy`, `resolution_changed`,
   `redirect_denied`, `redirect_hop_limit`, `tls_verification_failed`, `unreachable`,
   `kill_switch_active`, `registration_rate_limited`, `step_up_required`, `pending_activation`) —

   `kill_switch_active`; `suspended_recovery` and `suspended_validation_failed` →

4. **`egress-policy.json`** is the machine-readable artifact. T-AI-02 publishes it from

### 6. Security and privacy consequences

**Of the chosen option.**

- Provider endpoints and keys never exist on a client; the client contract cannot return them.
- Server-side request forgery is reduced to one audited, validated, pinned path with a network
  layer behind it; failure of the in-process validator is caught by the egress path's address
  deny, and failure of both is detectable by the in-workload verification job.
- Residual: registration validation is a coarse reachability oracle for public hosts on port 443
  (rate-limited, audited, reason classes only), and each attempt causes PenniLogic's resolver to
  query the attacker's authoritative name server, revealing the resolver's egress address and the
  attempt's timing — an accepted side channel bounded by the same rate limits. On managed runtimes
  the workload-local metadata or credential endpoint is not filterable at the network layer (R1,
  R2, R3b, R3c, R5); the compensation in RQ5 is mandatory and the gap is owned, not implicit.
  Least-privilege workload identity bounds what a leaked credential could do.
- **What egresses, and to whom.** The outbound data classes of §2.1 bound every mode: forbidden
  identifiers never leave the gateway, and another principal's shared data leaves for a Mode B or
  Mode C destination only under that principal's explicit per-grant AI-egress flag. Raw message
  content never reaches the server (ADR-004), so it cannot reach any destination. Provider-class
  destinations remain default-deny until the entry carries T-AI-07's retention-mode and region
  evidence and T-CMP-04's processor agreement and sub-processor disclosure
  (`compliance/01-regulatory-landscape.md` §5.3 describes the obligation; those two tickets own
  the evidence).
- **Transfer position of Modes B and C.** RQ8 places the gateway in the residency set, but Mode B
  sends data to the user's chosen provider under the *user's* provider terms and Mode C sends it
  wherever the user's endpoint is. Both are **user-directed transfers outside the residency set
  and outside PenniLogic's processor agreements**. The BYOK and registration screens state the
  destination (provider and region, or the registered A-label), that PenniLogic's processor
  agreement does not cover it, and which data classes of §2.1 will be sent; the consent is
  recorded against its purpose version in the consent and purpose registry (`T-CON-09`,
  PenniLogic/contracts#14; ledger `T-CMP-01`) and is withdrawn automatically when the key or
  destination is revoked. The privacy notice names Mode B and Mode C as user-directed processing
  distinct from PenniLogic's sub-processors.
- BYOK and Mode C keys follow the T-AI-01 envelope-encryption, step-up, recovery-suspension and
  no-plaintext-recovery rules; audit rows carry destination id and pinned address, never content
  or key material. Destination and audit rows have the stated retention and erasure treatment of
  §2.8 step 10.
- Kill switch fail-closed behaviour can deny AI during a flag-store outage longer than 300
  seconds, and the delayed single-operator re-enable of §2.9 accepts up to 30 minutes of outage
  after a false-positive OFF with one operator on duty. Both are the intended direction of failure
  for a security control. The delayed path's residual is a single compromised eligible operator
  who requests ON while nobody vetoes; it is bounded by the mandatory notification to the owner
  and the security channel, by the audit row, and by the fact that ON only restores traffic to
  destinations the other layers already permit.
- The class-aware proxy is a second trusted component in the egress path. Its residual is a
  compromise of the proxy itself, which could reach any public address the network layer allows
  it; that is bounded by giving the proxy no credential material (it never terminates TLS), a
  read-only view of the destination table, and the same in-workload probes (T8, T10) run against
  its network position. A proxy outage, a stale destination view (older than 60 s) or an
  unverifiable gateway token fails closed for Mode C only — open tunnels are closed, new
  `CONNECT`s refused, no in-flight grace — while provider-class traffic on the native primitive is
  unaffected; Mode C availability is therefore bounded by the proxy's, and no high-availability
  arrangement is assumed or required by this record.

**Of the rejected options.** O1 leaks endpoints and keys into extractable client storage, removes
quota, audit, safety and revocation, and makes the user's phone a request-forgery vector into
their own network. O2 makes every inference request a forgery attempt with no pinning or
revocation. O3 relies on a single layer with a long bypass history. O6 leaves the network layer
unimplemented on any runtime that is not Kubernetes.

### 9. Rollout and rollback

Adopted on merge. §2 and §5 bind T-AI-01, T-AI-02, T-AI-03, T-AI-05, T-AI-07, T-CON-04, T-CON-06,
T-ADM-08, T-PLT-01 and contracts#27 immediately; §3.3 describes the only
change this record undergoes when the owner picks a runtime. Reversing any decision in §2 requires
a superseding record that states the migration cost: removing the registration operation group and
enumerations from the contract (a breaking change under the additive-contract rule), migrating or
revoking registered destinations, changing network rules and firewall or proxy configuration, and
re-running the §8 suite. A superseding record that introduced client-direct AI traffic would also
have to revisit ADR-007 and the backend-routed principle in `PRODUCT.md`.

### 10. Non-goals

Implementation (the tickets in §11); provider selection and the retention-mode and region evidence
(T-AI-07) and processor agreements (T-CMP-04); the evaluation suite and spend gates (T-AI-06); the
quota and entitlement model (ADR-023); the step-up assertion and recovery mechanics (ADR-019); the
administrative boundary, operator eligibility and audit-stream stores (ADR-020); prompt-injection
defences and the redaction rules that implement the §2.1 data classes (T-AI-05); the sharing grant
model itself (ADR-005, T-CON-04, T-FAM-01); retention periods (T-CMP-01); persisted embeddings
(T-ADR-EMBED-12); the runtime, database and disaster-recovery topology beyond the requirements in
§3.1 (T-PLT-01).
