## ADR-019 — Authentication: passkeys at MVP, in-repository WebAuthn, relying-party identifier, device-bound sessions and recovery
**Status:** ACCEPTED · 2026-09-30

**Decision.** Passkeys (WebAuthn Level 3 discoverable credentials with user verification) are the
only primary authentication credential from the first release; there are no passwords and no
SMS-OTP login. The relying party is implemented inside the Kotlin/Ktor `api` (ADR-009, ADR-014)
with a vetted server-side WebAuthn library, not by a self-hosted identity server and not by a
managed vendor. The relying-party identifier (RP ID) is the registrable domain of the customer web
origin, written `<product-domain>` throughout this record because the owner has not yet confirmed
the product's public domain; it is a named owner input and no production credential may be
registered before it is bound. Access tokens are 15-minute JWTs and refresh tokens are opaque,
rotated, reuse-detected and bound to a per-device DPoP key (RFC 9449) that is hardware-attested on
Android where the device allows it. Recovery has exactly two routes — single-use recovery codes and
reverification of a mature verified channel — each with a cooling-off window, notification to every
channel and device, a cancellation path and a 24-hour restricted period afterwards. Phone
verification is a trial-abuse control that costs money and stays disabled until the owner approves
an SMS provider; it is never a login factor and never a sole recovery route. Service-to-service
calls carry a short-lived asymmetric-key workload token plus an `api`-minted delegation token that
binds the user subject to the calling workload; public clients cannot mint either. Admin operator
identity is ADR-020's domain and does not share this RP ID. The machine-readable parameters are in
section 15 and are mirrored by the contracts repository.

**Why.** Every authentication risk in this product concentrates on two things the research left
open: a wrong RP ID is unfixable once credentials exist, and a weak recovery path is the route an
attacker takes instead of breaking a passkey. Deciding both before code becomes Ready is cheaper
than any later migration. Passwords at MVP would add a second, weaker credential system (T-01
credential stuffing) and a permanent password-reset attack surface for no product gain; the epic's
"post-MVP" deferral and the security checklist's "MVP" requirement contradicted each other and this
record ends that silence. Auth already belongs to the `api` by accepted decision, so a second
runtime would add cost, a second identity store and custom extension code for the cooling-off,
device-binding and delegation semantics this product needs anyway.

### The six scope items — chosen and rejected

| Scope item | Chosen | Rejected |
|---|---|---|
| Passkey timing | Passkeys are the only primary credential at MVP, on Android (Credential Manager) and web (§2) | Email + password at MVP with passkeys later; SMS OTP as a login factor; deferring passkeys to E19 |
| Provider | (a) In-repository WebAuthn relying party in the Kotlin `api` with a vetted library (§3) | (b) Self-hosted identity server (Keycloak, ZITADEL, Ory Kratos/Hydra, Hanko); (c) managed vendors (Cognito, Auth0, Stytch, Clerk, Firebase Auth) — rejected unless the owner approves spend and every §1 criterion passes |
| RP ID and origin set | RP ID = registrable domain of the customer web origin (`<product-domain>`); origins = the canonical web origin(s) under it plus the Android `apk-key-hash` origins; admin excluded (§4) | A subdomain RP ID (`app.<product-domain>`); a separate RP ID per client; sharing the RP ID with the admin console |
| Recovery | Two routes: single-use recovery codes (24 h cooling-off) and mature-channel reverification (72 h), cancellation, "not me" reversal, restricted period (§10–§11) | Instant recovery by SMS/email; knowledge questions; support-operated recovery without at-least-as-strong proof; deleting existing passkeys on recovery |
| Sessions and refresh | 15-min ES256 JWT access token; opaque rotating refresh token with reuse detection and 30 s grace; both DPoP-bound to a per-device key, hardware-attested on Android when available (§8) | Long-lived bearer tokens; device fingerprinting as the binding; cookie-only sessions on Android; unbound refresh tokens |
| Phone verification | Optional, disabled until the owner approves an SMS provider; hashed phone; one trial per verified channel; layered vendor-independent abuse controls (§12) | Phone number as login identifier; SMS OTP as authentication factor; phone as sole recovery route |

### 1. Requirements fixed before any provider or vendor question

These requirements lead; any implementation, library or later vendor must satisfy every row.
They are the evaluation criteria a later vendor decision must meet (acceptance criterion on
vendor selection).

| # | Requirement | Why |
|---|---|---|
| R-1 | WebAuthn Level 3 relying-party operations (W3C Recommendation, 25 August 2026): discoverable (resident) credentials, `userVerification=required`, backup-eligibility/backup-state flags recorded, Signal API used on web where available | Passkeys are the credential; synced passkeys are the norm on Android |
| R-2 | Attestation conveyance `none` requested; attestation statements verified and stored when an authenticator returns one, never required | Synced platform passkeys return no attestation; requiring it would exclude the launch market |
| R-3 | All account, credential, session, device, recovery and audit records stored in the product's India-region primary database (compliance §2, `T-CMP-04` owns statutory values) | DPDP and CERT-In posture; no identity data in a foreign-region SaaS |
| R-4 | Exit: credential public keys, credential IDs, AAGUIDs, flags and timestamps exportable in a documented JSON shape we control; recovery-code hashes and refresh hashes never exported | Leaving a provider must not mean re-enrolling every user |
| R-5 | Cost ceiling: no new runtime, licence, provider, region or storage spend without explicit owner approval (`AGENTS.md`) | Free-plan organisation; unit economics depend on near-zero fixed cost |
| R-6 | The product's custom semantics — cooling-off with cancellation, young-credential rule, DPoP-bound refresh families, restricted post-recovery mode, delegated subject envelope — must be implementable without forking or writing plug-ins for a third-party product | These are the controls that make recovery safe; they cannot be optional vendor features |
| R-7 | Origin validation against the exact §4 origin set, including Android `apk-key-hash` origins and the DAL/ROR companions | Phishing resistance is only as good as the origin check |
| R-8 | Library or product: permissive licence, active maintenance, FIDO conformance evidence, used by at least one major relying party, security advisories process | Reviewability of the verification core |
| R-9 | No personal data in tokens; no raw phone numbers at rest; no credential, OTP or recovery code in any log | ADR-004 spirit, DPDP minimisation, `T-SEC-03` audit |

### 2. Passkey timing — passkeys are the only primary credential at MVP

**Decision.** From the first server-authenticated release, an account is created and signed in with
a passkey. Enrolment order: consent and age eligibility (web#26 and its Android counterpart) →
the email channel is entered and verified with a single-use code or link valid 600 s (the response
to the client is identical whether or not that email already has an account; the inbox learns the
truth) → passkey registration → recovery codes offered (§10). Registration: `residentKey=required`, `userVerification=required`,
`attestation=none`, `pubKeyCredParams` ES256 (-7), EdDSA (-8), RS256 (-257), `excludeCredentials`
populated, `credProps` requested, 32-byte single-use challenge valid 300 s and bound to the
ceremony. `user.id` is a random 32-byte handle stored with the account (never the email);
`user.name` is the verified email so the credential provider shows a recognisable entry;
`user.displayName` is the user's chosen display name. Authentication is username-less
(discoverable credentials, conditional UI on web, Credential Manager bottom sheet on Android);
cross-device (hybrid) sign-in is the platform's, not ours. Up to 10 credentials per account, each
with a user-set name, provider AAGUID, BE/BS flags, created and last-used times, visible on the
"Profile security and active sessions" surfaces (S-AND-064, S-WEB-044). A non-increasing signature
counter on a credential that reports counters marks the credential `clone_suspected`, forces
step-up with another credential and notifies every channel (`SignatureCounterRegressionTest`).

**Rationale, not deferral.** (1) The RP ID must be fixed before the first credential regardless of
timing, so "later" saves nothing. (2) A password system shipped first is never removed: it keeps
credential stuffing (T-01), breached-password checks, reset mail and a second recovery surface alive
forever and forces a migration campaign later. (3) The security checklist (AUTH-01) already made
passkeys the primary defence; the epic text that deferred them is rewritten by §20. (4) Google,
Apple and Microsoft platform managers sync passkeys in 2026, so a new phone normally signs in with
no recovery at all. (5) The recovery design in §10 is the same work whether or not passwords
exist; passwords would only add a weaker parallel path to it.

**Fallback for devices that cannot hold a passkey.** Credential Manager passkeys require
Android 9 (API 28) or later; the Android scaffold's `minSdk` is provisionally 26 (android#2
confirms or raises it). A device below API 28, or without any passkey-capable credential provider,
or a browser without WebAuthn, cannot create a server account: it remains in local-only mode
(capture, manual entry and local analysis work per `PRODUCT.md`; nothing syncs) and shows the
condition `authenticator_unavailable`. The condition is client-determined (the server never observes
it), so — like `device_permission_not_granted` — its taxonomy identifier is added through taxonomy
§13 by the client platform owners, android#20 (T-AND-01) with docs#88 (T-UXA-02) and web#8 with
docs#103, not by a server ticket, and it is **not** pre-bound to `degraded` (which promises automatic
re-checks for a condition that is permanent on that device). This record fixes its content: what
still works (capture, manual entry, local analysis); that a server account can be created later from
a passkey-capable device or browser and this device attached afterwards; exactly one action (the
explanation of how to get an account); no automatic re-check, no repeated prompt, no "Try again"
(`AuthenticatorUnavailableModeTest`). No password or OTP path is added for these devices: a weaker
path for a minority becomes the path attackers choose for everyone. Raising `minSdk` to 28 removes
the API reason for this mode; the provider-absence reason remains.

**Rejected.** *Email + password at MVP with passkeys later* — two credential systems, permanent
password attack surface, a forced migration, and api#4 would still need a rewrite when passkeys
arrive. *SMS OTP as a login factor (checklist AUTH-02)* — phishable, SIM-swap exposed, per-message
spend with TRAI DLT registration, and it turns the phone into the account. *Passkeys post-MVP
(E19)* — the deferral this record exists to end.

### 3. Provider — option (a): in-repository WebAuthn in the Kotlin `api`

**Decision.** The `api` is the relying party. Registration and assertion verification use a
vetted server-side WebAuthn library meeting R-8; the default is **WebAuthn4J** (Apache-2.0; the
verification core used by Keycloak, Quarkus Security and Spring Security), with Yubico's
`java-webauthn-server` as the alternative if api#4 documents a failing R-8 criterion. The library
verifies ceremonies only; accounts, credentials, sessions, devices, recovery, audit and delegation
are product code in the `api` under this record. Issuance and verification of access, refresh,
step-up, workload and delegation tokens are also in the `api`; the `ai-service` and the `admin`
service verify but never mint delegation tokens (§13).

**Why (a) over (b).** Against §1: (b) fails R-5 (a second runtime, database, TLS endpoint and
on-call surface in the India region is new spend without approval), fails R-6 (cooling-off with
cancellation and "not me" reversal, the young-credential rule, DPoP-bound refresh families,
restricted post-recovery mode and the delegation envelope all become Java SPI extensions or Go
hooks — custom code inside someone else's product, with two identity stores to reconcile with
entitlements and the audit service), and weakens R-4 (export is the product's realm format). (a)
satisfies every row, keeps auth where ADR-009 and ADR-014 already place it, and reuses the same
verification core Keycloak itself runs. Cost of (a): the `api` team owns session, recovery and
credential-lifecycle code and must track WebAuthn changes; that work exists in api#4, api#5, api#40
and api#57 regardless of provider. Exit from (a): R-4 export plus a standard WebAuthn RP can import
the public keys; the RP ID is unchanged so credentials survive.

**Why not (c).** Managed vendors are recurring spend without approval, most do not guarantee
India-region residency (research §7.4), their session and recovery semantics are theirs not ours
(R-6), and their exit is a credential re-enrolment unless they export public keys under the same RP
ID. Vendor choice follows requirements: a later record may adopt a vendor only if it passes every
§1 row, the owner approves the spend, and it can import R-4 exports under the unchanged RP ID.

**Cost and exit summary.**

| Option | New fixed cost | Custom code needed | Exit path | Residency |
|---|---|---|---|---|
| (a) in-repository, chosen | none beyond the `api` | product semantics only (needed anyway) | R-4 export → any WebAuthn RP | product database, India region |
| (b) self-hosted identity server | second runtime + DB + ops | SPI/hook plug-ins for §8–§13 semantics | realm/identity export → conversion | self-hosted, India region |
| (c) managed vendor | monthly per-MAU fee | glue for §8–§13; some semantics impossible | vendor export or full re-enrolment | vendor-dependent; mostly not India |

### 4. Relying-party identifier and origin set

**Exact RP ID string.** `RP ID = the registrable domain (eTLD+1) of the canonical customer web
origin`, written `<product-domain>`. Example instantiation: if the customer web app is served at
`https://<product-domain>` or `https://app.<product-domain>`, the RP ID is `<product-domain>` —
never `app.<product-domain>`, never `www.<product-domain>`. The literal value is owner input OI-1
(§14): the owner has not purchased or confirmed a domain, `pennilogic.in` appears in
`architecture/02-security-architecture.md` §5.2 only as an illustration, and this record does not
invent one as fact. The bound literal is recorded in the contracts mirror of §15 before the first
production credential; until it is bound, production passkey registration is refused by the api
(`RpIdAndOriginConformanceTest`). Choosing the registrable domain means any host under it (`app.`,
`web.`, a future `secure.`) may run a ceremony once listed, the DAL and ROR companions live at
the apex, and the identifier never has to move when the web app changes hosts.

**Full origin set** (the api's allow-list; every WebAuthn `clientDataJSON.origin` must match one
entry exactly):

| Client | Origin entry | Notes |
|---|---|---|
| Customer web, canonical | `https://<product-domain>` | The ceremony page host at MVP |
| Customer web, app host (only if used) | `https://app.<product-domain>` | Listed only when the web app is actually served there; `www.<product-domain>` 301-redirects to the apex and is not a ceremony origin |
| Android, Play-signed release | `android:apk-key-hash:<base64url(SHA-256(app-signing-certificate DER))>` | The Play App Signing certificate, OI-2 |
| Android, upload-key-signed build | `android:apk-key-hash:<base64url(SHA-256(upload-certificate DER))>` | Internal and pre-Play builds; removable once every supported install is Play-signed |
| Staging (separate RP ID) | `https://<staging-domain>`, plus the debug and upload `apk-key-hash` origins for `com.pennilogic.android.debug` | Its own RP ID, its own DAL; never listed in the production set |
| Admin console | **not in the set** | Separate authentication domain (ADR-014, ADR-020); separate credentials by design |

Android `origin` values are what Credential Manager places in `clientDataJSON` for a native app;
they change only when the signing certificate changes (§5). Consolidating additional brands or
country domains under this RP ID uses Related Origin Requests (§6).

**Cost of changing the RP ID after credentials exist.** Authenticators scope a credential to the
RP ID and the RP never holds the private key, so there is no server-side migration: 100 % of the
N enrolled credentials stop matching the new RP ID. The only path is a dual-RP-ID transition:
the api accepts assertions for both identifiers for at least 90 days; every returning user performs
one re-registration ceremony per authenticator while signed in under the old RP ID (≥ N
ceremonies); every user who does not return inside the window loses the credential and falls into
recovery (each case = a 24–72 h cooling-off, notifications to every channel and support load);
the DAL and ROR files are republished at the new host; an Android release with App Links intent
filters for the new host passes Play review; the web app is served at the new origin; and the dual-acceptance
code is security-reviewed then removed. Estimated engineering effort is at least three to five
weeks for two engineers plus the transition period, and a share of users equal to those with a
single device-bound credential and no saved recovery codes is unrecoverable through self-service.
Related Origin Requests do not reduce this cost: they let more origins use an RP ID, they do not
move credentials between RP IDs. Before the first production credential the cost is zero, which is
why OI-1 gates production registration rather than the ADR waiting for the purchase.

### 5. Android Digital Asset Links companion and rollout order

**File.** Exactly one statement list at `https://<product-domain>/.well-known/assetlinks.json`
(the RP ID host — not `www.`, not `app.`), HTTP 200, `Content-Type: application/json`, served
over HTTPS with a valid certificate, reachable without redirects or authentication, not blocked for
crawlers. Template:

```json
[
  {
    "relation": [
      "delegate_permission/common.get_login_creds",
      "delegate_permission/common.handle_all_urls"
    ],
    "target": {
      "namespace": "android_app",
      "package_name": "com.pennilogic.android",
      "sha256_cert_fingerprints": [
        "<SHA-256 of the Play App Signing certificate, colon-separated upper-case hex>",
        "<SHA-256 of the upload-key certificate, colon-separated upper-case hex>"
      ]
    }
  }
]
```

`get_login_creds` is what lets Credential Manager share passkeys between the web origin and the
app; `handle_all_urls` verifies App Links so the recovery cancellation and "not me" links
(§10–§11) open in the installed app (`android:autoVerify="true"` intent filters on the RP ID
host). The debug package `com.pennilogic.android.debug` appears only in the staging RP ID's file
with the locally generated debug certificate fingerprint; it never appears in the production file.
Fingerprints are the SHA-256 of the signing certificate as printed by `keytool -printcert` or the
Play Console app-signing page; they are owner input OI-2 and are mirrored, one for one, by the
`android:apk-key-hash` origins in §4 (same certificate, different encoding).

**Signing-key rotation without invalidating credentials.** Passkeys are bound to the RP ID, not to
the signing certificate; the certificate appears only in this file and in the api's origin
allow-list. Rotation (a Play App Signing key upgrade or an upload-key reset) therefore never
touches credentials if the order is: (1) obtain the new certificate; (2) publish the DAL file with
both old and new fingerprints; (3) add the new `apk-key-hash` origin to the api allow-list; (4)
verify with the Digital Asset Links API
(`https://digitalassetlinks.googleapis.com/v1/statements:list?source.web.site=https://<product-domain>&relation=delegate_permission/common.get_login_creds`)
and the `DigitalAssetLinksPublicationTest`; (5) release the newly signed build; (6) remove the old
fingerprint and origin only after telemetry shows no supported install still presents it. Removing
a fingerprint before step 6 breaks passkey sharing for every install signed with it — the file
must carry every fingerprint currently in the field.

**Rollout order (first production enablement).** (1) OI-1 domain confirmed and bound in the §15
mirror; (2) DNS and TLS for the apex with HSTS; (3) publish `/.well-known/assetlinks.json` and, if
§6 lists anything, `/.well-known/webauthn`; (4) verify both with the DAL API, a browser check and
the conformance tests against the production host; (5) configure the api allow-list from the bound
mirror; (6) only then flip the production passkey-registration flag; (7) the Android release
carrying the App Links intent filters goes live only after step 4. Staging follows the same order
on `<staging-domain>` first.

### 6. Related Origin Requests

**Decision.** The RP ID is one registrable domain; additional web origins that must share passkeys
are consolidated under it with Related Origin Requests while the inventory stays within the
platform limit: the JSON at `https://<product-domain>/.well-known/webauthn`, served as
`application/json`, holds `{"origins": [...]}`; clients count the distinct eTLD+1 *labels* of the
listed origins (e.g. `<brand>.co.uk` and `<brand>.de` share the label `<brand>`), WebAuthn
Level 3 requires clients to support at least five labels, Chrome enforces exactly five, and
entries beyond the limit are ignored in order. Origins already under the RP ID are not listed.

**Inventory at this record:** none. The customer web origins in §4 are under the RP ID and need no
related-origin entry; the admin console is excluded by design; no second brand or country domain
exists. The well-known file is therefore either absent (404) or `{"origins": []}` at MVP; the
`RelatedOriginsWellKnownTest` accepts either and fails on anything else. Any addition is a
reviewed change to the §15 mirror, listed origin by origin with its label, and may never exceed
five labels.

**Additional brands consolidate under one RP ID up to five labels.** A brand or country domain
operated by PenniLogic with the same account model joins the list (one label each). The sixth
label does not: the fallback for an over-limit inventory is to send that origin's sign-in through a
ceremony page on the RP ID host (redirect-to-canonical sign-in), which needs no related-origin
entry at all; only if that is impossible does the origin become its own RP ID with separate
credentials. Redirect-to-canonical is also the preferred design for any origin that can tolerate a
redirect, keeping the related-origin list small. `OverLimitOriginInventoryTest` fails the build
when the mirror lists more than five labels.

### 7. Credential custody, sync and portability

**Custody.** The user's credential provider (Google Password Manager by default on Android;
another provider on Android 14+; the browser or platform manager on web) holds the private key.
The api holds only the public key (COSE), credential ID, AAGUID, transports, BE/BS flags, signature
counter, name and timestamps. PenniLogic never holds, escrows or can recover a private key.

**Sync.** Synced passkeys (BE=1) are accepted and expected: they are what makes a new phone sign in
without recovery. Device-bound passkeys (BE=0) are accepted; an account whose only credential is
device-bound and that has not saved recovery codes exposes `recovery_readiness=no_codes` so the
clients can nudge (design owned by E34). The api records BE/BS on every assertion; a change from
BS=0 to BS=1 is an audit event, not a refusal.

**Platform migration and leaving.** Between providers or platforms the user either moves the
passkey with the provider's Credential Exchange (FIDO CXP/CXF, available on Android in 2026), or
registers a new passkey from an existing signed-in session (up to 10 credentials), or uses §10
recovery. A user leaving PenniLogic exports their account under the DPDP portability contract; the
authentication section of that export contains the R-4 credential metadata, never a private key
(we do not have it), never recovery codes or refresh material. On credential deletion or account
erasure (ADR-006) the web client calls the WebAuthn Signal API where supported
(`signalUnknownCredential`, `signalAllAcceptedCredentials`) so the provider removes the orphaned
passkey; credential rows are deleted with the account and the audit trail keeps only
non-identifying events.

### 8. Sessions, refresh tokens and device binding

**Access token.** JWT (`typ: at+jwt`, RFC 9068), ES256, 15-minute lifetime, `aud: pennilogic-api`,
`iss` = the api issuer, `sub` = opaque account UUID, `sid` (session), `dev` (device UUID),
`cnf.jkt` (DPoP key thumbprint), `amr` (`passkey`, `recovery_code` or `channel`), `acr`
(`trusted`, `recovering` or `unattested`), `auth_time`, `iat`, `exp`, `jti`, minimal `scope`. No
email, phone, name or any personal data in any token (`NoPiiInTokensTest`). Every request also
checks a per-`sid` revocation set cached for at most 60 s, so revocation propagates within 60 s
rather than the 15-minute lifetime; that 60 s is the published bound for "sign out everywhere".

**Refresh token.** 32 random bytes (base64url), stored only as SHA-256, grouped in a family per
sign-in with `family_id`, `device_id`, `jkt`, `created_at`, `rotated_at`, `revoked_at`,
`revocation_reason ∈ {reuse_detected, binding_mismatch, signout, signout_all, absolute_expiry,
recovery, not_me, admin}`. Each refresh rotates: a new token is issued, the previous is marked rotated.
Sliding lifetime 30 days from each rotation; absolute family lifetime 90 days, then a fresh passkey
assertion is required. Grace window 30 s, measured on the server clock from the recorded
`rotated_at` of the previous token to the server receipt time of its second presentation, inclusive
at exactly 30.000 s: within the window the previous token returns the same new pair (the
concurrent-refresh race); a rotated token
presented outside the window, or any token from a revoked family, revokes the entire family,
writes `auth.refresh.reuse_detected`, notifies the user and forces re-authentication. The client is
told `session_revoked` with a reason code, never token internals. Rotation counters distinguish
grace resolutions from reuse revocations (api#5 observability). Rotation is serialised per family
(row lock or equivalent) so two concurrent refreshes can never both mint; the second either receives
the grace result or waits.

**Device binding — yes, by DPoP.** Every session is bound to an asymmetric key generated on the
device: the client sends a DPoP proof (`htm`, `htu`, `iat` within ±60 s, unique `jti` cached
300 s, `ath` on resource requests) on the token endpoint and on every API call; access and refresh
tokens carry the key thumbprint and are rejected with any other key. The api requires its
`DPoP-Nonce` at the token endpoint, and every resource endpoint answers a proof whose `iat` is
outside the window, or whose `jti` was seen, with `WWW-Authenticate: DPoP error="use_dpop_nonce"`
and a fresh nonce (RFC 9449 §8–§9), so a device whose clock is skewed self-heals on the next request
instead of being locked out and resource replay is bounded by the nonce lifetime rather than the
client clock (`DPoPSkewRecoveryTest`, `DPoPAccessTokenHashTest`). On **Android** the key lives in the Android Keystore, StrongBox when
available, non-exportable, without a user-authentication requirement (the passkey supplies user
presence; the DPoP key signs every request). At device registration the app submits the Keystore
**key attestation** chain for that key with a server challenge; the attestation request includes
**no** device-identifier or device-properties extension (no `setDevicePropertiesAttestationIncluded`,
no ID attestation); the api verifies the chain to the
Google hardware attestation roots, the security level (`TrustedEnvironment` or `StrongBox`), the
package name and signing digest, stores only the derived `attestation ∈ {hardware, software, none}`,
the security level and `jkt`, and discards the chain — it is never retained
(`AttestationNoDeviceIdentifiersTest`). The verdict sits
alongside the Play Integrity standard-request verdict policy owned by `T-SEC-05`. Every device row also
carries `trust ∈ {trusted, recovering, unattested}`: `trusted` after a passkey assertion with UV on a
device whose attestation is `hardware`, `unattested` for the fallback below, `recovering` for a device
registered through §10 until §11 clears it; `acr` in the device's tokens equals its `trust`. On **web** the key
is a non-extractable WebCrypto P-256 key persisted in IndexedDB; the access token is held in script
memory only (DPoP's `ath` needs it) and never in persistent script-readable storage, the refresh token travels in an
`HttpOnly; Secure; SameSite=Strict` cookie (web#8) and `device.attestation = none`, `trust = unattested`. On web, DPoP
defeats token exfiltration, not in-page abuse by injected script; web#8's nonce-based content
security policy is the control for that. Losing the key (cleared app data, device reset, new browser
profile) simply ends the session; the next sign-in is a passkey assertion and a new device record.

**Fallback when attestation is unavailable** (API 26–27, custom ROMs, attestation failure): the
device is still registered with a software-held DPoP key and `attestation = software|none`,
`trust = acr = unattested`; it may sign in and read, but every step-up operation (§9) always requires a
passkey step-up no older than 300 s, and the `T-SEC-05` matrix decides sync and export policy. No
device is refused for lacking hardware attestation; none is trusted more than its evidence.

**Legitimate device change versus takeover.** A legitimate device change never moves a token: the
new device performs its own passkey assertion (synced passkey or hybrid QR flow) and receives its
own family, device record and key; the old device remains valid until the user signs it out, and
every channel plus every registered device receives "new device signed in" with the coarse device
model and, optionally, an approximate network location derived at send time from the request
address and never stored — shown only when the resolver reports high confidence, always framed as
approximate, and never itself a takeover verdict (carrier-grade NAT makes city-level lookups wrong
often enough that a confident "Mumbai" on a Pune user's phone is a false alarm; docs#88/docs#103 own
the copy). A device registered through §10 recovery is `trust = recovering` until the
§11 conditions are met. A takeover indicator is a token presented with a mismatched `jkt`, from a
revoked family, or after `sid` revocation: the family is revoked immediately, `auth.binding_mismatch`
is written, the user is notified and a fresh passkey assertion is required. Sign-out-everywhere
needs no step-up (it is protective) and revokes every family and device including the current one
within the 60 s bound, so a stolen session cannot use it to evict the owner while keeping itself
(`SignOutEverywhereIncludesCurrentSessionTest`, `RevocationPropagationBoundTest`);
the next sign-in is a passkey assertion. Local biometric app-lock (T-SEC-05) protects the local database and is not a server factor.

### 9. Step-up

A **step-up operation** requires a fresh passkey assertion with user verification no older than
300 s, minted as a single-use step-up token bound to `sid`, `jkt`, the one operation (`op`) and
`rq` = base64url(SHA-256(canonical operation parameters — the target credential, device, channel,
grant or export scope)), verified at execution so a confirmation obtained for "remove device A" cannot
be spent on device B (`StepUpTargetBindingTest`); replay is rejected (`StepUpReplayTest`). Step-up
operations apply to established authenticated sessions only: enrolment-time channel verification
(no account, no session yet; §2) and the one-shot first-credential rule of §10 sit outside this list.
Step-up operations: data export; account deletion;
sharing invitations, acceptances and grant changes; adding, removing or renaming a credential;
regenerating recovery codes (the once-only display of the new set is part of regeneration; reading
the count of unused codes needs no step-up and nothing else can be "viewed"); adding, removing or verifying a channel; adding or
replacing an AI provider key or custom endpoint (ai-service#2); removing a device. The
**window-restricted list** of §11 is this list plus detail-level reads of other members' shared
data. The
**young-credential rule**: on an account whose oldest credential is at least 24 h old, a credential
younger than 24 h cannot satisfy step-up for a step-up operation; the refusal returns the client
condition `step_up_credential_too_new` with the absolute instant at which the credential matures; an attacker who adds a passkey
must wait a day during which the owner is notified and can remove it, while the owner's own older
credential is never blocked. A brand-new account (all credentials younger than 24 h) is exempt: there
is no established owner to protect.

### 10. Recovery

**Routes.** Exactly two, enumerated in the contract so no client can invent a third:
`recovery_code` and `channel_reverification`. Support-operated recovery is not defined here;
`T-SUP-01` may add it only with proof at least as strong, the same cooling-off and ADR-020's
four-eyes controls. Recovery initiation, verification, cancellation and completion return identical
bodies, statuses and timing bands whether or not the account, channel or code exists — including
when a limiter applies: a limited request is accepted-and-dropped with the same shape, never a
distinct `rate_limited` response (`RecoveryEnumerationTimingTest`).

**Proof before anything counts.** An initiation is *unproven* until the initiator presents a valid
recovery code or proves the channel; only proven initiations start a window, notify every channel
and device, or count against the account. Before proof, the only outbound effect is the OTP or link
to the proving channel itself, and the only limiter is per source (request address and, when
present, DPoP key), applied silently. So a stranger who knows an email can neither spend the
owner's recovery budget, nor spam the owner's devices, nor learn whether the account exists
(`RecoveryRateLimitIndependenceTest`, `UnprovenInitiationHasNoAccountEffectTest`).

**Recovery codes.** 10 codes per set, each `S-XXXXX-XXXX`: a 1-character Crockford slot prefix
(`0`–`9`) plus 9 Crockford base32 secret characters (45 bits), shown grouped, entered in any case
with or without separators. Server normalisation before hashing and before comparison: uppercase;
strip hyphens, spaces and other whitespace; map `O→0`, `I→1`, `L→1` (Crockford); clients mirror the
same tolerance in their input formatting (`RecoveryCodeNormalisationTest`). The slot prefix selects
exactly one stored hash, so verification costs one argon2id evaluation, and an unknown account is
answered with one evaluation against a fixed dummy hash in the same timing band; argon2id work is
capped per source and globally by a bounded worker pool (`RecoveryCodeVerificationCostTest`).
Generated by the server's CSPRNG, displayed exactly once on a secure-window surface
(screenshot-suppressed, excluded from backup and autofill) with copy, download and print, and never
returned again. Stored as `argon2id(normalised_secret, 16-byte per-code salt; m = 64 MiB, t = 3,
p = 1)`; a database read yields nothing usable (`RecoveryCodeHashedAtRestTest`). A code is consumed
on success and cannot be reused. Failed attempts are limited per source (10 per 24 h per address or
DPoP key) and per account: 5 failed attempts within 24 h **against one account's code set** — an
attempt is attributable to an account when the initiator has already proved the account's channel
or presented a valid code for it in this recovery request, or when the request is a code attempt
inside a proven `channel_reverification` flow; anonymous attempts against an email are per-source
only — after which the `recovery_code` route for that account is locked for 24 h and every channel is
told (`recovery_locked` carries the absolute lift instant); a proven channel holder may lift the lock
early; login is never affected (`RecoveryCodeLockTest`).
Sets are versioned; **regeneration creates a new set and atomically deletes every code of the
previous set** (deleted, not merely marked), requires step-up, notifies every channel and is offered
when two or fewer codes remain. The clients expose the count of unused codes, never the codes.

**Channel reverification.** Proves control of a channel verified at enrolment and mature for at
least 7 days; a channel added during a recovery flow or younger than 7 days is refused. Email is the
mandatory verified channel (transactional email is owner approval item OI-3) and one account exists
per verified email; phone is optional and exists only when OI-4 is approved. Proof is a 6-digit OTP
or single-use link valid 600 s, 5 attempts per send. Proving a second channel does not shorten the
window. The per-account budget is **3 counted initiations per 7 days**, where an initiation counts
only while it is *pending* (proven and its window not yet ended) or once it has *completed and not
been reversed*; an initiation that is cancelled — through the credential-less link, from a
signed-in session, or from the in-app path the notification deep-links into — or that is reversed by
"not me" does not count, so no channel holder, however they cancel, can exhaust the owner's budget
(`RecoveryInitiationLimitTest`, `VetoDoesNotExhaustOwnerInitiationsTest` over all three cancellation
paths and "not me"); sends are limited per address and per source because
every send is spend.

**Mandatory channel invariant.** An account always has at least one verified email; removing the
last one is refused (`LastChannelRemovalRefusedTest`). Replacement is: add and verify the new email
(both channels and every device notified) → wait for its 7-day maturity → remove the old one
(`ChannelReplacementMaturityTest`). A channel removal notifies the removed channel and is reversible
from it for 24 h, mirroring the young-credential rule, so an attacker holding step-up cannot strip
the owner's recovery channel unnoticed. **Removal takes effect immediately for the veto** — the
7-day maturity applies only to a *new* channel proving recovery, never to ending an old one: from the
moment of removal the removed channel receives no further recovery notifications, its outstanding
cancellation and "not me" links are void, any pending initiation it proved is cancelled (not counted),
and its 24 h reversal link can only restore the channel, not act on recoveries
(`ChannelRemovalEndsVetoTest`).

**Total credential loss.** No device, no synced passkey, no codes, but a mature channel →
`channel_reverification` (72 h). No credentials and no channel → unrecoverable through
self-service by design: a path that recovers an account from zero proofs is a path an attacker can
walk; the person may create a new account, and erasure of the old one goes through the identity
verification `T-SUP-01` defines.

**Completion effects.** The completion notification carrying the "not me" link is dispatched to
every channel and to every device registered before completion **before** their revocation takes
effect, and push registrations of revoked devices stay addressable for the 24 h "not me" window so
the owner's own phones — where they will actually notice — receive it
(`NotMeReachabilityAfterRevocationTest`, with android#41). Then every session, refresh family and
device is revoked (`PostRecoveryRevocationTest` replays a pre-recovery refresh token and asserts
rejection); stored AI provider credentials are suspended (ai-service#2); the recovering device is
registered with `trust = recovering`; the account enters the 24 h restricted period of §11; existing
passkeys are **kept** (the owner may still hold them) and listed for review — removal becomes possible
once the owner holds a step-up-capable credential again (see the timeline).

**First credential after recovery (the one-shot rule).** On the recovering device only, the
recovery proof itself (`amr ∈ {recovery_code, channel}`) satisfies step-up for **exactly one**
`credential_add` at any time during the restricted period; the resulting passkey is subject to the
young-credential rule (it cannot confirm other step-up operations until it is 24 h old, counted from
its creation), and a UV assertion with
it after the restricted period has ended clears `recovering` on that device. Every other step-up
operation, including `credential_remove`, still requires a passkey. If the one-shot is not used
within the restricted period, the recovering session ends when the period does and the person
recovers again (`PostRecoveryFirstCredentialTest`). **Incapable devices:** recovery can only be
initiated from a device or browser that can hold the resulting passkey. An API 26–27 phone, a phone
with no passkey-capable provider, or a browser without WebAuthn (§2) is refused at initiation with the
client-owned `authenticator_unavailable` condition and the same content as §2 (what still works; use
a passkey-capable device or browser to recover, then attach this device) — the initiation is not
sent to the server, so nothing counts and nothing is notified. The hybrid (cross-device) flow is
deliberately not used to satisfy the one-shot: it would enrol the passkey on a *different* device than
the one the recovery proof was bound to, breaking the "recovering device only" rule
(`RecoveryRefusedOnIncapableDeviceTest`, android#39 and web#8).

**Recovery timeline (the phases clients render; design owns copy, this record owns the phases).**

| Phase | Starts | The person can | Contract returns |
|---|---|---|---|
| 0 Unproven | initiation | Receive the OTP/link on the proving channel; nothing else happens | identical anti-enumeration shape |
| 1 `notification_pending` | proof accepted, no notification accepted by a provider yet | Cancel; use the device in local-only mode (§2: capture, manual entry, local analysis; nothing syncs) | `state: notification_pending`, `window_ends_at: null`, `retry_after` |
| 2 Cooling-off | first notification accepted | Cancel; local-only mode; the pending screen (S-AND-007) works offline with the last-known instant | `state: cooling_off`, `window_ends_at` (24 h code route / 72 h channel route) |
| 3 Restricted period | completion | Sign in on the recovering device; read own data; enrol the one-shot first passkey (its 24 h young-credential age runs from creation, so enrolling at completion lets phases 3 and 4 overlap); cancel via "not me" | `state: restricted_after_recovery`, `restricted_until`, `not_me_until` |
| 4 Young credential | first passkey enrolled (may overlap phase 3) | Everything except step-up operations with that passkey until it is 24 h old; sync resumes when the restricted period ends | `step_up_credential_too_new` with `matures_at` when refused |
| 5 Full function | restricted period ended **and** first passkey ≥ 24 h old | Remove unknown credentials, regenerate codes, everything | — |

Honest totals after losing the only device: a restricted signed-in session on the new device at
24–72 h (the window, given the notification is accepted promptly); full function at **48–120 h** —
48 h if the code route is used and the one-shot is enrolled at completion (24 h window + 24 h
restricted period, with the young-credential age running concurrently), 120 h if the channel route
is used and the one-shot is enrolled only at the end of the restricted period (72 h + 24 h + 24 h).
Locally captured data from phases 1–3 merges after completion under the sync owner's rules (ADR-010,
`T-SYN`); this record only guarantees nothing is lost or synced early.

**What an attacker who controls the recovery channel gains.**

| Attacker holds | Can | Cannot | Owner's counter |
|---|---|---|---|
| Email (or SIM, once phone is a recovery channel) only | Start `channel_reverification`; after 72 h with no cancellation, hold a `recovering` session that can read the account's own data and enrol one passkey; full access once the restricted period has ended and that passkey is 24 h old — T+96 h at the earliest (enrolled at completion), T+120 h at the latest. Also **veto** the owner's own recovery attempts through the credential-less cancellation and "not me" links delivered to that channel | Sign in before 72 h; export, share, change channels, regenerate codes, use provider keys or read shared partners' details before T+96 h; exhaust the owner's initiation budget by any cancellation path; act silently — every channel and device is notified at proof, completion and each credential change | Cancel from any signed-in device or from the link on any other channel; sign out everywhere; remove the compromised channel with step-up (ends the veto); regain the channel at its provider; "not me" for 24 h after completion |
| Email + one recovery code | Same, with a 24 h window instead of 72 h | Skip the notifications, the restricted period or the young-credential wait | Same; plus "not me" now deletes the whole code set (§11) |
| Unlocked device with an active session | Read whatever the session allows | Any step-up operation without passkey UV; move the session elsewhere (DPoP) | Sign out everywhere from web or another device; the passkey's biometric gate |
| All channels and all devices | Complete recovery unobserved | Nothing else is possible for the owner either | None — this is the total-loss case above |

The combination that makes takeover expensive is: cooling-off + notification to every channel and
device + cancellation from unenrolled devices + "not me" reversal + restricted period +
young-credential wait + no SMS or email as a *login* factor. A SIM swap alone can complete a
phone-route recovery only if phone has been made a recovery channel (OI-4), the owner ignores 72 h
of notifications on email and every device, and then a further 24 h of restricted-period
notifications; it never shortens a window and never serves as a login factor. **Residual risk,
stated:** whoever holds a verified channel can cancel or reverse a recovery, because the
cancellation and "not me" links are deliberately usable without any credential. That is a veto, not
access; it does not consume the owner's initiation budget, it costs the attacker continuous
attention, and the owner ends it by removing the channel from any signed-in session or by regaining
the channel at its provider. Three properties keep the veto from becoming anything more: (1) only
pending or completed-unreversed initiations count, so neither device-cancelled proofs nor
link-cancelled ones exhaust the owner's budget, and unproven initiations never notify, so a channel
holder cannot spam the owner's other channels and devices either; (2) the per-account code lock is
not a second veto instrument — by the attribution rule above, only attempts made after proving the
account's channel or presenting a valid code for it can lock the code route, and a holder who has
proved the channel can already initiate the channel route, so the lock adds nothing they lack, while
anonymous guessing never locks; (3) removing the channel ends the veto at once (above), not after a
maturity period. No lock follows a cancellation or a "not me", so a veto cannot become a lockout.

### 11. Cooling-off periods and restricted capabilities

| Trigger | Window | What is delayed | Notifications | Cancellation |
|---|---|---|---|---|
| `recovery_code` recovery | 24 h | Any credential change or new session for the recovering party | All channels and devices at proof and completion | Signed single-use link, valid for the whole window, works from an unenrolled device; cancelling aborts recovery and keeps every existing credential and session; a successful passkey sign-in while a recovery is pending surfaces it and offers cancellation |
| `channel_reverification` recovery | 72 h | Same | Same, plus a reminder 24 h before completion | Same |
| Post-recovery restricted period (`restricted_after_recovery`) | 24 h after completion | The step-up operations of §9 except the one-shot first `credential_add`, plus detail-level reads of other members' shared data; rendered as the authentication-owned restricted state, never as a sharing denial | "Recovery completed" with the "not me" link, dispatched before revocation | "Not me" (valid 24 h after completion) revokes every session, device and credential created since initiation; for a channel-route recovery flags the proving channel `suspect` until re-verified with step-up; for a code-route recovery atomically deletes the entire current code set and any set created since initiation, notifies every channel and tells the owner to regenerate once they hold a step-up-capable credential (`NotMeInvalidatesCodeSetTest`) |
| Credential change on an established account (passkey added/removed, channel added/removed, code regeneration) | 24 h | Nothing for the owner's older credentials; the new credential cannot satisfy step-up (young-credential rule, `step_up_credential_too_new`) | Old and new channel, all devices | Remove the new credential with an older credential's step-up; reverse a channel removal from the removed channel |

During a pending recovery the owner's existing credentials and sessions are untouched; only the
recovering party waits, in local-only mode (§10 timeline). A window starts only once at least one
notification has been accepted by its delivery provider; until then the initiation is held as
`notification_pending` (`window_ends_at: null`, a `retry_after` hint, the one action = cancel) and
retried, so an outage can delay a recovery but never make it silent and no client may estimate or
invent a completion time (`WindowStartsOnlyAfterNotificationAcceptedTest`). During the post-recovery
period the server enforces the window-restricted list on every request
(`RestrictedCapabilitiesDuringWindowTest`); the client renders the authentication state `T-AUTH-01`
owns and never claims recovery is instant. **Interaction with device binding:** the device registered
by recovery carries `acr = recovering` in its tokens until the period ends *and* one passkey
assertion with UV — with the one-shot credential or any other passkey of the account — has succeeded
on it; a device that never performs that assertion stays `recovering` and cannot leave the
window-restricted list. The 24 h value matches the pending-activation period already fixed for
high-risk provider-key changes in ai-service#2.

### 12. Phone verification and trial-abuse controls

**Decision.** Phone verification is an optional, owner-approved anti-abuse control, not an
authentication factor and not a sole recovery route. It ships disabled: sending an OTP is
per-message spend and India requires TRAI DLT sender and template registration, so enabling it is
owner approval item OI-4 (SMS provider named by the owner; this record names none). When enabled:
6-digit OTP valid 600 s, 5 attempts, per-phone-hash and per-address limits, the number stored under
ADR-018's `channels.value` class: the HMAC blind index always (that is all the trial check needs);
the encrypted recoverable value only when the owner decides at OI-4 that phone is to serve as a
recovery or notification channel (owner decision OI-4b, recorded as `owner_inputs.phone_as_recovery_channel` in §15, default false);
never a clear value. The OTP is never logged; auto-read on Android only through the SMS Retriever API
— never the finance parser and never `READ_SMS` (ADR-004). A verified phone becomes a recovery
channel only after the 7-day maturity of §10 and never shortens a window.

**Trial-abuse controls independent of any vendor.** (1) One free trial per verified channel hash
— email at MVP, phone once OI-4 exists — with a server-side `trials_used <= 1` constraint
(`OneTrialPerChannelHashTest`); (2) Play Billing introductory-price eligibility for Play-billed
trials; (3) the Play Integrity device and account verdict policy of `T-SEC-05` at trial start; (4)
velocity limits keyed on the attested DPoP device key (a stable, consented device identity that is
not a fingerprint of personal data); (5) refusal of known disposable-email domains; (6) trial AI
quota is already small and server-authoritative (ADR-007, ADR-023) so the prize is small. Phone
verification, when approved, adds friction to (1); nothing else depends on it.

### 13. Workload identity and non-forgeable delegated user context

**Workload identity.** Every service-to-service call (api → ai-service, ai-service → api tool
endpoints, admin → api) is authenticated by a **workload token**: a JWT (`typ: wl+jwt`) signed by
that workload's own asymmetric key, `iss` = the workload identity (`api`, `ai-service`,
`admin`), `aud` = the target (`pennilogic-api-tools` for the api's tool endpoints,
`pennilogic-ai-service`, `pennilogic-api-admin`),
`exp` ≤ 300 s, unique `jti` cached for the lifetime, sent over TLS inside the private network
(ai-service#2 keeps the gateway unreachable publicly). Each service verifies callers against a
per-workload JWKS distributed by infra configuration. Keys rotate every 90 days with a 24 h
dual-key overlap; revocation is removal of the `kid` from the JWKS (effective within the 60 s JWKS
cache) plus an explicit `kid` deny-list for emergencies. If the runtime platform chosen by ADR-022
provides workload identity (SPIFFE, cloud OIDC, mTLS), it may issue these tokens instead of static
keys with the same claims, audiences and lifetimes; the verification rules do not change. Public
clients (Android, web) never receive workload keys or tokens; a user access token presented to the
ai-service is rejected.

**Four audiences, three token types, one dispatch rule.** Customer endpoints carry `aud
pennilogic-api`; the api's tool endpoints `pennilogic-api-tools`; the ai-service
`pennilogic-ai-service`; admin endpoints `pennilogic-api-admin`. Every verifier dispatches on `typ`
and key class **before** reading any other claim: customer endpoints accept `at+jwt` only, signed
with the user-token `kid` class, and require `cnf.jkt` to equal the DPoP proof key — a token without
`cnf`, or any `wl+jwt`/`dlg+jwt`, is rejected with `auth.token.type_mismatch`; tool endpoints accept
`dlg+jwt` (plus the presenter's `wl+jwt`) only; workload verification accepts `wl+jwt` only; admin
endpoints accept the operator delegation of ADR-020 only. A delegation token therefore never carries
`pennilogic-api`, so a compromised ai-service holding a live `dlg+jwt` cannot use it against a
customer endpoint even if a verifier forgot the `typ` check (`TokenTypeConfusionTest`); customer
endpoints reject `pennilogic-api-admin` and admin endpoints reject `pennilogic-api`
(`AudienceSeparationTest`).

**Delegated user context.** When the api acts for a user it mints a **delegation token**
(`typ: dlg+jwt`, ES256, separate `kid` class from user access tokens): `iss = api`,
`aud = ["pennilogic-ai-service", "pennilogic-api-tools"]`, `sub` = account UUID, `act.sub = api`
(the workload that minted it), `azp = ai-service` (the workload allowed to present it back),
`sid`, `scope` narrowed to the tool surface, `acr`, `iat`, `exp` ≤ 120 s, unique `jti`,
`rq` = base64url(SHA-256(originating request identifier)) binding it to the one user request being
served. **Minting owner:** no existing api ticket owns the api → ai-service call path that mints
`dlg+jwt` (api#36 covers the tool-endpoint *verification* direction only), so the coordinator opens
one new api ticket — "Mint and verify delegation tokens on the assistant call path" — depending on
this record, contracts#10 and ai-service#2; until it exists, no api code may call the gateway. The ai-service accepts a delegation token only together with a valid `api` workload token
and only for the originating request named by `rq`; the api's tool endpoints accept it only
together with a valid `ai-service` workload token whose `iss` equals `azp`, only while the `jti`
is in the api's own issued-and-unexpired set, and never after the originating request has
completed. The request body has no authoritative user-scope field (contracts#10): any subject
appearing in a body or header must equal `sub` or the request is rejected. Rejections, each with its own reason code and
conformance test: omitted subject (`OmittedSubjectTest`), forged signature or unknown `kid`
(`ForgedWorkloadIdentityTest`), wrong or missing audience (`WrongAudienceTest`), expired
(`ExpiredWorkloadCredentialTest`), replayed `jti` or mismatched `rq` (`ReplayedDelegationTest`),
`scope` wider than the api allows for that tool or a `sub` that differs from the session's
(`WidenedSubjectTest`). Only the api holds a delegation-minting key; the ai-service holds none, so
a compromised model or a leaked public-client credential cannot mint workload identity or widen a
subject (`ModelCannotMintTest`: a token signed with the ai-service key is rejected by the api).

**Admin → api.** The admin service presents its workload token plus an **operator delegation token**
issued by the administrative identity domain that ADR-020 defines. Its claim set is ADR-020's (§7 and
§10 item 5): `sub` (operator identity), `sid`, `iss`, `aud = pennilogic-api-admin`, `act.sub = admin`,
`acr` (the administrative values ADR-020 defines; not this record's customer `acr` set), `iat`,
`exp` — no ticket or access-basis claim: the access basis is an operation parameter per ADR-020
§4.3. ADR-020 owns the values and lifetimes of every claim in that set; this
record fixes only the envelope and the audience separation: customer endpoints never accept the
admin audience, admin endpoints never accept `pennilogic-api`, and operator identity never shares
the customer RP ID.

### 16. Contract, schema and interface consequences this record forces

- **Authentication contract group (contracts#1, consumed by api#4/api#5/api#57):** registration
  options and result; authentication options and result; `POST` token endpoint with
  `grant_type=refresh_token`, `DPoP` header and `DPoP-Nonce` challenge (`WWW-Authenticate: DPoP`,
  `use_dpop_nonce`); device registration carrying the key attestation chain; credentials list,
  rename and delete; sessions and devices list, revoke one, sign out everywhere; recovery
  initiation, verification, cancellation and completion with `route` as the two-value enum; "not me";
  recovery-code regeneration; channel verification and removal; step-up assertion returning the
  single-use step-up token; the root-level `DPoP` security scheme so no operation is generated
  without a security requirement. Every window end (cooling-off completion, restricted-period end,
  "not me" expiry) is returned as an absolute UTC instant in the ADR-015 representation; clients
  render it locally and never compute it.
- **Error catalogue bindings (contracts#1 → client-state taxonomy):** `rate_limited` for every
  limiter here except the recovery limiters, which are accepted-and-dropped (limit, window and lift
  time in the shape); `validation_rejected` for malformed ceremonies; the authentication-owned
  conditions `session_revoked`, `step_up_required`, `step_up_credential_too_new` (carries the
  absolute `matures_at`), `restricted_after_recovery` (carries `restricted_until` and
  `not_me_until`), `recovery_notification_pending` (carries `window_ends_at: null` and
  `retry_after`), `recovery_locked` (carries the absolute lift instant) bound by `T-AUTH-01` before
  any client ships them; `authenticator_unavailable` bound by the client platform owners (§2);
  identical anti-enumeration shapes for every recovery operation.
- **Machine-readable mirror:** the §15 block as a schema component in the contracts repository,
  with the literals for OI-1 and OI-2 bound there and a test that the mirror equals this block on
  every non-placeholder field.
- **Internal contract (contracts#10 and the admin contract group):** the `wl+jwt` and `dlg+jwt`
  envelopes with audience, issuer, subject, actor, presenter, expiry, request binding and replay
  identifier; the four audiences and the `typ`/key-class dispatch rule of §13; no authoritative
  user-scope field in any request body.
- **Database (api):** the identity row is ADR-018's **`users`** (opaque UUID, `webauthn_user_handle`,
  display name — no email or phone; this record calls it the *account* in prose and the token `sub`
  is `users.id`; ADR-018's financial `accounts` table is unrelated, and `channels.account_id`
  references `users.id`), `channels` (type, value under ADR-018's blind-indexed class, `verified_at`,
  `matured_at`, `suspect`),
  `credentials` (public key, credential ID, AAGUID, transports, BE/BS, counter, name, flags, timestamps),
  `devices` (`jkt`, platform, attestation level, trust, timestamps), `sessions`, `refresh_tokens`
  (hash, family, rotation and revocation fields), `recovery_code_sets` and `recovery_codes`
  (slot, argon2id hash, salt, `used_at`), `recovery_requests` (route, state, window ends, cancellation and
  "not me" link hashes), `step_up_assertions`, and authentication events written through the shared
  audit service (`T-SEC-03`, api#39). Refresh, recovery-code and link values are never stored in
  the clear.
- **Lifecycle (retention and purge of authentication artefacts):** these rows are *product* data
  kept only while they serve a purpose; the *events* live in the `T-SEC-03` audit store under the
  `T-CMP-04` retention profile and are the only long-lived record. Superseded recovery-code sets are
  deleted on regeneration or "not me" (not marked); `refresh_tokens` rows are purged 30 days after
  family revocation or absolute expiry (the reuse-detection horizon); `devices` and `sessions` are
  purged when no live family remains for them; `recovery_requests` are purged 30 days after their
  window or "not me" period ends; `step_up_assertions` 24 h after expiry; attestation chains are
  never stored (§8); `channels.suspect` clears on re-verification and leaves only an event. All
  purges are restore-safe per `T-SEC-07` (a restored backup must not resurrect purged rows); values
  are in the §15 `lifecycle` object (`AuthArtefactRetentionTest`).
- **Purposes of `channels.value` for the `T-CMP-01` purpose registry (api#24):** (1) account
  uniqueness and sign-up verification; (2) recovery lookup and channel reverification; (3) security
  notifications (recovery, new device, credential and channel changes); (4) the trial-abuse channel
  hash (§12). No other purpose — in particular no marketing use — is authorised by this record, and
  a later purpose is a consent-ledger change, not an authentication change.
- **Interface with ADR-018 (data-protection floor), stated explicitly:** (1) ADR-019 **relocates the
  contact values**: the `users` row carries no email or phone; both live in `channels`, and their
  encryption at rest plus the one equality-searchable blind index this record needs (recovery
  initiation lookup, the one-account-per-verified-email rule and the phone trial-hash of §12) are
  ADR-018's to specify — ADR-019 requests no other searchable identity field. (2) ADR-019 **adds no
  in-database token verification**: access-token, DPoP, step-up, workload and delegation
  verification happen in the `api` process; the api then calls ADR-018's row-level-security trusted
  setter (`begin_request`, ADR-018 §5) with the API-verified `users.id` (for tool calls, the
  delegated `sub`), the `acr` value the window-restricted list needs, and the request/actor
  parameters ADR-018 §5 defines (`p_actor`, `p_targets`, `p_level`) — never a token. The database
  never receives, parses or verifies a token.
- **Android manifest and hosting (android#20, web#8, infra):** App Links intent filters with
  `autoVerify` on the RP ID host; `/.well-known/assetlinks.json` and `/.well-known/webauthn`
  served from the apex with the exact content types; production and staging files never mixed.
- **Client-state taxonomy:** the server-owned authentication conditions above are new identifiers
  under `T-AUTH-01` ownership; `authenticator_unavailable` is client-owned (§2); this record does not
  edit the taxonomy.

### 17. Security and privacy consequences

**Of the chosen options.** Phishing-resistant, origin-bound primary credential; no password
database, no reset mail, no credential-stuffing surface; tokens unusable off their device; a stolen
refresh token is usable at most once and its use is detected; recovery takeover requires the owner
to ignore notifications on every channel and device for 48–120 h before the attacker reaches full
function (24–72 h before a restricted session exists); a SIM swap alone can only ever
complete a phone-route recovery under the same notified windows and never shortens one;
the identity artefacts at rest are credential public keys, `jkt` thumbprints, hashed refresh
tokens, hashed recovery codes and hashed or ADR-018-encrypted channel values — none is a reusable
secret, and the email value is kept for exactly the four purposes enumerated in §16; tokens carry no personal
data; the credential provider learns the
user's email through `user.name`, which is the user's own provider; the api holds the verification
code, so its correctness is our review burden (mitigated by R-8 and the conformance tests); key
attestation and Play Integrity give device evidence without fingerprinting.

**Of the rejected options.** Passwords: stuffing, reuse and reset-mail takeover. SMS OTP login:
SIM swap, SS7 and phishing kits, plus a per-message cost that grows with attack volume. Self-hosted
identity server: a second privileged store of identity data to patch, back up and residency-check.
Managed vendor: identity data outside the India region, vendor session semantics, exit by
re-enrolment. Deleting passkeys on recovery: an attacker who wins recovery would evict the owner
instantly. Instant recovery: the silent takeover this design makes impossible.

**Invariants.** A compromised model, a leaked public-client credential or a stolen user token cannot
mint workload identity or widen delegated scope; raw SMS never leaves the device even for OTP
auto-read; no credential, OTP, recovery code, refresh token or link value appears in logs, traces,
analytics or diagnostics bundles; every limiter is server-side; every authentication outcome is an
audit event.

**Coercive situations.** A person forced to perform a biometric step-up on their own device is
outside what any server control can detect; this record contributes the young-credential rule, the
notification of every credential and device change to every channel, the device list with one-tap
removal and sign-out-everywhere, and the veto property above, which also lets a victim who still
holds a channel stop an abuser's recovery attempt. Duress unlock and rapid conceal are android#49's.

### 21. Rollout and rollback

Adopted on merge. Nothing here is deployed by this record. Production enablement follows the §5
rollout order and is gated on OI-1, OI-2 and OI-3; OI-4 gates phone features only. Reversing any
decision here requires a superseding record that states the migration cost: for the RP ID that cost
is a full credential reset (§4); for the token model it is a forced re-authentication of every
session; for the recovery model it is a re-issue of every recovery-code set and a re-notification of
every account; for the provider it is the R-4 export and import under the unchanged RP ID.

### 22. Rejected options — consolidated

| Rejected | Why |
|---|---|
| Passwords at MVP | Second, weaker credential system kept forever; migration campaign later; api#4 rewrite either way |
| SMS OTP as authentication factor or sole recovery route | SIM swap, phishing, spend, DLT; phone becomes the account |
| Deferring passkeys to E19 | RP ID must be fixed now anyway; contradicts the security checklist |
| Self-hosted identity server (Keycloak, ZITADEL, Ory, Hanko) | Fails R-5 and R-6; second identity store; custom SPI code for the semantics this product needs; same verification core available as a library |
| Managed vendor (Cognito, Auth0, Stytch, Clerk, Firebase Auth) | Spend without approval, residency, R-6, exit; vendor choice follows requirements — criteria recorded in §1 |
| Subdomain RP ID or per-client RP IDs | Unfixable later; blocks moving the web app between hosts; Android and web would not share credentials |
| Sharing the RP ID with the admin console | Breaks ADR-014's separate authentication domain |
| Device fingerprinting as the binding | Not a secret, not consented, and personal data; DPoP keys are both stronger and cleaner |
| Unbound or long-lived bearer refresh tokens | Token theft equals account theft |
| Instant recovery; knowledge questions; deleting passkeys on recovery | Silent takeover; guessable; evicts the owner |
| Requiring attestation or device-bound passkeys only | Excludes synced platform passkeys and most of the launch market |
| Related Origin Requests as a domain-migration tool | Extends origins for an RP ID; cannot move credentials |
| Certificate-only (mTLS-only) workload identity at MVP | Needs a private CA and issuer infrastructure not yet decided (ADR-022); the JWT envelope carries the same claims and can be issued by mTLS/SPIFFE later |

**Revisit if:** the owner approves identity-provider spend and a vendor passes every §1 row; the
platform limit for related-origin labels changes; passkey portability or the Signal API changes on
Android; hardware attestation coverage in the launch market makes the `unattested` fallback
unnecessary; ADR-022 provides platform workload identity that should issue the §13 tokens; or a
regulator requires a recovery assurance level this design does not reach.
